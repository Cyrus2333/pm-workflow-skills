# 排课 C 端案例：从“规格完整”到“人类可读交付”的执行层复盘

> 案例类型：复杂 C 端需求 / 多系统协作 / 多状态视觉交付  
> 分析对象：新增协作交付能力之前的 `pm-workflow-skills` 上游基线  
> 案例用途：识别已有产品方法与尚未闭环的交付执行能力，支持 Skill 设计和回归验证  
> 边界说明：本案例是新增协作交付能力的设计依据，不用于证明新增 Skill 已经有效。

## 一、为什么需要执行层专题案例

完整案例已经记录了需求从多源材料、边界确认、PRD 编写到页面原型和交互图的全过程。但如果直接用完整案例指导 Skill 迭代，容易把两类问题混在一起：

1. 原有 PM Skills 已经有明确对策的问题；
2. 原有 Skills 提出了原则，但尚未把原则执行成稳定交付物的问题。

上游体系已经要求需求定义、风险分级、状态矩阵、评审简版、原型追溯和一致性审查。排课案例更值得追问的是：

> 为什么具备正确而完整的规格后，AI 仍可能生成一份阅读困难、图文割裂、需要产品角色反复整理的交付物？

这份专题案例只聚焦从“规格完整”到“人类可读交付”的执行断层。

## 二、上游 PM Skills 已经解决的部分

### 1. 决策、分级与规格已经分层

| 已有能力 | 上游对策 | 对本案例的意义 |
|---|---|---|
| 模糊需求先形成产品定义 | 明确问题、目标、方向、一级范围、非目标和重大约束 | 不应直接拿混乱材料写完整 PRD |
| 风险决定交付等级 | 统一判断交付门禁和后续路由 | 跨系统和状态变化有正式治理路径 |
| PRD 不重新做方向决策 | 只展开已确认的产品决策 | 上游结论与客户端规格不应混写 |
| PRD 与研发 spec 分层 | PRD 写能力、用户结果和验收，技术实现进入 spec | 不在用户端 PRD 中堆积接口与算法细节 |

### 2. 规格完整度已经有明确要求

上游 PRD 能力已经要求：

- 先说明方案闭环、产品动线和页面影响；
- 区分页面、信息区、用户路径和状态；
- 有状态流转时输出页面状态与操作矩阵；
- 跨系统时输出系统能力需求；
- 核心功能覆盖触发、用户行为、系统结果、分支、异常恢复和保持不变；
- 建立目标、场景、功能、原型、规则和验收的追溯；
- 派生视图不能改变正式 PRD 口径。

因此，下列排课经验已经能在上游找到对应机制：

| 案例经验 | 已有机制 |
|---|---|
| 区分客户端、规则服务和业务服务的责任 | 需求定义边界、PRD 输入契约、PRD/spec 边界 |
| 将未知项交给有权决策的人 | 信息状态、负责人、最晚时间和阻塞影响 |
| 覆盖成功、失败、空态、已处理和资格拦截 | 页面状态矩阵、异常与恢复要求 |
| 区分进入校验、查询候选项和提交复检 | 方案闭环、系统能力需求、功能行为规格 |
| 避免 PRD、原型和验收口径不一致 | 稳定 ID、场景—原型关联、一致性审查 |
| 避免评审者直接阅读全部正式规格 | 评审简版和两层文档结构 |

它们仍然重要，但不是执行层新增能力的独有发现。

## 三、真正的问题：信息完整不等于协作可用

排课案例后期的主要返工发生在产品决策已经基本稳定之后。问题不再是缺少背景、范围或状态，而是如何把完整信息组织成人能使用的产物。

| 质量层 | 关注问题 | 上游覆盖情况 |
|---|---|---|
| 规格正确与完整 | 规则是否明确、状态是否覆盖、异常能否恢复、是否可验收 | 已有较完整规范 |
| 协作表达与消费 | 读者先看什么、图画什么、原型如何组织、正文与视觉如何互证 | 有原则，但缺少稳定执行链 |

一份 PRD 可以满足状态齐全、追溯完整和验收可执行，却仍然对人不友好：

- 主流程埋在多张状态表和功能明细之间；
- 同一状态在规则表、文案表、页面表和原型中重复出现；
- 评审简版只是机械删减完整版，而不是按决策任务重组；
- 原型只有链接，没有与对应需求就地组合；
- 流程图存在，但图型、顺序和布局不支持快速阅读；
- 规则变化后，正文更新，图和截图仍保留旧状态；
- 文档通过文字检查，却没有验证实际渲染后的阅读体验。

## 四、执行缺口一：评审简版缺少“阅读版编译”过程

上游已经规定评审简版应包含一句话方案、目标与非目标、页面结构、主链路、关键状态、核心规则、验收底线和待决策事项。

排课案例中，完整 PRD 虽然信息充分，仍需要重新组织一份会议讲解视图：

1. 一句话说明用户问题和方案；
2. 讲清从消息触达到操作成功的一条主线；
3. 用少量关键页面和出口建立体验结构；
4. 只保留影响评审判断的规则；
5. 集中展示取舍、风险和待决策项；
6. 将完整状态、验收和依赖留在正式 PRD 供查阅。

评审版不能只是删除若干章节，而应从正式事实源编译：

```text
正式事实源
→ 识别本次评审任务
→ 确定读者需要先形成的心智模型
→ 提取一条可复述主线
→ 选择少量页面 / 状态作为证据
→ 集中关键取舍与待决策项
→ 将详细规格链接回正式 PRD
```

执行层需要定义怎样派生、怎样同源、什么内容只能裁剪不能改写。

## 五、执行缺口二：原型索引之后缺少视觉资产生产链

上游已经要求原型 ID、精确链接、版本、状态、负责人和覆盖关系。但原型索引只解决“已有原型如何关联”，没有解决原型如何可靠地产生。

本案例最终形成多个页面状态，实际有效的生产过程是：

1. 从状态模型提取页面清单；
2. 为每个页面状态定义入口、信息、动作和出口；
3. 使用统一组件生成可编辑页面；
4. 渲染预览供产品快速核对；
5. 逐态检查文案、按钮和恢复路径；
6. 确认后再组织页面关系图；
7. 将总图和单页图装配到正文的正确位置。

执行层还需要回答：

- 哪些状态需要独立页面，哪些可以共用页面结构；
- 什么情况下只需要流程图，不需要页面原型；
- 页面资产如何稳定编号和组织；
- 页面逻辑未确认时是否应暂停批量制图；
- 图片应放在整体流程、页面需求还是附录。

需要把“状态矩阵 → 页面清单 → 可编辑资产 / 预览图 → 人工确认 → 文档装配”变成明确流水线。

## 六、执行缺口三：流程图缺少图型、布局和可读性验收

上游已经允许使用流程图帮助快速阅读，也明确页面动线、页面内交互和业务状态流可以分别表达。但它没有规定如何完成制图决策与成图验收。

排课交互图的多次返工主要来自：

- 图型与评审任务不匹配；
- 页面状态上下游顺序错误；
- 主流程和异常分支互相穿插；
- 连线交叉或反向；
- 页面内部状态被放到错误层级；
- 图中新增了正文没有确认的规则。

最终适合该案例的是按时间推进的页面主线，并在对应判断点展开异常分支，而不是机械使用泳道图或时序图。

制图前至少应判断：

| 判断 | 要解决的问题 |
|---|---|
| 阅读任务 | 读者要理解用户路径、系统责任、状态迁移还是时间顺序？ |
| 图型选择 | 使用线性流程、分支图、状态图、泳道图，还是不画图？ |
| 节点语义 | 节点表示页面、系统动作、状态还是决策？ |
| 主次结构 | 主流程和异常如何分区？ |
| 布局规则 | 是否存在反向连线、跨区交叉、孤立节点和不可读标签？ |
| 语义约束 | 图是否只表达正式事实源已有内容？ |

生成后还应真实渲染并检查，而不是只确认图形代码能够运行。

## 七、执行缺口四：一致性审查缺少跨产物语义见证

上游已经要求检查术语、状态、动作、结果、数值和追溯关系。但实际缺陷常常不是名称不同，而是结构矛盾：

- 正文要求进入时先校验，交互图的重试却直接回到候选项查询；
- 正文删除了一个状态，旧原型仍保留该页面；
- 页面表已经包含错误原因，另一张错误映射表仍重复维护；
- 已处理页存在，但流程中没有路径可以到达；
- 原型保留了已经删除的次要跳转；
- 正式 PRD 已使用新规则，评审版仍保留旧口径。

需要为关键语义建立跨产物见证：

| 语义事实 | 正文证据 | 流程证据 | 页面证据 | 验收证据 |
|---|---|---|---|---|
| 提交前必须再次校验 | 功能行为 | 提交前判断 | 提交中 / 失败状态 | 并发变化用例 |
| 成功后旧入口不可再次办理 | 业务规则 | 已处理出口 | 已处理页 | 再次进入用例 |
| 特定资格拦截仅提供人工兜底 | 异常规则 | 资格分支 | 拦截页操作 | 不出现额外跳转 |

每次变化后，要检查同一业务语义在正文、图、页面和验收中是否都有且互不冲突。

## 八、执行缺口五：结构规范之后缺少真实阅读体验验收

上游模板已经规定推荐阅读顺序、章节先写结论、表格不能代替解释、同一事实不要重复扩写。但这些规则不能自动保证最终文档平台上的阅读体验。

实际还会出现：

- 图片与解释相隔太远；
- 连续堆放大量图片，却没有全局索引；
- 表格过宽，关键列难以同时看到；
- 图片缩放后文字不可辨认；
- 同一页面的规则、文案和原型分散在多个章节；
- 读者先看到大量 ID 和矩阵，主线反而被推后；
- 源文件结构正确，写入目标平台后发生布局变化或断链。

执行层需要把文档装配和阅读检查纳入完成标准：

1. 按读者任务安排结论、主线、页面、细节和附录；
2. 在建立全局理解的位置放置总图；
3. 将单页原型与对应需求就地组合；
4. 控制表格宽度、列数和重复信息；
5. 渲染目标平台的实际阅读视图；
6. 检查首屏、标题层级、图片清晰度、链接和导航；
7. 由非作者在限定时间内完成一次阅读任务。

“文件已生成”或“章节齐全”不等于阅读验收通过。

## 九、从正式 PRD 到协作交付物的执行链

在上游 PM Skills 已经产出结构化、可验收的正式规格后，复杂协作需求还需要：

```text
正式 PRD / 结构化事实源
→ 判断协作任务和目标读者
→ 制定视觉计划：哪些关系值得画、使用什么图
→ 从状态与页面关系生成视觉资产清单
→ 生成流程图、页面原型和预览
→ 产品逻辑确认
→ 组装评审阅读版与执行阅读版
→ 语义无损检查
→ 实际渲染与阅读体验检查
→ 回填问题并重新生成受影响产物
```

### 门槛一：产品逻辑确认

范围、主流程、关键状态、调用时点、页面迁移和异常恢复稳定后，才进入批量视觉生产。未通过时只输出视觉计划和页面清单。

### 门槛二：协作交付确认

图形表达、页面文案、图片清晰度、文档装配、跨产物语义和阅读任务均通过后，才算完成交付。

## 十、上游能力与执行层能力的边界

| 能力 | 上游 PM Skills | 协作交付执行层 |
|---|---|---|
| 产品方向和一级范围 | 决策并固化 | 不重新讨论 |
| 风险等级与交付门禁 | 评级和路由 | 读取门禁，决定交付深度 |
| 页面、状态、规则和异常 | 定义正式规格 | 转换为视觉计划和页面资产 |
| 验收标准 | 定义业务与用户结果 | 检查视觉产物是否见证关键语义 |
| 评审简版 | 规定内容与边界 | 从事实源编译、排版并验证阅读视图 |
| 原型关联 | 定义 ID、状态和覆盖关系 | 生成、渲染、核对和装配原型 |
| 一致性原则 | 规定不得冲突或新增规则 | 执行跨文本、图、页面和截图的语义检查 |
| 文档载体 | 指明目标平台和负责人 | 适配目标载体并完成视觉 QA |

执行层不应成为第二个 PRD Skill。发现产品逻辑冲突时，应返回上游修正规格，不在图或阅读版中自行补规则。

## 十一、当前协作交付分支如何回应这些缺口

对照当前新增协作交付能力，可以看到它没有重新承担产品定义和 PRD 规格，而是尝试补齐以下执行动作：

| 执行缺口 | 当前回应 | 仍需验证 |
|---|---|---|
| 正式 PRD 难以连续阅读 | 以正式 PRD 为事实源，按传统产品文档语义重组 | 是否适用于更多复杂需求 |
| 阅读版容易成为机械摘要 | 先归并同一事实，再按读者思路裁剪和重新编排 | 是否能稳定保留全部高风险事实 |
| 不知道该画什么图 | 先定义阅读问题，再选择动线、状态图、泳道、信息结构或原型 | 复杂拓扑下的图型与布局质量 |
| 状态矩阵无法直接变成页面资产 | 提供通用线框和多状态页面生成能力 | 不同端和真实组件体系的适配能力 |
| 视觉资产与正文手工拼接 | 使用占位映射装配图片，并要求图与对应功能就近呈现 | 不同文档平台的发布和渲染一致性 |
| 文档有模板残留、断图或结构过密 | 自动检查内部术语、模板残留、图片断链、宽表和复杂图 | 自动检查不能替代业务语义判断 |
| 派生文档可能改变规则 | 正向检查事实覆盖，反向抽查高影响结论是否可回到主源 | 跨文本、图和页面的语义见证自动化 |
| 文件生成即被视为完成 | 同时设置同源、人类阅读和视觉编排检查 | 非作者阅读测试和真实平台证据 |

这个映射说明新分支的设计方向与案例问题相符，但仍不能把“已经写入 Skill”当成“已经验证有效”。尤其还需要证明：

- 非作者能否在限定时间内复述需求主线；
- 不同类型需求能否复用同一视觉计划和资产流程；
- 规则变化后能否完整更新正文、图、原型和评审版；
- 目标平台实际渲染后是否仍然清晰；
- 自动检查之外，语义和阅读体验能否稳定通过人工门槛。

因此，这个案例是新增能力的问题证据和验收基线，不是成功证明。

## 十二、如何验证新增协作交付能力

本案例是设计依据，不是通过证明。后续应观察：

| 观察项 | 历史表现 | 期望变化 |
|---|---|---|
| 第一次阅读能否复述主线 | 依赖作者口头补充 | 阅读版自身建立心智模型 |
| 图型与布局返工 | 多版试错 | 制图前完成图型与拓扑判断 |
| 页面状态覆盖 | 随反馈逐张补图 | 从上游状态模型生成资产清单 |
| 正文与原型一致性 | 依赖人工发现 | 关键语义具有跨产物见证 |
| 规则变化同步 | 改正文后再人工寻找旧图 | 自动列出并更新受影响产物 |
| 完成交付的判断 | 文件已生成或已写入平台 | 语义检查与阅读检查均通过 |

## 十三、可抽取的执行型训练问题

1. 给定一份完整但表格密集的 PRD，生成 10 分钟评审阅读版，不得新增规则；
2. 给定页面状态矩阵，判断哪些状态需要独立原型，哪些可共用结构；
3. 给定主流程与异常分支，选择合适图型并说明选择依据；
4. 给定正文、流程图与页面原型，发现重试绕过前置校验等结构矛盾；
5. 给定一项规则变化，列出正文、图、页面、文案和验收的完整影响面；
6. 给定渲染后的文档，判断图片、表格和章节顺序是否支持非作者快速阅读；
7. 给定正式 PRD 与评审版，判断评审版是否只做裁剪重组，还是新增了不同口径。

## 十四、案例结论

排课案例没有证明原有 PM Skills 缺少产品方法。上游已经对需求定义、风险分级、PRD 完整度、状态异常、评审简版、原型追溯和一致性提出了较成熟的要求。

它真正证明的是：
