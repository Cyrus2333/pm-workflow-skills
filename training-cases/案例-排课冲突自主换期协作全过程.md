# 排课冲突用户自主换期：从陌生业务到可评审 PRD 的真实协作案例

> 案例类型：复杂 C 端需求 / 多系统协作 / 多状态交互  
> 案例用途：本 skill 的参考案例——展示一份陌生业务输入如何一步步变成可评审 PRD，以及人工判断发生在哪些环节  
> 案例来源：产品角色与 WorkBuddy、Codex 的真实协作过程  
> 基线说明：本案例发生时尚未使用当前 `pm-workflow-skills`，因此它用于展示问题如何被解决、人工判断发生在哪里，不用于证明现有 Skill 已经有效。

## 一、为什么把这个案例收入训练集

这是一个很适合训练产品工作流的案例，因为它不是“拿到明确需求后写一篇 PRD”，而是完整经历了：

```text
进入陌生业务
→ 阅读并判断多份互相冲突的资料
→ 找到自己的责任边界
→ 把业务结论翻译成用户流程
→ 补齐状态、异常和跨系统调用
→ 生成 PRD、流程图和页面原型
→ 根据真实界面、评审反馈和上游变更持续修正
→ 收口为可评审、可协作的正式交付物
```

它暴露出的主要问题不是 AI 不会写文字，而是 AI 如果没有稳定工作流，会在五个地方持续返工：

1. 没有先建立资料的可信顺序，把旧结论和新结论混在一起；
2. 没有划清责任边界，把上游算法、CRM 能力和 C 端设计写成一团；
3. 没有先建立状态与调用模型，过早进入 PRD 和原型制作；
4. PRD、流程图、原型和文案各自生成，规则改变后难以同步；
5. 文档虽然信息齐全，但不一定方便评审者理解和做决策。

因此，本案例训练的不是某个固定业务答案，而是复杂需求从“信息混乱”走向“可决策、可交付”的方法。

## 二、案例背景

### 1. 业务问题

用户可能同时购买多门正式课程，不同课程由不同业务线独立排课，因此会出现同一时间需要参加多场直播的情况。系统侧计划识别冲突较严重的用户，并通过客户端提醒，引导符合条件的用户自主调整课程期数。

本案例承担的是其中的 C 端闭环：

```text
系统识别需提醒用户
→ APP 站内信与 Push 触达
→ 用户进入 H5
→ 系统判断是否允许自主调整
→ 用户查看并选择候选期
→ 确认提交
→ 调整成功，或进入明确的失败 / 拦截状态
```

### 2. 项目为什么难

需求虽然表面上像“增加一个换期页面”，实际上同时依赖：

- 排课侧提供冲突识别与候选期判断；
- CRM 提供资格校验和换期执行；
- C 端负责消息触达、H5 交互、状态展示和错误转译；
- 数据侧需要识别这类换期并统计效果；
- 业务侧需要决定可换范围、重复操作、服务归属等经营规则。

最初输入还同时包含群聊、会议人工笔记、AI 纪要、总体产品方案、CRM 规则、历史需求和真实页面截图。这些材料的时间、目的与可信度不同，部分表述互相矛盾。

### 3. 产品负责人的初始状态

案例开始时，负责该模块的产品角色尚未建立完整的业务认知，主要存在以下疑问：

- 整个项目真正要解决什么；
- 项目分工中归属本模块的内容具体对应哪些产品工作；
- 哪些规则需要本模块设计，哪些只需依赖上游结果；
- 应该直接写 PRD，还是先推动业务与研发确认；
- 页面之外还要考虑哪些状态、接口和异常。

因此，第一阶段的正确目标不是马上生成文档，而是先帮助负责人形成对问题、分工和工作路径的稳定理解。

## 三、输入材料与事实判断

### 1. 材料类型

| 材料 | 能回答的问题 | 使用风险 |
|---|---|---|
| 项目群会后人工结论 | 当前范围、负责人、会议最终收口 | 信息零散，需要结合上下文 |
| 总体产品方案 | 背景、完整链路、上游规则设计 | 可能包含早期方案和非 C 端范围 |
| CRM 换期规则与 PRD | 现有能力、校验条件、执行约束 | 面向内部操作，不能直接复制到用户端 |
| 会议人工笔记 | 讨论中的明确口径 | 可能记录不全 |
| AI 纪要、图文纪要、思维导图 | 快速定位讨论主题 | 可能概括错误，不能覆盖人工结论 |
| 真实 APP 截图 | 现有消息组件、视觉形态和交互习惯 | 只证明当前界面，不能替代业务规则 |
| 历史同类需求 | 旧系统逻辑和潜在冲突 | 是否沿用需要业务重新确认 |

### 2. 关键做法：先建立事实秩序

案例中最早出现的一次高价值纠偏，是发现“本期不做小程序”的会后结论已经收窄了早期方案。如果只按照总体方案摘要生成 PRD，就会把被排除的范围重新带回来。

后来又出现过类似问题：

- 不同材料同时出现不同提醒阈值；
- AI 纪要对检测节点的描述与人工会后总结不同；
- CRM 材料描述的是内部人员办理逻辑，不等于用户端全部适用；
- 历史需求存在一套旧规则，但不能默认与本期完全衔接。

这部分形成了本案例第一个训练原则：

> 多源材料的第一步不是总结，而是判断来源、时间、责任主体和冲突；无法确认时，应把问题交还给有权决策的人，而不是由 AI 静默补全。

## 四、第一阶段：从业务陌生到明确产品职责

### 1. 先把需求翻译成人话

早期梳理将整个项目压缩为一条可理解的用户链路，并区分各方责任：

| 事项 | 主要责任方 | C 端产品需要做什么 |
|---|---|---|
| 冲突如何计算、谁需要提醒 | 排课规则侧 | 理解接口结果和展示所需字段，不重新定义算法 |
| 哪些用户允许自主换期 | 业务与 CRM | 梳理用户场景，推动规则确认，将结果转成页面状态 |
| 用户在哪里收到提醒 | C 端 | 设计站内信、Push、跳转与去重逻辑 |
| 用户如何选期和提交 | C 端 + CRM | 设计主流程、调用时机、提交确认和失败恢复 |
| 换期后服务与业绩归属 | 业务负责人 | 暴露影响并推动决策，不由单个产品角色自行决定 |
| 页面、状态和用户文案 | C 端 | 负责完整设计并接受评审 |
| 接口内部如何实现 | 研发 | 定义业务能力、返回状态和用户侧要求，不写实现细节 |

这一步解决了产品角色最核心的职责问题：既不能被动等待所有结论，也不能越过责任边界替业务拍板。正确职责是：

> 找出哪些事情尚未形成可执行规则，准备场景、选项、影响和建议，推动负责人决策；结论形成后，再把它翻译成流程、页面、状态、接口需求、异常和验收。

### 2. 初步工作流

```text
还原现状
→ 区分事实、矛盾与未知项
→ 建立责任和范围边界
→ 为阻塞问题准备方案与影响
→ 先与产品负责人预对齐
→ 推动业务 / 研发确认
→ 形成决策记录
→ 再进入正式需求设计
```

这也是整个案例中 Codex 最重要的贡献：它帮助产品角色先看清本模块应该承担什么，而不是直接提供一份貌似完整的答案。

## 五、第二阶段：从整体方案收口到 C 端 PRD

### 1. 第一次明显偏差：范围过宽

早期初稿容易复述总体方案，把冲突阈值、灰度算法、多个触达端和 CRM 内部流程都写入 C 端 PRD。负责人进行了明确纠偏：

- 本期落地为 H5；
- 小程序不在本期范围；
- 冲突阈值是上游输入，不是 C 端要重新决策的内容；
- PRD 应像 CRM 文档一样，只把本侧真正要完成的事情写清楚；
- 上游材料通过依赖关系引用，不在正文中重复展开。

调整后，C 端范围稳定为：

- APP 站内信和 Push 的展示、文案与跳转；
- H5 的进入、选择、确认、提交和结果反馈；
- CRM 返回状态到用户页面和文案的映射；
- C 端埋点和必要的效果观察。

### 2. 第二次偏差：模板完整，但逻辑分散

初版 PRD 虽然覆盖了背景、流程、功能和异常，却出现了典型的“信息齐全但不好读”：

- 同一个错误状态在规则表、错误码表、页面说明和附录中重复出现；
- 5.1、5.2 等章节内部条目过碎；
- 多张图表达相似信息，却没有形成统一主线；
- 时序图对非技术评审者理解成本过高；
- 页面和错误文案分开维护，导致原型与正文不一致。

用户提出了一个影响后续 Skill 设计的重要判断：

> PRD 本身也是一个产品。它不仅要信息完整，还要让评审者沿着自然路径理解；一件事应该在最合适的位置集中讲完。

随后文档结构改为：

1. 先讲一句话方案、范围和依赖；
2. 用一张主流程 / 分支图讲清用户路径；
3. 按消息、落地页、确认、结果和拦截等页面展开；
4. 每个页面就地说明状态、动作、文案和异常；
5. 详细上游规则只保留引用和 C 端消费结果；
6. 待确认问题与正文事实分开。

## 六、第三阶段：真正困难的是状态和调用时机

### 1. 为什么页面不能直接开始画

案例中最大的结构性返工来自“什么时候校验用户资格”。一度因为 CRM 文档未明确独立预检接口，只保留了提交时校验；后续继续推演“已办理过”“后台已代操作”“用户停留页面时状态变化”等场景后，又恢复并稳定为三个调用阶段：

```text
阶段一：进入 H5 时校验
→ 判断是否已经处理、是否具备自主调整资格

阶段二：查询候选期
→ 返回可选期数及候选期相关结果

阶段三：提交时复检并执行
→ 防止用户停留期间发生退款、转课、后台换期或重复提交
```

如果不先把这三个时点想清楚，就无法稳定回答：

- 已经办理过的用户再次进入看什么；
- 第一次打开但没有操作，能否再次进入；
- 查询失败和资格拦截是不是同一种页面；
- 提交失败后“重新尝试”应该回到哪一步；
- 后台状态变化后，前端旧页面如何失效；
- 一条提醒到底代表一次成功机会，还是一个长期换期入口。

### 2. 一次成功操作的语义

最终设计区分了四种情况：

| 情况 | 是否允许继续 |
|---|---|
| 只打开页面，没有提交 | 可以再次进入 |
| 提交失败，没有完成换期 | 可以重新尝试 |
| 已经成功换期 | 旧提醒不再允许再次换期 |
| 后续新订单或新事件产生新的冲突 | 由新事件形成新的提醒和资格 |

这个区分比笼统写“链接有效期”更准确，也避免用户把冲突处理入口当成无限延期工具。

### 3. 状态模型

最终需要覆盖的不是一个页面，而是一组页面状态：

- 消息触达：Push、消息列表、学习小助手卡片；
- 进入过程：校验 / 加载中、加载失败；
- 落地页：初始态、推荐期、其他可选期；
- 无法继续：已办理、无候选期、退款中、无权限或转课、存在在途申请；
- 提交过程：确认弹层、提交中；
- 结果：调整成功、提交失败；
- 人工兜底：联系班主任。

这里的重要训练信号是：

> 页面清单应由状态和用户任务推导，而不是从 PRD 章节数或固定模板推导。

## 七、第四阶段：真实界面和目标用户带来的纠偏

### 1. AI 初版为什么不够用

AI 初版曾把学习小助手消息画成通用对话气泡，标题使用普通的“上课时间提醒”，并给出较长、过度口语化或包含内部意味的文案。这些产物逻辑上能看懂，却不符合真实产品。

负责人补充真实 APP 截图后，要求同时满足：

- 使用既有消息卡片形态，而不是创造新的对话样式；
- 标题要让用户知道这是可操作的课程调整入口；
- 面向老年用户，信息必须完整、句子清晰、操作明确；
- 不能为了“易懂”而过度大白话或显得不专业；
- 不向用户暴露 CRM、审批状态码等内部术语；
- 异常页不要增加“查看进度”等新跳转，统一采用轻量的班主任兜底。

### 2. 异常交互的收口

最初的异常设计容易为每种后台状态增加不同操作。实际评估后，退款审核、无听课权限 / 转课、在途申请等状态虽然原因不同，但用户侧的主任务相同：当前无法自主调整，需要联系班主任。

因此最终采用：

```text
图标
→ 用户可理解的具体原因
→ 单一主去向：联系班主任
```

这里不是把不同业务状态合并成同一个错误，而是保留不同原因，同时统一用户侧结构和恢复动作，减少认知与开发成本。

## 八、第五阶段：从页面原型到完整协作交付

### 1. 原型如何产生

原型并不是直接拿 PRD 全文生成，而是先拆成“页面 × 状态”，再批量生成低保真页面。最终形成 17 个页面状态，覆盖：

- 消息触达；
- 落地页的初始、推荐和可选状态；
- 加载、失败、空态和已完成；
- 确认提交；
- 成功与失败；
- 多类资格拦截。

原型采用统一组件和灰阶样式批量生成 SVG，并渲染为 PNG 预览。这样修改文案、按钮或页面状态时可以重复生成，而不需要逐张手工重画。

### 2. 交互图为什么反复返工

交互画布先后尝试过分支、泳道和时间流等表达。多轮修改主要不是视觉不够精致，而是：

- 页面先后顺序不正确；
- 推荐 / 可选状态被放到了错误的流程位置；
- 异常分支连线交叉，读者无法顺着用户路径阅读；
- “重新尝试”绕过了本应再次执行的前置校验；
- 图中出现正文没有定义的新逻辑。

最终采用按时间推进的主线，并在对应判断节点展开异常分支。交互图只表达已经确认的页面关系，不再创造规则。

### 3. 三种最终交付视图

最终成果不是一份单一文档，而是同一需求面向不同协作任务的三种视图：

| 视图 | 主要读者 | 作用 |
|---|---|---|
| 完整 PRD | 产品、设计、研发、测试及后续 AI | 保留规则、页面、状态、异常、依赖与验收 |
| 评审讲解稿 | 产品负责人、业务与跨团队评审者 | 用较短时间讲清主线、关键取舍和待决策问题 |
| 页面原型与交互总图 | 设计、研发与测试 | 让页面关系和状态覆盖不依赖文字想象 |

三者共享同一组规则和状态，但信息密度不同。完整 PRD 负责“不遗漏”，评审稿负责“不让人迷路”，原型与交互图负责“不靠想象理解”。

## 九、WorkBuddy、Codex 与产品角色的实际分工

### WorkBuddy 的主要贡献

- 读取大量资料并形成初步全景；
- 生成 PRD 框架和多轮正文；
- 批量生成 SVG / PNG 页面原型；
- 写入并维护飞书文档；
- 生成和修改交互画布；
- 对规则变化进行文档同步和交叉验证。

### Codex 的主要贡献

- 在最初阶段识别项目的真实 C 端闭环；
- 帮助产品角色理解责任边界和项目工作流；
- 发现资料中的关键矛盾与风险；
- 解释复杂遗留问题和多方决策关系；
- 后期辅助资料核对、历史需求识别和文档精修。

### 产品角色承担的关键判断

- 决定本期边界，删除小程序和非本侧内容；
- 判断哪些业务结论必须由负责人确认；
- 选择 H5 方案并控制交互开发量；
- 识别文档结构是否适合真实评审；
- 推演一次成功、后台代操作、并发与失败恢复；
- 用真实界面和目标用户纠正原型与文案；
- 持续核对 PRD、流程、原型和交互图是否一致；
- 决定哪些内容进入正式交付，哪些探索稿应删除。

这说明当时的 AI 已能承担大量执行工作，但高价值产品判断仍主要来自人。Skill 的优化方向不是隐藏这些判断，而是更早地把判断点暴露出来，让产品在少量关键位置做决策。

## 十、案例中的典型失败方式

### 失败一：先写完整文档，再发现范围错了

表现：把总体方案和本侧需求混写，小程序、算法阈值等重新进入范围。  
根因：没有在写作前建立来源、责任与非目标。  
训练方向：强制完成范围基线和决策权检查后再进入 PRD。

### 失败二：按模板填满章节，却没有形成用户主线

表现：信息重复、条目零散，评审者需要在多张表和多幅图之间拼接逻辑。  
根因：从文档结构出发，而不是从用户任务和状态模型出发。  
训练方向：先建立行为模型，再派生正文与图。

### 失败三：产品逻辑未稳定就批量生成原型

表现：校验时点改变后，流程、页面和十余张图片全部返工。  
根因：缺少“产品逻辑确认门”。  
训练方向：范围、状态、调用时点和页面迁移稳定后才进入批量制图。

### 失败四：每份产物各自正确，但放在一起互相矛盾

表现：已完成页没有入口、重试绕过校验、同一状态使用不同名称。  
根因：PRD、流程图、原型和画布没有共同事实源。  
训练方向：使用稳定状态 / 页面标识，并做跨产物一致性检查。

### 失败五：把“用户友好”理解成更口语或更多按钮

表现：文案过度大白话，异常页增加查看进度等重跳转。  
根因：没有结合目标用户、真实产品形态和任务成本。  
训练方向：用户友好应同时检查信息完整、语言恰当、下一步明确和操作最小化。

## 十一、这个案例应教会 Skill 什么

### 1. 写 PRD 前必须完成的工作

- 盘点材料来源、版本和可信度；
- 区分事实、推断、方案和待决策项；
- 明确本侧负责、协作依赖和非目标；
- 判断问题、目标、方案方向和重大取舍是否已经稳定；
- 对阻塞问题给出场景、选项、影响、建议与决策人。

### 2. 复杂交互需求应先建立行为模型

至少包括：

- 用户触发与主任务；
- 系统调用时点；
- 关键状态和判断条件；
- 页面及页面迁移；
- 异常恢复和人工兜底；
- 规则变化影响的产物范围。

### 3. PRD 应从同一事实源派生不同阅读视图

- 完整执行视图保留规则和验收；
- 协作评审视图突出主线、取舍和待决议；
- 页面状态视图驱动原型；
- 交互总图表达页面关系；
- 不允许不同视图各自重新创造规则。

### 4. 可视化交付需要两道确认门

1. 产品逻辑确认：范围、调用时点、状态和页面迁移稳定；
2. 原型逻辑确认：页面信息、动作、文案和恢复路径稳定。

只有通过前一道门，才继续批量生成下一层产物。

### 5. 变更不能只修改提出问题的位置

任何上游规则或产品决策变化，都应检查：

```text
PRD 正文
→ 状态矩阵
→ 流程与交互图
→ 页面原型
→ 用户文案
→ 验收场景
→ 评审简版
```

## 十二、如何把本案例用于后续 Skill 迭代

### 用法一：作为方法训练案例

让 Skill 维护者阅读完整案例，理解哪些高频返工应该被固化成工作步骤、检查表或中间产物。重点学习“为什么发生修改”，而不是复制最终文案。

### 用法二：作为回归基线

后续可使用脱敏后的初始材料重新运行 Skill，观察它是否能：

1. 在第一版就排除已明确不做的小程序；
2. 区分 C 端、上游排课规则和 CRM 的责任；
3. 不把 AI 纪要或旧文档直接当作最新事实；
4. 在写 PRD 前识别状态、调用时点和待决策项；
5. 覆盖打开、失败重试、成功处理、后台状态变化等语义；
6. 让正文、流程、原型和文案保持一致；
7. 在规则改变后找出全部受影响位置；
8. 同时生成适合执行和适合评审的阅读视图。

### 用法三：作为反例来源

可从案例中继续整理成更小的训练片段：

- 旧方案把小程序带回范围，如何纠正；
- 错误码表与页面状态分开，如何合并；
- 进入校验被删除后，如何通过场景推演恢复；
- 泳道图不适合当前阅读任务，如何选择时间流分支图；
- 异常页操作过重，如何统一为轻量人工兜底。

这些片段适合用来测试 Skill 是否能够发现问题，而不是只模仿最终答案。

## 十三、不能从本案例直接推出什么

- 不能认为所有 PRD 都需要 17 张原型；
- 不能认为所有 C 端流程都需要三次接口调用；
- 不能把本案例的换期规则和文案写成通用模板；
- 不能用聊天轮数或文档版本数代表有效返工次数；
- 不能把最终质量全部归因于某一个 AI 工具；
- 不能在尚未重新运行当前 Skill 前，声称仓库已经解决了这些问题；
- 不能仅凭 PRD 评审结果证明方案已经通过研发、测试或线上验证。

## 十四、训练集中的案例结论

这个案例最终沉淀的不是“排课换期应该怎么做”，而是以下可迁移结论：

> 面对多来源、多角色、多系统和多页面需求，先建立事实秩序与责任边界，再建立用户行为和状态模型；从同一事实源派生 PRD、评审视图和视觉交付物，并在每次变化后做跨产物一致性检查。

如果 Skill 能把这条路径稳定执行出来，它替代的将不只是“写初稿”，而是大量资料整理、状态展开、原型规划、变更同步和交付检查工作；产品角色则能够把精力集中在真正需要判断的范围、取舍、风险和验收上。
