# pm-collaboration-deliver

把稳定的正式 PRD 编译成一份简洁、完整、视觉清楚的传统产品文档。正式 PRD 是高密度、可追溯、可供 AI 和执行团队继续消费的产品事实源；本 skill 是面向人的承接层，负责读者主线、信息分层、页面理解、交互表达、交付平台和质量门槛。

## 优先读取

参考文档共五份，每份只负责一个主题：

1. 始终完整读取正式 PRD 和[转译与文档结构](./references/转译与文档结构.md)（唯一主交付面、传统语义链、信息分层、转译方法与模板）。
2. 需要任何视觉、原型，或输入中包含截图、设计稿、现有页面时，读取[视觉与原型](./references/视觉与原型.md)（表达路由、流程图、页面交互总览渲染、原型生产与截图承接、资产稳定定位与版本变更信号、工具地图）。
3. 进入交互版时读取[交互型 PRD 与状态模型](./references/交互型PRD与状态模型.md)（载体—页面—状态—迁移四层模型，页面交互总览的权威定义）。
4. 成稿后、以及存在多个相互依赖资产或正式门禁时，读取[质量与门槛](./references/质量与门槛.md)（执行层定位、交付物契约、执行包、两道门槛、全部检查清单与通过标准）。
5. 只有用户要求创建、更新或验收飞书文档时才读取[飞书发布与渲染](./references/飞书发布与渲染.md)。

想看完整案例再动手时，按需读仓库级训练案例[案例：排课冲突自主换期协作全过程](../../training-cases/案例-排课冲突自主换期协作全过程.md)（输入如何一步步变成可评审 PRD）或[案例：从规格完整到人类可读交付](../../training-cases/案例-从规格完整到人类可读交付.md)（为什么需要这个执行层）。

## 工作边界

负责：

- 把已确认的正式 PRD 编译为传统 PRD 主文档，并按交付面发布（本地 / 飞书）；
- 重组读者主线与信息分层，生产并装配视觉资产（流程图、页面交互总览、原型）；
- 承接截图与设计稿输入，登记证据角色并按充分度决定复用、标注或低保真；
- 交付前的主源一致性、阅读与渲染验收。

不负责：

- 重新决定产品方向、范围、规则或验收——阻断缺口返回 `pm-prd-write`；
- 编写研发 spec——接口字段、队列、存储、算法保持研发下钻；
- 替代最终设计稿，或发布到用户未指定的平台。

## 输入契约

开始前至少取得：

- 正式 PRD（`pm-requirement-define` / `pm-requirement-grade` 结论齐备时质量更稳，但只有正式 PRD 是硬前提）；
- 存在界面变化时：现状截图、已确认设计稿或现有页面三者之一，或明确登记"无视觉上下文"；
- 用户指定的交付面与格式（未指定时默认本地 Markdown 传统 PRD）。

承接上游遵守三条取舍原则（产物级映射见[转译与文档结构](./references/转译与文档结构.md) §4）：

1. **选集不全集：**上游矩阵、AC、稳定 ID 是全量事实源；正文只取第一次评审所需子集，其余保留来源下钻可达，不回删上游；
2. **身份保持：**上游已标"待确认 / 假设"的内容按原身份承接，不洗白成事实；上游内部冲突不静默选边，进入"评审关注"或返回上游；
3. **重述不照抄：**上游冗杂段落按用户任务重述；页面与原型按"用户任务 × 状态"重构，不按上游章节顺序铺排。

输入不是标准 `pm-prd-write` 格式时（外部 PRD、口头需求）：先整理输入摘要与阻断 / 非阻断缺口清单再继续，不强行套用映射。

收到输入后先核对、再开工：

- 正式 PRD 主流程是否已无大面积"待定"；不稳定则列阻断缺口返回上游，不边猜边写；
- 有界面变化却无截图、设计稿或现有页面时，先向用户索取，或明确登记"无视觉上下文"；
- 交付面与格式未指定时，按默认（本地 Markdown 传统 PRD）执行并告知用户，不默默选择。

## 先锁定交付物

默认只交付一份传统 PRD 主文档。除非用户明确要求，不把协作简报、评审讲稿、执行包或研发交接表混进主文档，也不并行生成第二种主阅读稿。

先锁定主文档的交付面和文件格式。用户或项目已有约定时遵循约定；未指定的本地交付默认使用 Markdown，以便保留链接、图源和自动检查。只有用户明确要求、现有团队模板要求或目标平台确实需要时才生成 DOCX/PDF；此时调用对应文档技能并完成最终渲染检查，不能用未渲染的办公文件替代主文档验收。

阅读版、视觉版、交互版是同一主文档的内容深度，不是三种文档模板：

| 路径 | 适用情况 | 在传统 PRD 中增加什么 |
|---|---|---|
| 阅读版 | 单点变化、规则简单、无复杂迁移 | 聚合正文与必要小表 |
| 视觉版 | 顺序、交接、条件、状态或空间关系用图更清楚 | 回答独立问题的流程、关系图或局部原型 |
| 交互版 | 多页面、多状态、异步结果、返回/取消/重进或高风险恢复 | 完整交互模型证据 + 产品主流程 + 页面交互总览 + 局部交互故事板 |

不要按页面数、节点数或固定套餐选路径。复杂度来自读者必须理解的关系和错误代价。

选定路径后，按下表总装本路径的套件（每行包含上一行的全部内容，不重复列出）：

| 路径 | 加读 | 加用模板（assets/） | 加跑脚本（scripts/） | 门槛 |
|---|---|---|---|---|
| 阅读版 | 转译与文档结构 | traditional-product-document | check_reading_view | 基础 |
| 视觉版 | 视觉与原型 | flow-diagram、mobile-screen-storyboard | render_flow_diagram、build_screen_html、capture_html_png、check_flow_diagram | 增强 |
| 交互版 | 交互型PRD与状态模型 | page-interaction-overview | render_overview_board、check_page_interaction_overview | 增强；严格发布时启用 audit/ 可选审计件 |
| 飞书交付（可叠加于任一路径） | 飞书发布与渲染 | feishu-delivery-audit | export_flow_mermaid | 发布验收：回读正文并查看画板 |

本表只做路径级总装；各脚本的完整用法与渲染链路见《视觉与原型》工具地图，各门槛的检查清单见《质量与门槛》。

无论选择哪条路径，都不以“保留上游章节”为完成标准。必须把正式 PRD 中分散在一页结论、FR、RULE、状态矩阵和 AC 的同一用户任务重新聚合；若成稿仍要求读者理解上游 ID、参数、路由或系统实现才能走通，说明转译尚未完成。

## 不可破坏的契约

- 只编译已确认事实；不得新增入口、权限、页面行为、业务状态、结果或恢复规则。阻断缺口返回上游，不用假设掩盖。
- 传统 PRD 是唯一主阅读面，遵循“需求背景 → 需求目标 → 需求范围 → 产品方案 → 需求详情 → 验收标准”的传统语义链；内部模型、来源映射、检查日志和生成过程不得污染正文。
- 每个视觉只呈现产品经理已决定的方案：真实文案、具体示例数据、已决定的状态；未决定的问题回到上游或写进正文缺口，不画“待定/占位”式注释。
- 截图只能证明可观察的现状或视觉参考，不能单独授权隐藏状态、动作结果、权限和恢复；产品语义与视觉上下文必须分别判断。
- 必须查看最终交付平台中的正文和视觉；文件存在、脚本通过或上传成功都不等于可交付。

## 主工作流

```text
正式 PRD
→ 事实稳定性与边界检查
→ 传统 PRD 读者主线和模块归属
→ 视觉问题与表达路由
→ 按用户任务生产正文和局部资产
→ 压缩重复并下沉内部术语
→ 同源、交互和最终阅读检查
→ 按需发布飞书并回看
```

### 1. 确认事实稳定

归并背景、决策、范围、FR、规则、状态、AC 和数据中的同一事实。再登记正式设计、现状截图和视觉参考的证据角色。会改变入口、权限、用户可见信息、主操作、状态、结果、恢复、时间或数据口径的阻断缺口，停止受影响模块并返回上游；非阻断缺口必须写清缺什么、影响什么、由谁在何时补齐。

### 2. 建立读者主线

使用 `assets/traditional-product-document-template.md` 规划主文档。章节名可以贴合业务，但必须保留传统语义；背景只写客观事实，问题写事实中的断点，目标写可验证的用户或业务状态而非过程描述。展开正文前先完成人类化转译：把接口、路由、参数、状态枚举改写成用户入口、页面表现、可用操作、反馈和结果。

### 3. 建立视觉问题

先问读者要理解什么，再选表达（交接→泳道、任务→动线、条件→决策表、迁移→状态图、页面空间→原型）。交互版先建立完整状态模型，再抽取正文所需子图；页面交互总览与局部故事板必须同源于该模型。页面交互总览中的可见页面卡片必须像缩略页面；只有标题和状态文案的圆角框仍是状态网络，不是页面交互总览。

### 4. 编译正文与资产

按用户任务聚合入口、信息、动作、反馈、结果和恢复。界面详情优先使用“当前界面或来源证据 → 调整后原型/关键状态 → 就近交互规则”的结构。原型与截图承接的充分度判断、视觉生产线（HTML 截图、纯 SVG 画板、mermaid 导出）与全部脚本用法见[视觉与原型](./references/视觉与原型.md)；执行包与原型计划的落盘时机见[质量与门槛](./references/质量与门槛.md)。

### 5. 压缩与分层

全文回读并删除重复扩写、仅用于作者工作的来源 IDs 与生成术语、不改变协作判断的实现细节、空章节和装饰性图表。保留信息不是保留篇幅：每个模块只留下读者完成第一次评审所需的信息，完整规格通过正式 PRD 来源下钻可达。

### 6. 验证与发布

| 级别 | 适用情况 | 必须完成 |
|---|---|---|
| 基础 | 所有交付 | 主源抽查、传统骨架检查、作者连续阅读、查看实际资产 |
| 增强 | 视觉版、交互版或多个关联资产 | 跨产物一致性核对、严格阅读检查、`--fail-on-warnings` 阅读视图检查 |
| 严格 | 重要评审、重复发布或用户明确要求审计 | 结构化证据、无上下文读者测试、平台发布审计；高风险交付可选对抗性自审（见《质量与门槛》§8.1） |

用户要求飞书时，飞书文档是唯一主交付面，本地 Markdown、XML 和图源只是构建材料。发布后回读正文，并逐个查看本轮新增或修改的画板/图片在正文宽度和放大视图中的表现。

## 默认输出

- 一份符合传统 PRD 语义、按需求裁剪的主文档；
- 视觉版/交互版中回答独立问题的必要图形与局部原型；
- 多页面交互版中一张可追踪的页面交互总览，除非有明确且可审查的不适用理由；
- 正式 PRD 的稳定来源下钻入口；
- 只有用户要求时才展示内部执行包、覆盖报告或审计日志。

## 交接契约

- 上游：`pm-prd-write` 的正式 PRD 是事实主源；`pm-requirement-grade` 的分级结论与"体验交付复杂度"标记作为路径与验证深度的依据；
- 下游：研发 spec 承接实现细节（本 skill 只交研发下钻线索，不写字段）；文档确认后的更新同步与留档交 `pm-update-write`；
- 收到规则变化时，按[质量与门槛](./references/质量与门槛.md) §6 的变更影响链定位受影响产物，再决定更新范围。

## 质量门禁

本 skill 的"完成标准"只表示产物已按方法生成，不等于已通过交接质量审计。

- 讨论、探索或用户明确要求"只先给初稿"时，不自动审计，并明确标记"未审计"；
- 当输出达到 `ready`、准备交给设计 / 研发 / 测试 / 运营，或用户要求复核 / 验收时，必须在本次交付前自动调用 `pm-quality-audit`；
- 只有 `PASS`，或用户明确接受带责任人和完成条件的 `PASS_WITH_CONDITIONS`，才可标记为可交接；
- `BLOCKED` 必须回到本 skill、证据 skill 或上游决策，不得用补造事实的方式消除；
- 是否需要把审计报告写入项目根目录 `quality-audits/`，按用户是否要求留档 / 交接附件决定。

## 完成标准

- 非作者能连续回答为什么做、目标是什么、做什么与不做什么、用户怎样到达结果、哪些条件改变结果；
- 第一屏建立背景、问题与目标，而不是生成说明、方案口号或研发术语；
- 正文简洁但不缺入口、信息、动作、反馈、状态、异常和恢复；
- 图、表、原型和文字各自解决独立问题，局部图与对应规则相邻；
- 页面交互总览能从入口沿页面卡片和带语义连线追到主结果、异常、返回与外部出口，不依赖分散详情拼接；
- 交互模型完整不等于正文巨图；展示资产在最终平台缩放后仍清楚；
- 原型深度与上游语义、设计资产和截图证据相匹配，没有把观察或推断升级为产品规则；
- 已完成与风险和平台匹配的新鲜检查，不依赖作者口头补充核心事实。
