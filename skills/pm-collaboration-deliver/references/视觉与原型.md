> 正文组织见《转译与文档结构》；页面交互总览的卡片/连线语义权威定义见《交互型PRD与状态模型》§5.2；检查清单见《质量与门槛》。

## 1. 表达计划与路由

每个表达项先记录：读者需要回答的具体问题；正式 PRD 来源；核心关系（顺序、交接、状态、空间、条件、层级或对比）；选择的表达及选择理由；明确包含与排除的内容；正文放置位置；视觉角色（总览、局部或下钻）；正文内联还是独立可缩放；语义和渲染如何验证。

先判断短文或小表能否直接回答。只有视觉明显降低理解成本时才画图；不能把章节标题直接转换成节点。

| 核心关系 | 首选表达 | 需要换型的信号 |
|---|---|---|
| 连续步骤与条件分支 | 流程图 | 重点其实是参与方随时间交互时改用泳道/时序 |
| 多角色或多系统交接 | 泳道或时序表达 | 只需要责任边界、不涉及顺序时用职责表 |
| 单一对象状态与事件迁移 | 状态图 | 混入多个对象或大量页面空间时拆开 |
| 页面区域、控件和反馈位置 | 原型或状态对比 | 只说明字段口径时改用表格 |
| 条件组合到确定结果 | 决策表 | 条件本身形成用户路径时使用流程图 |
| 多条件联动决定界面状态 | 逻辑表 + 测试用例表 + 静态示例（三件套，见 §7.3） | 条件少、结果单一时退回决策表 |
| 信息父子层级 | 信息结构图 | 只是章节目录时不画 |
| 范围、职责、字段和简单事实 | 短文、小表或列表 | 不使用装饰性视觉 |

同一需求可以组合多种表达，但每种必须回答不同的读者问题。

表达路由除了选图型，还要选**交互深度**，按四档判断：

| 读者需要 | 交互深度 |
|---|---|
| 理解文案、字段、不可见规则 | 不出视觉面，短文或小表 |
| 看清单屏结构、前后对比、组件状态 | 静态图即可 |
| 判断多步流程的操作行为（点完去哪、失败怎么回来） | 静态图 + 可交互原型双轨 |
| 评审视觉方向本身 | 只有用户明确使用"高保真、像素级、生产级视觉"措辞时才升级为设计模式 |

默认线框。"干净、好看、像 Linear 那样"描述的是内容与密度标准，不构成高保真请求。双轨时静态图与可交互版**同源同标签**：静态图是可检视的参照，可交互版是同一流程的可操作版本，不是另一个设计方向。可交互形态不在本 skill 内重建运行时；确需时作为独立画板交付（见 §2.4），可引用外部多屏原型工具或手工单文件 HTML，仍遵守单一事实源与稳定定位（§7.5）约定。

## 2. 视觉分层

### 2.1 总览层

建立共同心智，只回答一个跨模块问题。跨系统协作用泳道/时序，用户任务用产品动线。总览不承担完整页面空间、字段规则或全部状态覆盖。

### 2.2 页面交互总览层

把页面卡片、页面内关键状态、主次操作和跳转条件放在同一张可追踪画布上，默认用于多页面、多分支交互版。它承接产品动线，但比纯流程图更具体；统领局部故事板，但不替代字段规则和页面细节。

卡片粒度、chip/瞬态规则、screen_ref 同源和连线映射的权威定义见《交互型PRD与状态模型》§5.2，此处不重复。不能把没有页面内容的流程节点改名为页面交互总览，也不能把无连线页面画廊当作总览。

### 2.3 局部任务层

与需求详情相邻，用连续关键帧、状态对比或局部原型解释一个用户任务。每张局部图同时让读者看见关键内容、主操作和操作反馈；异常放在发生位置附近，原因很多但结果相同时使用原因组或决策表收敛。局部原型可以包含连续关键帧和少量连线，但不能混入全部异常网络。

### 2.4 完整核查层

完整状态模型、覆盖报告和全景图服务于查漏，不自动进入正文。只有满足以下条件之一时才交付全景：评审任务本身需要检查全部状态和迁移；设计、研发或测试需要一个可缩放的共同索引；用户明确要求完整交互画板。

全景在正文宽度下不可读时，提供独立画板/链接，正文只放产品主流程、页面交互总览的可读预览和局部子图。不得把"底层迁移完整"解释成"所有迁移必须画在同一张正文图"。

## 3. 上游输入充分度

`pm-prd-write` 在复杂界面需求中应交付 Page / Surface、IA / Section、用户可见状态、操作、迁移、异常恢复和验收来源。它定义产品交互语义，不保证最终视觉稿、坐标或设计系统细节。先在两个独立维度判断输入。

### 3.1 产品语义充分度

| 状态 | 已知内容 | 允许输出 | 不允许输出 |
|---|---|---|---|
| `interaction_complete` | 页面、状态、动作、迁移和恢复均可追溯 | 完整状态模型、聚焦故事板、状态对比、低保真结构示意 | 新增业务条件或恢复规则 |
| `structure_complete` | 页面目的、信息区、可见内容和主要动作明确，但迁移不完整 | 页面地图、单状态低保真、局部结构对照 | 声称完整的交互故事板或全景 |
| `partial` | 只有页面名、功能摘要或零散界面描述 | 缺口清单、现状截图标注、已有资产索引 | 目标页面和连续交互 |
| `insufficient` | 无法确定页面目的、主要内容或动作结果 | 返回上游补齐 | 任何看似确定的目标原型 |

不能因为 AI 能推断常见模式，就把 `partial` 升级为完整设计。会改变入口、信息、操作、状态、结果或恢复的缺口必须回到上游。

### 3.2 视觉上下文充分度

| 状态 | 默认策略 |
|---|---|
| `confirmed_design` | 复用具体 Frame / 组件，优先做局部标注、差异说明或增量修改 |
| `existing_ui` | 提取现状结构和约束；目标方案仍由正式 PRD 决定 |
| `reference_only` | 只借鉴可说明的视觉模式，不默认沿用结构、文案和交互 |
| `declared_unverified` | 正式 PRD 声明资产存在，但文件本轮不可访问或禁止读取；记录声明与限制，不把它当作已查看资产，按 `plan_only` 或明确标注的低保真策略继续 |
| `none` | 使用明确标注的低保真结构示意，不伪装成最终设计 |

产品语义充分不等于视觉上下文充分；有截图也不等于交互规则充分。两个维度必须分别记录。

`declared_unverified` 不等于 `none`：前者保留"上游声明已有设计/原型"的事实，避免误写为没有资产；但在实际读取前，不得选择 `reuse_confirmed` 或声称完成设计一致性验证。

### 3.3 持久视觉上下文（按需落盘）

同一产品会反复进入本流程时（多期迭代、系列需求），把视觉上下文判断沉淀为项目目录内的一份持久文件（如 `design-context.md`，在项目目录向上有限层级内查找），避免每次从零重建：

- **首次建立**：从截图、设计稿、现有页面或代码库中提取并落盘——平台形态（移动端/桌面/响应式）、导航模式、页面类型与布局习惯、组件词汇、字号/间距/密度节奏、可复用的视觉惯例；每条注明来源（观察到的事实还是推断）；
- **后续交付**：先读档，再核对新鲜度（它是否仍代表当前产品）；本期新发现的模式增量更新回文件；
- **与充分度判断的关系**：持久上下文不替代 §3.2 的逐次判断，而是把"每次重评"变成"读档 + 核对"；文件过期或与本次输入冲突时，以本次实际输入为准并更新文件；
- **权限边界**：它是辅助事实源，只约束视觉习惯，不授权任何新产品行为；产品语义充分度仍单独判断。

没有持久文件且本次输入充分时，不强行创建；只在同一产品预期会再次进入本流程时才落盘。

## 4. 设计权限与资产策略

对每个受影响 Surface 选择一种策略，并写明来源和理由：

- `reuse_confirmed`：直接复用已确认设计，不重画整页；
- `adapt_existing`：沿用现有页面壳、组件和信息层级，只表达本次变化；
- `reference_only`：截图或案例仅作观察证据，目标原型从正式 PRD 编译；
- `low_fidelity_new`：没有可复用资产但语义足够时，生成结构示意；
- `plan_only`：输入不足，只输出需要补齐的设计问题。

已存在正式设计时，重画必须说明为什么复用、标注或增量修改不能回答评审问题。局部变化默认标注局部，不为了"看起来完整"重新设计整页。

只要本期改变页面结构、主操作、可见反馈或关键状态，视觉就属于需求解释的一部分，而不是装饰项：

- 输入包含可访问截图或设计稿时，至少在对应详情中复用一处相关视觉，并明确它是现状、已确认设计还是参考；
- 输入没有视觉上下文但产品语义达到 `structure_complete` 或 `interaction_complete` 时，至少为核心变化页面输出一张低保真结构示意；
- 只有纯文案、字段、不可见规则、或图无法比短文/小表更清楚时才可以不生成页面视觉。

"源文档有图但正文未使用"和"新增核心页面但只有流程框图"都视为原型承接未完成。

设计语义层可以补全的是：信息分组、阅读优先级、主次操作关系、反馈邻近性、关键状态差异和故事板关键帧选择。不得补全的是：上游未确认的业务规则、入口、权限、状态结果和恢复路径。

## 5. 截图证据工作流

截图进入流程后，先把它当作可观察证据，不把像素当作产品规则。

### 5.1 分类与登记

为每张图记录：角色（`current_ui`、`confirmed_design` 或 `visual_reference`）；覆盖的页面、版本、端和状态；原文件路径和尺寸；是否含用户姓名、头像、手机号、班级、订单、内部账号等敏感信息；能观察到什么，以及无法从单张图判断什么。

### 5.2 分两遍检查

1. **全图检查：** 识别设备/页面壳、主要区域、信息层级、主任务、主次操作、反馈位置和整体密度。
2. **局部检查：** 以原始分辨率查看关键区域，核对文案、按钮状态、选中/禁用、弹层、错误提示、留白和裁切。

需要时先生成带编号的标注图，再根据编号建立观察表（工具见 §8）。

### 5.3 区分观察与推断

每条记录必须标记：

- `observed`：截图中直接可见，例如"底部存在一个主按钮"；
- `inferred`：根据模式推测，例如"点击后可能进入确认弹层"；
- `unknown`：单张图无法判断，例如"失败后是否保留选择"。

`inferred` 和 `unknown` 不能成为目标交互的事实来源。正式 PRD 没有确认时，写为待确认或排除，不偷偷进入按钮、连线和结果页。

### 5.4 从截图提取什么

提取对评审有用的结构，不机械 OCR 全屏：页面壳与导航；区域顺序、分组和视觉优先级；关键可见内容、控件类型和主次操作；状态线索（选中、禁用、加载、弹层、错误、空态）；可复用组件和视觉惯例；本次方案需要保留、替换、移动或删除的区域。

截图不提供隐藏状态、完整动作集合、返回/重进规则、权限或跨系统结果。若同时能读取设计节点、组件树或可访问性结构，把它们作为补充证据，但仍保持产品事实与视觉证据分离。

## 6. 流程与关系图

### 6.1 建立语义骨架

从正式 PRD 提取本图所需的最少事实：入口、参与方、动作、判断、交付物、状态变化、结果与恢复。先写无样式的节点和边清单，再选择方向、分组和图形语法。

节点写可观察的动作、页面反馈或业务结果；判断写成问题；互斥分支写清条件；跨角色连线说明交付物或状态变化。不要在节点中塞完整规则、字段或验收句子。

### 6.2 根据阅读方向布局

- 连续任务优先沿自然阅读方向展开；
- 层级或多分支判断选择能减少宽度和交叉的方向；
- 角色或系统存在稳定边界时分组；
- 返回和重进保留真实语义，不为排版删除；
- 状态图只描述一个主要对象，状态用名词，迁移用事件或条件。

数量不是拆图门槛。出现下列实际问题时才调整：一张图混合多个抽象层或多个独立读者问题；关键路径被次要异常、回边或交叉线遮蔽；标签、节点或分组在目标平台缩放后不可读；不同受众只需要其中一部分；同一图同时试图表达顺序、生命周期和页面空间。

优先尝试重新分组、改变方向或压缩原因；仍不清楚时按评审问题、语义层或受众拆图。不要为了减少节点删除正式 PRD 中的分支。

### 6.3 语义检查

- 每个非入口节点有来源，每个非终点节点有去向；
- 每个判断的分支含义明确，互斥或覆盖关系能解释；
- 终点是用户或业务结果，而不是"完成处理"；
- 失败、取消、返回、重进和人工兜底回到正确位置；
- 图中没有主源未定义的页面、状态、按钮或结果。

## 7. 页面与原型设计

### 7.1 先规划评审问题

每个原型资产先写一句读者问题。常见输出不是固定套餐：

| 读者问题 | 合适表达 |
|---|---|
| 现状哪个区域需要变化 | 局部裁切 + 编号标注 |
| 页面有哪些稳定区域和主操作 | 页面地图或单状态低保真 |
| 条件改变后哪里不同 | 并列状态对比 |
| 用户一次任务如何连续完成 | 关键帧故事板 |
| 全部状态和迁移是否闭环 | 状态模型或可缩放全景，不用手机卡片堆砌 |
| 全部关键页面、页面状态和跳转是否能连续追踪 | 页面交互总览：页面卡片 + 带动作或条件的连线 |

### 7.2 设计单个页面

每个关键状态至少能回答：用户此刻的任务是什么；第一眼必须看到什么；主要信息、辅助信息和风险提示如何分组；主操作、次操作、禁止操作分别是什么；操作反馈出现在哪里，是否靠近触发点；与相邻状态相比，信息、操作或结果改变了什么。

低保真不是所有内容都画成灰框，更不是把未决问题画成虚线"占位"框。文字、真实状态文案和按钮标签若影响判断，应直接显示；与评审无关的装饰、占位数据和精细样式应省略。具体规则：

- 页面只呈现产品经理已决定的内容：真实文案（来自正式 PRD）、具体示例数据、已决定的按钮与状态；
- 业务规则必须翻译成用户可见的界面元素：限制条件画成横幅提示，防重复提交画成禁用态按钮，资格失效画成拦截页文案；禁止在页面内放置"防误触：xxx""规则：待定"式虚线注释框；
- 未决定的业务问题不进原型：写进正文缺口清单或返回上游；
- 结构示意保留"不代表最终布局"声明，但视觉必须干净到可以直接评审。

### 7.3 设计连续故事板

以一个用户任务为单位选择关键帧：进入/准备 → 用户动作 → 即时反馈或处理中 → 明确结果/恢复。关键帧数量由状态变化决定，不按固定数量裁剪。

- 在相邻帧之间标动作或系统事件，不用"下一步"；
- 主线沿统一阅读方向，分支靠近分歧点；
- 同一结果的多个原因可在展示层收敛，底层模型保留完整迁移；
- 并列状态只展示真正变化的区域，必要时高亮差异；
- 返回、取消、重进和失败恢复若会改变结果，必须在故事板或相邻规则中出现；
- 无连线的页面组只能称状态概览，不能称交互故事板。

**复杂联动用三件套，不硬做交互**：多条件共同决定界面状态、字段间实时联动这类逻辑（如"按 A×B×C 三个维度判定按钮是否置灰"），原型不必把联动真的做出来——成本高、易出 bug，且评审要的是"理解规则"而不是"操作规则"。改用三件套表达：

1. **逻辑表**：情况 → 处理方式，把规则本身讲清；
2. **测试用例表**：输入组合 → 预期输出，枚举到多条件并存和边界（如"全部命中"），多原因并存时预期输出须写"原因全部列出"而非只显示一个；这张表应达到 QA 可直接当测试用例用的精度；
3. **静态示例**：在原型里放一个该状态的真实静态样例（如一行置灰记录 + 原因标签），旁注"原型为静态示例，不做联动"，让评审一眼看到长什么样，不用脑补。

禁止用伪代码描述命中条件——评审现场实测反而更难懂；具体用例（是/否/具体值 → 预期状态 + 原因）才是最直观的评审语言。三者分工：逻辑表讲规则，用例表验证理解，静态示例给视觉锚点。

### 7.4 原型边界

- 结构示意必须标注"不代表最终布局"；
- 原型只承担空间、信息层级、状态、动作和反馈位置；
- 权限、业务条件、数据口径、异常与验收仍由正文或决策表承载；
- 没有确认的页面结构不生成看似确定的高保真设计；
- 单张截图不能证明隐藏状态、动作结果、返回、重进、权限或跨系统行为；
- 声明为完整交互画板的资产必须从同一状态模型生成，并明确 `coverage=complete`；局部故事板使用 `coverage=focused`，只核对声明的状态和迁移子集；
- 不在正文中并排展示过多完整手机页；优先截取关键区域或拆成相邻的任务故事板。

### 7.5 资产稳定定位协议

评审反馈、批注和跨轮修改都需要精确指回资产中的位置，而视觉资产会被反复重生成。位置引用必须跨轮稳定，否则"第三个状态的那个按钮"这类描述会在重生成后错位。多轮迭代或需要承接评审反馈的资产启用本协议；一次性评审稿不强制。

生成侧约定：

- **资产级**：每个视觉资产和每个状态故事有稳定 id（如 `sb-change-period`、`state-orders-loading`），出现在正文引用、图注或资产文件中。id 一旦给出，只增、不改、不复用；删除的 id 留痕，不分给新内容；
- **区域与节点级**：关键信息区、主操作、状态差异节点携带以资产 id 为前缀的语义 id；重复数据节点使用稳定 data-key（业务 id），不使用数组下标；
- **禁用定位方式**：正文段落序号、`nth-child`、文字内容、"第几个按钮"等会随重生成漂移的引用，都不作为定位协议；
- **脚本配套**：`build_screen_html.py`、`render_overview_board.py` 等生成脚本输出的 HTML 应为关键节点携带上述稳定 id，使定位协议在机器生成资产上同样成立；脚本尚未输出稳定 id 时，先补齐脚本再依赖定位引用。

反馈侧约定见[质量与门槛](./质量与门槛.md) §6：评审意见以"资产 id + 区域/节点定位 + 意见"三元组登记后，再进入分类处置。

**批注覆盖层（生成层与人改层分家）**：需要人在资产上直接批注、且资产还会被 AI 重生成时，把人的批注存进独立的覆盖层文件（模板见 `assets/annotations-overlay-template.js`），与生成层分离：

- 可批注的文本载体携带稳定 `data-anno-id`（遵守本条 id 规则：只增不改不复用）；
- 覆盖层以 id 为键存放人的改动（覆盖 / 新增 / 删除），渲染时合并回生成层；
- 重生成资产时**永不覆写覆盖层文件**——生成层可以随便重写，只要 id 稳定，人的批注就不丢。

覆盖层是可选增强：只交付 PNG 的默认路径不需要它；交付 HTML 形态资产且需要现场批注时启用。

### 7.6 原型版本与变更信号

同一套原型或视觉资产经历两轮以上评审、或已对外发布时启用版本信号；一次性内部评审稿不强制。版本信号解决两个问题：评审人打开资产时一眼看出"这一轮改了哪"；争议时拿得出"当时定的是哪个版本口径"的锚点。

**版本节奏**：`v0.1` 为内部制作期（未对外同步）；`v0.2` 为已对外发出；评审通过后进入 `v0.3.x`。升号判据是"上一版是否已发出并通知下游"：

- 已通知 → 本次改动升号，锁定为新的对照快照；
- 未通知（含已存档但未告知）→ 改动合并进当前版本号，变更摘要追加，不机械升号。

版本号是给下游对照者看的，不是自己的存档编号；每次小改都升号会让评审同事追不上、变更记录被淹没。

**变更信号三件套**（v0.2 起任何改动都执行；v0.1 阶段整页全新增加可免标，改删既有内容仍须标）：

1. **原位徽标**：改动处在原位挂徽标，措辞固定为"新增 / 修改 / 删除"三类并带版本号（如 `v0.3.2 修改`）；
2. **旧值保留**：修改与删除不覆盖旧内容——旧值删除线保留、新值并列，让评审看出"原来什么样、改成什么样"；
3. **版本变更记录**：在主文档或原型入口页独立成章（不埋在其他章节内部），固定列为 版本号 / 时间 / 类型 / 涉及资产（可跳转）/ 变更摘要，按时间倒序，最新在顶。

**摘要口径**：变更摘要只写业务与原型层变化（规则变化、文案口径、交互流程、数据口径），每条是一句业务话；不写工程实现细节（文件结构调整、引用方式、样式工程），不写"优化体验"式口号。一次版本涉及多处文件改动时，按业务事项归并，不按文件流水账展开。

**两个版本号分离**：面向评审的版本号（v0.1 / v0.2 / v0.3.x）按上述规则维护；静态资源的工程修订号（如 `?v=` 查询参数）只用于破除缓存，与评审版本号解耦，不写入版本变更记录。

**范围裁剪用隐藏而非删除**：评审定档后需要把原型裁剪到本轮范围时，非本轮内容用隐藏处理并就近注释原因，不真删——优先级定档变化时可逆恢复。裁剪后扫描一遍残留入口：不允许存在"从本轮活跃页面可点击进入已隐藏页面"的死胡同，也不允许本轮内容因唯一入口被隐藏而成孤儿（必要时给该内容改挂一个本轮入口）。

## 8. 工具地图与执行顺序

需要跨资产可追溯审计时（复杂原型、重复发布或用户要求结构化证据），再用 `assets/prototype-plan-template.json` 建立计划并运行 `scripts/audit/check_prototype_plan.py`；默认路径用本节的充分度判断即可，不强制落盘计划。

执行顺序：

```text
登记正式 PRD、设计资产和截图
→ 判断产品语义与视觉上下文充分度
→ 选择复用、标注、适配、低保真或只规划
→ 建立 Surface、区域、状态与输出计划
→ 先做一张代表性资产并查看
→ 按区域或任务增量生成
→ 装配进对应正文位置
→ 检查正文宽度、放大视图和交互连续性
```

工具选择服从资产目标：

| 任务 | 工具 |
|---|---|
| 流程图 / 分支流程 | `assets/flow-diagram-template.json` 建模 → `scripts/check_flow_diagram.py` 语义检查 → `scripts/render_flow_diagram.py` 渲染 SVG+PNG；本地渲染不依赖 mermaid-cli / graphviz / 网络，`.mmd` 只作可选交换格式 |
| 关键页面故事板 / 低保真原型 | `assets/mobile-screen-storyboard-template.json` + `scripts/build_screen_html.py`（组件词汇见 `scripts/mobile_screen_kit.py` 头注）→ `scripts/capture_html_png.py` 无头浏览器截图出 PNG；无浏览器环境退回 `scripts/render_wireframe_board.py` 灰盒渲染器 |
| 页面交互总览 | `assets/page-interaction-overview-template.json` 映射卡片与连线 → `scripts/check_page_interaction_overview.py` 检查 → `scripts/render_overview_board.py` 渲染（HTML/PNG/SVG 同源同布局；主路径置顶成连续阅读线，分支/异常挂在分歧点下方，外部出口收进右侧出口栏，`layout_group` 渲染为分组底带，线型区分主路径/分支/异常/返回并附图例；自动布局不满意时可用卡片级 `layout` 显式覆盖） |
| 截图编号标注 | `scripts/annotate_reference_screenshot.py` |
| 飞书画板输入 | 简洁流程用 `scripts/export_flow_mermaid.py` 导出 mermaid；精确布局组合图用 `render_overview_board.py --svg` 纯 SVG（飞书画板 SVG 导入只保留原生图元，不支持 foreignObject） |

工具分两层：上表是默认生产链（SVG→PNG 转换由内部库 `scripts/render_svg_png.cjs` 承担，不直接调用）；`scripts/audit/` 下的执行包、交互模型、原型计划与飞书审计检查器是**可选审计件**，只在严格发布或用户要求结构化证据时启用（见《质量与门槛》§9）。

已有设计系统或可编辑设计文件时优先复用组件、变量和现有页面；现状截图或已确认视觉优先标注、裁切和差异表达；复杂状态关系使用状态图或可缩放画板。飞书只负责发布与阅读，不应反向决定产品原型结构。不要把 Figma、飞书画布、Mermaid、SVG 或某个节点数阈值写成所有需求的强制规则。

线框规格声明 `delivery_role`：正文资产使用 `inline` 并设置目标阅读宽度；完整全景使用 `zoomable`。渲染器按最终宽度推算字号和高度，不能通过时应拆成聚焦故事板，而不是提高固定节点上限。

正文内联的故事板默认只包含完成当前任务所需的连续状态。若需要完整交互核查，先从模型抽取展示子图；不要用手机页面卡片承载庞大的状态网络。完整生命周期更适合状态图，复杂全景更适合作为独立可缩放画板。

## 9. 文档装配

先判断是否存在不同抽象层的独立问题。例如：跨系统端到端任务链、用户产品动线、完整页面状态核查、单个任务的页面空间分别属于不同问题。若一张图能清楚回答全部问题，可以合并；只要混合后需要读者反复解码，就拆开。

装配时遵循：

1. 产品主流程放在读者需要建立任务心智的位置；多页面交互的页面交互总览紧随其后；
2. 局部视觉紧邻对应用户任务和规则；
3. 图前一句说明阅读目的；
4. 图后只补无法视觉化的限制与边界；
5. 图已承担顺序、状态或空间关系时，删除同构段落和大表；
6. 同一事实跨模块需要再次出现时使用引用或来源下钻。

## 10. 渲染检查与返工

第一版资产只代表结构已经生成，不代表可交付。必须实际查看目标平台中的图：

- 中文、字号、裁切和留白是否可读；
- 连线是否穿过文字、方向是否误导、条件标签是否贴近对应分支；
- 页面状态差异、按钮可用性和反馈位置是否清楚；
- 主线能否快速扫描，异常是否靠近发生位置；
- 图注和来源是否正确，是否含敏感信息；
- 图与上下文是否连续，是否需要读者来回翻找；
- 页面真实性：读者能从页面卡片或局部原型识别这是哪个页面、此刻要做什么、主要操作在哪里；只有状态标题和说明文字的不通过。

额外执行两种视图检查：

1. **正文宽度：** 不放大时能否读清标题、节点、动作和状态差异；不能则拆分或改为局部图。
2. **放大视图：** 独立画板中的完整路径、回边和异常是否仍可追踪；不能则改用状态图、按任务分区或减少可见迁移。

线条没有穿字不等于布局合格。还要检查主路径是否连续、长回边是否遮挡其他任务、标签是否属于唯一连线、视觉是否因过高或过宽而在正文中失去意义。

人工检查还包括：设计正确性（所有页面行为和状态能回到正式 PRD）；信息完整性（入口、关键信息、操作、反馈、结果和恢复按适用性覆盖）；参考一致性（已确认设计被复用，现状截图没有被误当目标方案）；变化承接（源文档中与本期变化直接相关的截图/设计已被查看并复用、标注或明确说明不适用，没有静默丢失）。

发现问题时按根因返工：产品行为缺失回上游；证据角色错误回输入层；关键帧或信息层级错误回设计语义层；语义错误回到事实或交互模型；图型错误重新路由；布局错误调整方向、分组或拆分；错位、裁切和交叉回渲染层；文字重复回装配压缩。删除不能降低理解成本的视觉。

## 11. 方法来源

只吸收可迁移的方法，不复制工具约束或平台语法：

- [Figma MCP screen-building workflow](https://github.com/figma/mcp-server-guide/blob/main/skills/figma-generate-design/SKILL.md)：先检查现有页面和设计系统，按区块增量构建，再分别查看整体与局部截图。
- [Storybook](https://github.com/storybookjs/storybook) 与 [test runner](https://github.com/storybookjs/test-runner)：把界面状态作为可独立呈现、可执行验证的场景，而不是只检查一张最终页面。
- [XState](https://github.com/statelyai/xstate)：用显式状态、事件、迁移和图遍历保持复杂交互可预测、可检查。
- [Playwright visual comparisons](https://github.com/microsoft/playwright/blob/main/docs/src/test-snapshots-js.md)：保留稳定基线、在一致环境下比较渲染结果，并人工审阅变更。
- [Microsoft OmniParser](https://github.com/microsoft/OmniParser)：将截图拆成结构化可理解元素；本 skill 只借鉴"先结构化再行动"，不要求安装模型。
- [GitHub screenshot guidance](https://docs.github.com/en/contributing/writing-for-github-docs/creating-screenshots)：只在空间定位确有帮助时使用截图，保留恰当上下文并处理敏感信息。
- [Mermaid layout reference](https://github.com/mermaid-js/mermaid/blob/develop/docs/intro/syntax-reference.md)：根据关系复杂度选择布局，布局算法只解决排布，不替代语义拆分。
- [baoyu-design](https://github.com/JimLiu/baoyu-design)：原型/线框的默认载体是自包含 HTML + 浏览器截图预览；"不加填充内容、不用占位文字、真实数据、44px 触控目标、CJK 字体栈"等工艺标准已并入本 skill 的组件系统（`scripts/mobile_screen_kit.py`）。
- [ui-mockup-desktop-workbench](https://github.com/PANGKAIFENG/ai-product-manager-skills/tree/main/skills/ui-mockup-desktop-workbench)：先结构（页面清单、状态模型、ASCII 布局）后视觉的门禁式推进，与本 skill 的原型计划/检查器分工一致。
