## 1. 产物定位与唯一主交付面

`pm-prd-write` 的正式 PRD 是产品事实主源，保存完整规则、状态、异常、验收、发布和研发 spec 交接。本 skill 的传统 PRD 是面向产品、设计、研发、测试和运营的主阅读文档：它不改变事实，只把事实组织成更符合人类评审习惯的产品叙事。

默认成稿不是会议简报、作者总结或执行日志。标题与正文直接使用业务语言，不展示"读者主线""协作下钻""视觉角色""执行包"等生产术语。

一次交付先选择一个主阅读面。默认是传统 PRD；用户要求飞书时，飞书文档就是主阅读面，本地 Markdown、XML、图片和画板源文件只作为构建材料。

以下是不同交付物，不得混成同一目录：

| 交付物 | 主要任务 | 默认状态 |
|---|---|---|
| 传统 PRD | 支撑产品、设计、研发、测试完成第一次共同评审并继续执行 | 唯一主文档 |
| 会议讲解稿/评审简版 | 帮助主持人在有限时间内讲清取舍和待决策 | 仅用户明确要求时附加 |
| 正式 PRD | 保存完整产品事实、验收、发布与 spec 交接 | 上游事实源和下钻 |
| 交互模型/执行包 | 检查状态、迁移、来源和跨资产一致性 | 内部证据 |
| 研发 spec | 说明字段、接口、存储、队列、算法和实现 | 下游文档 |

不要因为正式 PRD 很长，就把传统 PRD 改写成"一句话方案—评审重点—研发下钻"的简报。简报可作为附加视图，不能替代默认产品文档。

## 2. 读者主线与默认骨架

传统 PRD 的稳定语义链是：

```text
需求背景（现状与问题）
→ 需求目标
→ 需求范围
→ 产品方案
→ 需求详情
→ 验收标准
```

这六类信息是默认核心，不等于必须机械保留六个等长章节。小需求可以合并背景与问题，或把范围写成很短的"本期做 / 本期不做"；但不得丢失目标、边界或验收。章节可以按需求复杂度合并小节或增加业务标题，但不能失去这条推理链。

第一屏优先帮助读者理解背景、问题和目标；产品方案建立共同心智，需求详情支撑执行。

以下内容仅在有真实信息时出现：修订记录、业务流程、用户流程、页面变化总览、通用规则与异常、影响与上线、数据与效果验证、关联资料。删除不适用章节、空表和模板提示，剩余编号连续。

不把下列内容设为主骨架：作者的一句话总结；生成过程、来源盘点和检查日志；研发待办或接口清单；按页面/状态机械展开的目录；会议议程和评审问题。

## 3. 核心语义

### 3.1 需求背景

先写与本需求直接相关的客观现状，再指出现状中的具体问题。回答：谁在什么场景下做什么，当前如何完成，哪里受阻，影响谁。

背景只承载客观既定事实，不带任何诉求：不出现"本期""我们将""需要""希望"等意图词。问题从事实直接推出，不提前写方案：不出现"通过""新增""支持""优化"等方案词。

事实、数据和反馈说明来源与时间。没有数据时不补造数字；"体验差""能力不足"等判断必须落到可观察的问题。

### 3.2 需求目标

写本期预期达到的理想终态：全局性、结果性的用户或业务状态变化，而不是过程，也不是要交付的功能。

- 合格（量化）：换期类班主任人工协调量下降；冲突用户的换期完成率提升（注明口径与基线）。
- 合格（定性）：用户可以在无需班主任代办的情况下完成一次换期，并明确知道结果。
- 不合格：新增换期页面；支持换期功能；按时完成上线；引导用户进入调整页面（过程描述）。

有可信基线和口径时优先量化（降低 xx、提升 xx）；没有可信指标时写一句可验证的终态；两者都写不出时删除目标一节，不要硬凑。步骤、耗时、成功率、使用率、转化或投诉等上线后观察指标放在"数据与效果验证"。

方案描述（"本期的改变是……"这类话）只在"产品方案 / 整体方案"出现一次；背景、问题、目标章节引用结论即可，不重复展开。

### 3.3 需求范围

明确本期做什么、不做什么，以及必要的端、角色、场景和版本边界。范围写产品边界，不写实现任务清单。

### 3.4 产品方案

用一段短文或一张总览图说明产品如何从入口连接到结果，以及关键角色如何协作。只有存在真实顺序、分支、交接或页面迁移时，才增加流程图、用户动线或页面变化总览。

### 3.5 需求详情

按用户任务、业务对象或内聚闭环组织，而不是机械按页面、FR 编号或系统拆章。每个模块尽量就近说清：

1. 进入条件；
2. 用户看见的信息；
3. 可执行动作；
4. 系统反馈；
5. 成功、失败和恢复结果。

详情标题直接说明对象和变化，例如"课程冲突提醒与换期入口""确认换期与结果反馈"，避免"功能说明""相关优化"这类空标题。

### 3.6 验收标准

保留跨角色可以共同确认的产品结果，不复制正式 PRD 的全量 AC 矩阵。验收应覆盖主路径、关键限制和高风险异常，并能回到正文规则。

## 4. 从正式 PRD 转译

### 4.1 上游产物映射（承接的唯一权威表）

正式 PRD 的标准结构来自 `pm-prd-write`（0-8 章 + 组合输出模块）。承接时按下表取料；上游是全集，传统 PRD 是选集：

| 上游产物 | 传统 PRD 归宿 | 承接方式 |
|---|---|---|
| 0 一页结论、1 决策依据 | 需求背景 / 需求目标 / 需求范围 | 重述不照抄：保留事实与结论，压缩来源叙述 |
| 2 方案总览、2.2 产品动线 | 产品方案 | 先给短结论，必要时配总览图 |
| 2.4 原型与设计资产索引、2.5 场景—原型关联 | 需求详情的视觉证据 | 只登记证据角色与可达性；原型生产按《视觉与原型》的充分度判断独立决策，索引不直接变成页面清单 |
| 3 交付范围与功能需求（FR / RULE） | 需求详情 | 按用户任务聚合，形成局部闭环 |
| 4.x 页面状态与操作矩阵 | 交互模型 + 详情关键状态 | 主路径与会改变结果的异常进正文 / 总览；全量矩阵只进交互模型核查层；矩阵中已定文案直接作为原型真实文案素材 |
| 3.x 系统能力需求表 | 产品方案职责表 / 协作依赖层 | 只写会改变评审与跨团队责任的边界 |
| 6 验收与追溯（AC / Given-When-Then） | 验收标准 | 提炼跨角色可确认的产品结果，全量矩阵回链主源 |
| 稳定 ID（目标 / 场景 / 功能 / 规则 / 验收） | 内部证据 | 作为同源检查与评审关注的定位锚点，退出正文 |
| 5 影响、依赖与发布 | 影响与上线（按需） | 只写会影响评审和交付的事项 |
| 7 效果验证 | 数据与效果验证（按需） | 有上线判断需求时保留 |
| 通用规则、跨模块联动 | 通用规则与异常（按需） | 只保留真正跨模块的内容 |
| 8 研发 spec 交接清单 | 不承接 | 保持研发下钻，防止实现语言回流正文 |

### 4.2 承接纪律

1. **选集原则：**正文只取第一次评审所需子集；被裁内容不删除、不回改上游，保持来源下钻可达。
2. **身份保持：**上游标注的"待确认 / 假设"按原身份承接，不洗白成事实；上游内部冲突不静默选边，进入 §4.5 评审关注或返回上游。
3. **重述不照抄：**冗杂句段按用户任务重述为短句；缺口会改变入口、权限、主操作、状态、结果或恢复时标为待确认，不自行补规则。
4. **输入分级：**轻量输入只承接背景、范围与功能明细，不强制全套映射核对；非标准输入先整理输入摘要与缺口清单。

### 4.3 执行四次转译，而不是删减章节

1. **事实归并：** 把一页结论、FR、RULE、状态矩阵和 AC 中描述同一用户任务的事实合并，先消除重复和不同措辞。
2. **用户化：** 把路由、参数、状态枚举和系统动作改写为"用户从哪里进入、看到什么、能做什么、得到什么结果"；精确技术值只保留在研发下钻。
3. **变化化：** 对每个受影响页面或任务明确"当前怎样—本期怎样—哪些保持不变"，让读者先看懂变化，再读条件和异常。
4. **图文化：** 已有截图/设计时优先裁切、标注或增量表达；没有视觉上下文但交互语义完整时，为核心变化生成低保真。只有图明显不能降低理解成本时才省略，并说明由什么文字或小表替代。

正式 PRD 的章节、ID 和矩阵是提取索引，不是传统 PRD 的目录。一个任务的入口在 FR、失败在 RULE、结果在 AC 时，必须在同一详情模块中重新闭环。

### 4.4 缺口的模块级处理

- **阻断缺口：** 会改变用户看到什么、能做什么、最终得到什么、如何恢复，或会改变权限、时间、数据口径。停止受影响模块的定稿、原型和验收，返回上游补齐；其他稳定模块可以继续。
- **非阻断缺口：** 产品行为已经确定，只缺设计稿、实现字段、负责人、发布时间或来源下钻资料。正文可以继续，但要就近写明缺口、影响、责任角色和补齐门槛。
- **表达要求：** 使用"待产品补齐""待设计确认""待研发细化""待数据补口径"等准确标签。不要把全部未知统一写成"评审待确认"，更不能把产品已经确认的规则重新列为会议拍板项。

### 4.5 评审关注区块（可选）

正式 PRD 本身已写明风险、待确认项、关键决策或验收风险时，可以在正文之前放一个不参与编号的"评审关注"区块，帮助评审者快速定位需要拍板的点。纪律：

- **只摘取，不生成：** 每条必须来自正式 PRD 已有内容；源文档没有这些材料时整块省略，不输出模型自己的总结、建议或"泛化提醒"；
- **每条带来源定位：** 末尾标注正式 PRD 的章节号或 FR/RULE/AC ID，读者可跳回原文核对；
- **不复述正文：** 功能明细、规则矩阵和验收表不在此重复；
- **保持紧凑：** 不超过 7 条，超出说明摘取标准过宽。

## 5. 三层信息模型

### 5.1 产品主阅读层

写用户和业务可观察的事实：场景、问题、范围、用户任务、页面信息、操作、反馈、状态、异常、恢复和明确文案。默认读者不需要理解系统实现也能走通主线。

### 5.2 协作依赖层

只写会改变产品评审或跨团队责任的系统边界：谁触发、谁提供结果、谁执行、失败由谁兜底、依赖何时可用。系统名称可以出现在方案泳道、职责表和详情中的必要调用点，不在每一段反复出现。

### 5.3 研发下钻层

接口字段、错误码映射、鉴权、幂等实现、并发控制、队列、缓存、存储、算法、日志结构和数据库设计进入研发 spec。传统 PRD 只保留对应能力要求或结果约束，例如"重复点击不能产生第二次有效提交"。

使用"产品结果"替换"实现手段"：

| 不放在主阅读层 | 主阅读层写法 |
|---|---|
| CRM 幂等键阻止重复请求 | 提交中不可重复操作；重复进入不能产生第二次有效结果 |
| 接口超时和错误码统一映射 | 结果不明确时不展示成功，并提供明确恢复或人工出口 |
| 用满返回 P0 字段 | 进入可操作页面前，关键展示信息必须完整 |

## 6. 模块聚合方法

以用户任务或协作闭环作为详情模块。一个合格模块通常能独立回答：

1. 谁在什么条件下进入；
2. 用户需要看懂什么；
3. 用户可以做什么；
4. 系统如何反馈；
5. 正常结果、异常结果和恢复是什么。

页面和状态是模块内证据，不自动成为章节。同一页面承担多个独立任务时可以拆模块；多个页面共同完成一个任务时应合并说明。

为每个高风险事实指定一个主要模块。概述只保留能建立全局心智的压缩结论，验收只引用结果，不重新扩写完整规则。

## 7. 按需求裁剪

| 需求结构 | 正文重点 | 常见视觉 |
|---|---|---|
| 文案、字段、单一展示规则 | 背景、目标、范围、改动前后、验收 | 局部标注或对比；也可不用图 |
| 单页或单任务迭代 | 核心骨架、关键状态、异常恢复 | 局部原型、状态对比 |
| 完整用户流程 | 核心骨架、入口到结果、分支规则 | 用户流程或产品动线 |
| 多角色或跨系统协作 | 职责边界、交接、失败兜底 | 泳道或时序图 |
| 多页面、多状态、高风险恢复 | 任务模块、状态迁移、返回/重进 | 总览流程 + 局部交互故事板 |
| 后台、规则或数据调整 | 操作对象、字段规则、结果与兼容 | 小表、决策表、必要页面示意 |

视觉数量和节点数不预设。只有图能明显降低理解成本时才使用；一张图只回答一个主要问题。

轻量需求默认压缩成四个连续模块即可：`背景与目标 → 范围与方案 → 需求详情 → 验收标准`。可以在一个模块内同时保留背景、问题和目标语义，不为凑齐六个标题拆成多页。轻量成稿通常不应比输入显著更长；若篇幅增加，必须来自新增的可读视觉、明确边界或源文档已有但原先分散的关键规则，而不是模板字段和重复表格。

## 8. 详情表达

### 8.1 简单变化

用"当前 → 调整后"或短表说明改动对象、准确内容、触发条件和保持不变项。

### 8.2 条件交互

使用"当……时……；否则……"说明展示条件、默认值、操作、校验、反馈和生效时机。条件较多时使用决策表。

### 8.3 页面与原型

原型紧邻对应规则，优先采用以下顺序：

1. 当前界面或来源截图（确有对比价值时）；
2. 调整后页面或关键状态示意；
3. 紧邻图片的交互规则与边界。

图片负责说明位置、层级、主次操作和状态差异；文字负责说明条件、动作、结果与边界。源文档已经包含页面截图、原型或设计节点时，不得在不查看的情况下静默省略，也不得无理由重新设计整页。

页面规则不要默认塞入五列以上宽表。单一页面优先使用短段落、三列以内的状态/操作小表，或在原型旁做编号说明；只有存在多个同构条件需要横向比较时才使用宽表。

### 8.4 跨端与多状态

写清各端差异、状态进入与退出、优先级、刷新/重进、取消/失败后的恢复。若上游未定义，不根据常识补齐。

## 9. 语言与版式

- 标题使用业务对象和变化，不使用内部方法术语；
- 开头先讲背景、问题和目标，不先讲生成过程或研发实现；
- 一段只表达一个结论，优先短句；
- 重复规则只保留一个主要归属，其他位置引用；
- 图表前写清它回答什么，图表后只补充无法从图中读出的结论；
- 避免宽表、长段落、连续页面画廊和无信息装饰；
- 不把接口、字段、错误码、幂等、队列或数据库设计写进产品主阅读层。

## 10. 反模式

- 同时交付"协作 PRD""视觉版 PRD"和"传统 PRD"，但没有说明哪个是主文档；
- 正文每节都重复范围、一次限制、成功条件和失败出口；
- 用系统名作为用户旅程节点，或用接口状态作为页面标题；
- 把所有页面排成九宫格，却没有说明动作和结果；
- 把全部状态和迁移画成一张大图并缩进正文；
- 原型集中在文档前部，规则集中在后部，读者需要跨页匹配；
- 以"模型通过、图片生成、飞书上传成功"代替读者和渲染验收。

## 11. 术语表

全库术语的唯一定义处；其他文档与正文使用术语时以本节为准，不再各自解释。

| 术语 | 定义 |
|---|---|
| 主阅读面 | 读者实际阅读的交付面（本地文档或飞书文档）；区别于只作构建材料的本地图源与中间文件 |
| 研发下钻 | 实现细节（接口字段、队列、存储、算法等）移交研发 spec，正文只保留产品结果约束 |
| 视觉下钻 | 完整全景作为 `delivery_role=zoomable` 的独立资产存在，正文只放可读的总览与局部子图；视觉角色枚举值"下钻"（总览 / 局部 / 下钻）即指此义 |
| 来源下钻 | 完整事实、全量矩阵与验收回链正式 PRD 的章节 / ID，正文不复制全量 |
| 同源 | 正文、视觉与验收描述同一上游事实，且各自能定位回正式 PRD 的具体位置 |
| 低保真 | 只表达信息结构、主次操作与状态差异的示意页面；不代表最终视觉设计，不得伪装成设计稿 |
| 内部证据 | 交互模型、执行包、覆盖报告等生产过程文件；供检查与追溯，不进入正文 |
| 评审关注 | 正文前可选的不编号区块，只逐条摘取正式 PRD 已写明的风险、待确认与关键决策并标注来源 |
