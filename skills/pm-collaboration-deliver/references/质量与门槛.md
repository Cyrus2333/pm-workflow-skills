## 1. 执行层的定位

上游 `pm-prd-write` 决定并展开产品事实；本执行层把稳定规格编译成可阅读、可视化、可检查的协作产物。它不重新决定产品方向、范围、规则或验收。

这项能力按五层组织。这里的“层”是能力分工，不是需求分级中的 L0/L1/L2/L3：

| 能力层 | 负责回答 | 必须留下的结果 |
| --- | --- | --- |
| 1. 输入契约层 | 正式来源是什么，结论是否稳定，设计资产与截图各自能证明什么，本次可以开始交付编译吗 | 正式来源、证据角色、稳定性判断、待确认项 |
| 2. 语义编译层 | 给谁看、为完成什么任务看、阅读主线是什么，传统 PRD 各模块如何按事实语义落位 | 读者任务、决策主线、背景/问题/需求/目标等正文结构 |
| 3. 交付生产层 | 哪些逻辑应写成文字，哪些应转成流程、页面状态或原型，产物如何贴近对应规则编排 | 页面/状态清单、视觉计划、图和原型、组装后的交付物 |
| 4. 证据校验层 | 高风险事实是否在正文、流程、页面和验收中一致，真实渲染后是否可读 | 语义证据链、来源校验、渲染检查、阅读测试、门槛结论 |
| 5. 工具适配层 | 如何降低机械成本并适配具体文档、原型或发布平台 | 检查脚本、渲染工具、平台适配器；不得承载业务真相 |

前四层构成可用能力的闭环；第五层只负责提效。不能因为有生成图或检查脚本，就跳过语义编译和人工产品判断。

一个可用的执行层必须完成五件事：

1. **编译：**识别读者任务，重组主线，而不是机械删减正式 PRD；
2. **生产：**从状态与页面关系生成视觉计划和资产，而不是从全文直接生图；
3. **装配：**把总图放在建立心智模型的位置，把单页图与对应规则放在一起；
4. **见证：**确保高风险事实能在正文、流程/页面和必要验收中互相印证；
5. **验收：**检查实际渲染与非作者阅读任务，而不是以“文件已生成”作为完成。

## 2. 交付物契约与交付蓝图

### 2.1 交付物契约

开始生产前先锁定：

- `primary_artifact.type` 默认为 `traditional_prd`；
- `primary_artifact.surface` 是本地文档、飞书或用户指定平台中的一个；
- `primary_artifact.format` 遵循用户/项目约定；未指定的本地交付默认 `markdown`。选择 `docx`、`pdf` 或其他办公格式时，必须同时声明对应渲染与验收方式；
- `reader_spine` 至少覆盖需求背景、需求目标、需求范围、产品方案、需求详情和验收标准；
- `technical_depth` 默认为 `collaboration_only`，实现细节下钻；
- 每个视觉声明总览、局部或下钻角色；
- 完整模型与展示子图分离。
- 需要原型时，分别声明产品语义充分度、视觉上下文和复用/标注/低保真策略。

用户明确要求会议简报或讲解稿时，可以追加 secondary artifact；不得静默用简报替换传统 PRD。用户要求飞书时，本地文件是构建源，飞书文档是主交付面。

### 2.2 交付蓝图

视觉版或交互版在写正文前，先在工作上下文或执行包中确定：

- `primary_artifact`：传统 PRD；
- `reader_spine`：需求背景、需求目标、需求范围、产品方案、需求详情和验收标准；
- `modules`：按用户任务命名，每个高风险事实只有一个主要归属；
- `review_questions`：读者要回答的问题；
- `representation`：文字、表格、流程、泳道、状态或原型；
- `visual_role`：总览、局部或下钻；
- `placement`：视觉在正文中的准确位置；
- `term_policy`：哪些系统术语需要保留，哪些实现术语下沉；
- `validation`：同源和最终渲染如何验证。

蓝图是内部生产计划，不进入最终文档。

## 3. 执行包

### 3.1 何时落盘执行包

执行包是严格验证或用户要求结构化审计时的内部证据，不是生成协作 PRD 的前置表单。默认与增强路径不强制落盘；只有存在跨产物漂移风险时才落盘，例如：

- 使用交互模型，同时生成正文、总览图和一个以上局部资产；
- 多角色/系统交接、多个校验时点或恢复路径共同改变用户结果；
- 高风险规则分布在多个正文模块和视觉资产中，需要可追溯更新；
- 同一产物会重复发布、增量修改或作为正式评审门禁；
- 用户明确要求结构化审计、覆盖报告或机器检查证据。

只有一张辅助图、少量页面状态或一次性评审稿时，可以直接在工作上下文中保存读者问题和来源，不必创建执行包。局部替换、单控件规则或少量条件只执行基础验证。

原型计划与执行包也不是同一物：原型计划只在需要承接设计资产、截图或复杂页面生产时记录设计权限与输出策略；执行包只在跨产物漂移风险较高时建立。两者都不是正文。

### 3.2 执行包结构

执行路径使用 `assets/delivery-execution-pack-template.json` 建立内部执行包。它不是新事实源，只记录正式 PRD 已确认内容的生产归宿。

#### 阅读任务与主文档

- `audience`：谁要使用成稿；
- `review_task`：读者需要理解、判断或执行什么；
- `mainline`：一条可复述的正常主线；
- `source` 与 `document`：正式 PRD 和传统 PRD 路径。
- `primary_artifact`：文档类型、交付面、读者骨架和技术深度；

#### 高风险事实

只记录会因误读导致越权、错误状态、错误结果、数据损失或错误时间生效的事实。每项写明：

- 事实陈述；
- 正式 PRD 来源定位；
- 传统 PRD 正文归宿；
- 是否必须由流程图或页面状态见证；
- 对应视觉资产。

#### 页面、状态、操作与迁移

复杂界面使用 [交互型PRD与状态模型](./交互型PRD与状态模型.md) 的四层模型。先列稳定载体/页面，再列该页面的用户可见状态、每个状态的可用操作，以及触发动作/条件通往的下一状态。每个状态至少写清：载体、进入条件、用户看到什么、能做什么、结果/出口、失败恢复、正式来源和对应视觉。

以下情况拆成独立状态：用户看到的信息、主操作、结果或恢复路径发生明显变化。只有文案或局部数据不同、页面骨架和行为相同的状态可以共用一个页面并在规则中列差异。

#### 评审问题与表达计划

先为每个读者问题写明来源、关系类型、表达选择、范围、选择理由和验证方法；只有选择视觉时才新增视觉资产。不能用“补一张流程图”作为问题；应写“用户提交失败后回到哪里，是否需要重新校验”。

视觉再声明：

- `role`：overview、local 或 deep_dive；
- `coverage`：focused 或 complete；
- `delivery_role`：inline 或 zoomable；
- focused 子图引用的状态/迁移；
- 在正文宽度和放大视图中如何检查。

只有 `coverage=complete` 才要求覆盖完整模型；focused 只验证声明的子集。复杂全景默认 `delivery_role=zoomable`，不能成为正文唯一解释。

同一事实只在完整交互模型中保存一份规范化状态/迁移定义。页面总览、原型计划和执行包优先引用模型 ID、来源锚点与正文归宿，不复制整段状态文案；确需为读者改写时，只保存当前视图所需的短标签，避免四套内部文件成为四套事实副本。

#### 原型计划（按需）

存在截图、已确认设计、现有页面承接、多状态故事板或多个原型资产时，使用 `assets/prototype-plan-template.json` 记录：

- 产品语义充分度与视觉上下文充分度；
- 正式 PRD、设计、现状截图和参考图的证据角色；
- 每个 Surface 的区域、来源和设计复用策略；
- 每个输出回答的问题、状态/迁移范围、正文位置和交付角色。

截图观察必须区分 `observed`、`inferred` 和 `unknown`。只有正式 PRD 证据可以授权新的产品行为；截图不能单独授权交互故事板。

## 4. 两道门槛

### 门槛一：产品逻辑确认

以下内容稳定后才批量生成视觉资产：

- 本期范围与主任务；
- 页面/载体和主要状态；
- 入口、关键调用时点和页面迁移；
- 成功、失败、空态、已处理和资格拦截等适用出口；
- 异常恢复与再次进入规则；
- 视觉所需的文案和操作含义。

未通过时，只整理缺口和执行计划，返回 `pm-prd-write` 补齐产品事实；不能用假设原型掩盖缺口。

### 门槛二：增强或严格协作交付确认

以下全部通过才完成：

- 正文可以在不看完整规格时复述背景、问题、需求、方案和主线；
- 图型与阅读任务匹配，主流程和异常分支清楚；
- 页面清单无不可达状态、无缺失出口、无错误恢复；
- 高风险事实的正文、视觉和必要验收见证互不冲突；
- 图片、表格、链接、标题和正文在最终阅读视图中清晰；
- 主文档仍是传统 PRD，而不是内部执行说明、会议简报或页面画廊；
- 正文视觉在无需放大时可读；全景下钻在放大后可追踪；
- 规则变更后，所有受影响正文、图、页面和验收均已更新。
- 多轮迭代或已对外发布的资产，版本变更记录、原位徽标与实际改动一致，评审反馈均已按定位三元组登记并处置。

## 5. 增强路径的证据化执行顺序

```text
完整读取正式 PRD
→ 确定读者与协作任务
→ 锁定传统 PRD 主交付面和读者骨架
→ 提取主线和高风险事实
→ 建立页面—状态—操作—迁移模型
→ 判断原型输入充分度并按需建立原型计划
→ 建立评审问题与表达计划
→ 门槛一：产品逻辑确认
→ 生成总览/局部展示子图并实际查看
→ 编译传统 PRD并就近装配图文
→ 建立高风险语义见证
→ 运行阅读结构检查（审计模式再加跑 scripts/audit/ 检查器）
→ 查看最终渲染/目标平台
→ 门槛二：协作交付确认
```

不要跳过页面/状态清单直接批量生图；不要先排版完整文档再发现主线和范围错误。

## 6. 变更影响

收到规则变化时，先定位它影响的事实，再检查：

1. 背景/问题/需求是否改变；
2. 正文功能与规则；
3. 主流程或状态迁移；
4. 页面状态、操作与文案；
5. 原型/截图；
6. 验收与效果验证。

不能只修改用户指出的那一段。执行包中的 `facts`、`states` 和 `visuals` 用于列出受影响产物。

评审反馈进入变更流程前，先登记为**定位三元组**：资产 id（或正文锚点）+ 区域/节点定位 + 意见内容。定位方式遵守[视觉与原型](./视觉与原型.md) §7.5 的稳定定位协议，不接受"第三个状态的那个按钮"这类漂移引用；反馈没有定位时先补定位再处置，避免改错位置或返工后无法核对。资产经历多轮评审迭代时，改动落地同步执行 §7.6 的版本信号（原位徽标、旧值保留、版本变更记录），并先按升号判据决定本次改动升号还是合并进当前版本。

登记后的反馈按类型分类处置，处置方式由反馈类型决定，不由手感决定：

| 反馈类型 | 处置方式 | 约束 |
|---|---|---|
| 视觉微调（列宽、间距、密度） | 直接改 | 改完即贴出验证，不攒批 |
| 文案 / 术语 / 字段名 | 直接改，并同步更新术语口径 | 同一概念跨页面、跨资产同名，改一处要排查连带引用 |
| 交互逻辑（跳转、状态、操作） | 先与提问方对齐选项再改，不凭空猜 | 改变入口、状态、结果或恢复的，回到正式 PRD 主源确认后再落地 |
| 产品规则 / 范围 / 设计基线变化 | 不直接改；先讨论清楚，可能重做受影响模块 | 属于上游决策的返回 `pm-prd-write`，不在交付层补造规则 |

每次处置中暴露的"我以为可以"式误判（如替产品写了无来源文案、把推断当事实），记入本 skill 的常犯错清单并按仓库 ITERATION_GUIDE 回流沉淀，让教训在 skill 层累积而不只留在当次会话。

## 7. 检查清单

### 7.1 语义检查

#### 需求背景

- 是否写清角色、场景、目的、当前行为和现状数据；
- 是否只包含客观事实、证据、约束和已发生事件；
- 是否混入“体验差、能力不足”等问题判断或本期方案；
- 数据是否有口径、来源和时间，没有数据时是否说明缺失原因。

#### 需求问题

- 是否指出现状中具体哪个环节与预期不符；
- 是否能从背景事实推导，而不是新增无证据判断；
- 是否说明需求未满足、流程阻断或体验问题影响谁、范围和程度如何。

#### 需求目标

- 是否写清本需求希望改变的用户或业务状态；
- 目标是否从背景和问题推导，并能通过产品结果验证；
- 是否误写成新增页面、支持功能、开发上线或实施步骤；
- 没有可信基线时是否避免制造数值目标。

#### 需求范围

- 是否明确本期做什么、不做什么；
- 是否写清必要的端、角色、场景和版本边界；
- 是否混入研发任务或未确认的后续方案。

#### 方案与需求详情

- 产品方案是否用最短路径说明入口、关键动作与结果；
- 每个主要页面或任务是否写清入口、信息、操作、结果及必要状态/恢复；
- 页面内规则是否就近，跨功能规则是否确实影响两个以上模块；
- 是否混入 API 字段、队列、存储、算法等研发 spec。
- 详情标题是否直接说明“什么对象发生什么变化”；
- 界面需求是否把原型、信息项和对应逻辑就近编排，而不是让读者跨页找规则；
- 直接替换是否写清前后变化，条件交互是否补默认值/校验/反馈/生效，跨端状态是否补端差异/优先级/持久化/恢复。
- 界面变化是否实际承接了输入中的截图/设计，或在语义完整但无视觉上下文时为核心变化页生成了低保真；是否出现“源文档有图、成稿却纯文字”的断层。

#### 效果验证（若保留）

- 指标、计算方式、数据来源和验证用途是否清楚；
- 是否只保留真正需要上线后判断的结果、行为或护栏；
- 是否把研发验收用例误放在效果验证中。

### 7.2 章节取舍检查

- 需求目标是否描述可验证的用户或业务状态，而非功能产出或交付过程；
- 方案流程是否存在多角色/系统/时间交接，而不是简单步骤装饰；
- 场景拆分是否确有多用户、多场景或多套方案；
- 版本拆分是否每期都有独立价值，而不是开发排期；
- 产品动线是否存在入口、跳转、返回、取消、失败或重试变化；
- 信息结构图或原型是否承担页面空间和信息层级问题；
- 效果验证是否会用于上线后的继续、调整、补实验或止损判断；
- 所有不适用章节是否已直接删除，没有空标题或大段“不适用”。

### 7.3 同源检查

从正式 PRD 正向抽查：

1. 现状事实、主要问题、目标和范围均有正文归宿；
2. 每个 P0 功能在传统 PRD 中有正文归宿或明确来源下钻；
3. RULE、状态矩阵和数据口径中的高影响条件已回到相关页面/任务；
4. AC 暴露的关键异常、权限、兼容和恢复没有被压缩掉。

从传统 PRD 反向抽查至少 5 条高影响结论，优先选择权限、禁止结果、时间、数值、状态和数据口径；每条都应能在正式 PRD定位。无法定位的结论删除或返回上游确认。

### 7.4 信息分层检查

- 主文档是否仍是传统 PRD，而不是协作简报、执行报告、生成说明或研发清单；
- 第一屏是否先建立背景、问题和目标，再进入方案；
- 用户主线能否在不理解内部系统名、错误码或实现方式的情况下读懂；
- 必要的系统职责是否集中在产品方案的流程或职责表，而非散落全文；
- 接口字段、鉴权、幂等实现、并发方案、队列、存储、算法和日志结构是否已进入研发 spec；
- 是否用产品结果约束替代实现手段，例如“重复进入不能产生第二次有效结果”；
- 内部模型、执行包、来源 IDs、检查记录和生成术语是否完全退出正文。
- URL、query 参数、HTTP 状态码、Node、缓存键等实现表达是否已转换为用户入口、页面状态、操作和结果；确需保留的精确值是否集中到下钻而非散落正文。

### 7.5 编排与视觉检查

- 第一屏是否依次建立背景、问题和目标，而不是先摆方案或生成说明；
- 章节是否按需求结构裁剪，是否存在模板填空感；
- 同一事实是否在概览、规则和详情中反复扩写；
- 一个段落是否同时承担背景、问题、方案、异常和实现；
- 表格是否过宽且需要频繁横向扫描；
- Mermaid 是否先建模角色/状态/动作/结果，节点是否过多、分支是否有标签、失败是否有落点；
- 页面图是否标明现状、目标、结构示意或参考；
- 图片是否可打开、未裁切、文字可读且无敏感信息。
- 是否为简单需求强行增加流程图或信息结构图；验收标准可以很短，但不能缺失；
- 是否用“同原逻辑/保持一致”掩盖本次差异，而没有列清例外和变化。
- 每个视觉是否对应独立读者问题，并按顺序、交接、状态、空间、条件或层级关系选择了合适表达；
- 是否只在不同抽象层无法由一张图清楚承担时分层，且没有重复画同一逻辑；
- 详情是否按内聚的用户任务聚合，同一高风险事实是否只有一个主要正文归宿；
- 是否把完整状态模型直接渲染成正文巨图，或让一张图同时承担系统交接、用户动线、页面空间和完整状态覆盖；
- 总览图是否只建立全局心智，局部原型是否紧邻对应任务，完整全景是否在需要时作为可缩放下钻；
- 交互版是否区分 `coverage=focused` 的展示子图与 `coverage=complete` 的核查视图；
- 原型是否覆盖确认、处理中、成功/失败等真正改变用户操作和反馈的关键状态，而非只展示静态页面壳；
- 是否分别判断了产品语义和视觉上下文充分度，没有因“有截图”就补造隐藏交互；
- 已确认设计是否优先复用；现状截图和参考图是否明确标注角色；观察、推断和未知是否分开；
- 单页原型是否有清楚的主任务、信息层级、主次操作和就近反馈；故事板关键帧是否由状态变化决定并标明动作；
- 在正文实际宽度下，标题、节点、动作和状态差异是否无需放大即可读清；
- 在独立画板放大后，主线、回边、分支标签和异常归属是否仍可追踪；
- 页面交互总览中的页面卡片是否具有可识别的缩略界面结构；若只是圆角框加状态说明，必须降级命名为状态网络或改做真正页面卡片。
- 轻量需求是否被元数据、固定章节和重复表格扩写；若成稿明显长于输入，新增篇幅是否都在解决真实理解问题。
- 多条件联动决定界面状态的规则是否用三件套（逻辑表 + 测试用例表 + 静态示例）表达，测试用例是否枚举到多条件并存与边界、达到 QA 可直接使用的精度；没有用伪代码描述命中条件，也没有为演示硬做高成本联动交互。

### 7.6 版本与反馈定位检查

适用于多轮评审迭代或已对外发布的资产（启用条件见[视觉与原型](./视觉与原型.md) §7.5、§7.6）：

- 每条评审反馈是否已登记为"资产 id + 区域/节点定位 + 意见"三元组，没有使用会漂移的引用方式；
- 资产与状态故事是否有稳定 id，id 是否只增不改不复用；重复数据节点是否使用稳定 data-key 而非下标；
- 启用了批注覆盖层时，人的批注是否只在覆盖层文件中，重生成资产是否未覆写它；
- 版本升号是否符合判据（上一版已通知下游才升号），没有出现每次小改都升号或多轮改动无版本锚点；
- v0.2 起的改动是否有原位徽标（新增/修改/删除 + 版本号），修改与删除是否保留旧值对照；
- 版本变更记录是否独立成章、倒序、五列齐全（版本/时间/类型/涉及资产/摘要），摘要是否都是业务句子而非工程流水账；
- 评审版本号与静态资源工程修订号是否分离，工程修订号未混入版本变更记录；
- 范围裁剪是否用隐藏而非删除，且裁剪后不存在指向已隐藏内容的可见入口，也没有本轮内容因入口被隐藏而成孤儿；
- 评审反馈是否按 §6 的四类规程处置（微调与文案直接改、交互逻辑先对齐、规则与基线变化回上游），处置中暴露的误判是否已记入常犯错清单。

## 8. 人类阅读检查与无上下文读者验收

自动检查只能发现结构问题。作者先用下列问题检查成稿；严格验证时，再让没有本轮对话上下文的人只读传统 PRD并回答：

1. 当前谁在什么场景下做什么，客观事实和数据是什么；
2. 现状中哪个环节存在什么问题，影响谁；
3. 本需求希望改变什么用户或业务状态；
4. 本期做什么、不做什么，选择了什么总体方案；
5. 用户怎样完成主要任务，关键页面和结果是什么；
6. 哪些状态、权限、异常或时间会改变结果；
7. 若存在数据与效果验证，使用什么口径判断目标是否达到；
8. 完整验收或实现细节去哪里查。

记录每个问题是否答对、误解来自哪里、依赖了哪些未写明前提，以及需要作者口头补充什么。再让读者额外检查歧义、隐含假设、矛盾和来源下钻断点。任一答案依赖作者补充核心事实时，返回造成缺口的编译、架构、表达或装配阶段。

前六问需要作者口头补充主要产品事实时，文档不通过。第七问只在相关章节适用时回答；第八问可以下钻正式 PRD。

执行包必须区分 `reader_type=author` 的作者回读和 `reader_type=independent` 的独立读者测试。增强验证可以使用作者回读；严格验证必须使用没有本轮上下文的独立读者，不能把作者自问自答记录成独立证据。

### 8.1 对抗性自审（严格级可选）

检查清单是作者视角——查"我有没有做到"，查不出"我哪里想错了"。严格验证或高风险交付（重要评审、重复发布、大范围变更）可以追加一轮对抗性自审：让一个不带作者立场的审查者（独立会话或子代理）只读成稿，任务是**挑错而不是肯定**，专找：

- 难逆决策被隐含做掉而没有显式陈述（范围边界、状态口径、权限结论）；
- 结论没有锚定到正式 PRD 或真实证据；
- 该拍板处给了选项菜单，把决策推给读者；
- 明显的缺失决策（"那 X 情况下怎么办"）；
- 不改变协作判断的填充内容。

两条纪律：**非阻塞**——成稿先交付给用户读，自审并行进行，不让用户等它；**修复与上报分流**——明确的错误（无来源结论、断链、矛盾）直接修正，真正的判断分歧不静默拍板，列出来交回用户决定。自审后向用户简述改了什么、浮现了哪些待决项。

它成本不低（约翻倍验证开销），基础与增强路径默认不启用；它和独立读者测试互补：一个测可读性，一个测正确性，不互相替代。

## 9. 自动检查

基础路径可运行：

```bash
python3 scripts/check_reading_view.py \
  --profile traditional-prd \
  --document /absolute/path/to/traditional-prd.md \
  --source /absolute/path/to/formal-prd.md
```

脚本只发现结构、密度、断链和模板残留，不能替代语义、同源和真实阅读检查。普通单点文档不因没有执行包而失败。

增强路径使用 `--fail-on-warnings` 运行阅读视图检查：

```bash
python3 scripts/check_reading_view.py \
  --profile traditional-prd \
  --fail-on-warnings \
  --document /absolute/path/to/traditional-prd.md \
  --source /absolute/path/to/formal-prd.md
```

以下为**可选审计件**（严格发布、重复发布门禁或用户要求结构化证据时启用；默认与增强路径不强制）。执行包检查会联动交互模型与原型计划检查：

```bash
python3 scripts/audit/check_execution_pack.py \
  --pack /absolute/path/to/execution-pack.json

python3 scripts/audit/check_interaction_model.py \
  --model /absolute/path/to/interaction-model.json \
  --report /absolute/path/to/interaction-coverage.md
```

交互检查覆盖载体/页面、状态、可用操作、迁移、异步成功失败、可达性与视觉引用；它不能证明业务语义正确，仍需依据正式 PRD 完成人工正向与反向抽查。

审计模式下，复杂原型、截图承接或设计资产复用还应运行：

```bash
python3 scripts/audit/check_prototype_plan.py \
  --plan /absolute/path/to/prototype-plan.json
```

该检查阻止输入不足时生成完整交互、截图单独授权产品行为、已确认设计被无理由重画，以及输出与证据、Surface、状态或迁移断链；它不能替代实际查看原图、局部裁切、最终原型和发布后的正文。

飞书的日常发布只需回读正文并查看已发布视觉；严格飞书交付再读取[飞书发布与渲染](./飞书发布与渲染.md)的审计部分并运行：

```bash
python3 scripts/audit/check_feishu_delivery.py \
  --audit /absolute/path/to/feishu-delivery-audit.json
```

自动检查只能提示骨架缺失、内部术语、重复、密度和断链。图形是否选对、内容是否聚合、视觉是否在最终平台真正清楚，仍需要查看成品和读者测试。

## 10. 通过标准

- 主链完整：需求背景 → 需求目标 → 需求范围 → 产品方案 → 需求详情 → 验收标准；
- 需求目标不是功能产出或交付过程；数据与效果验证只在适用时出现；
- 主要产品行为与正式 PRD 同源；
- 非作者可以连续理解并开始第一次协作；
- 图、表、原型和文字各自承担不同问题；
- 文档没有内部工作过程、追溯外壳、空模板或 AI 总结腔。
- 执行路径的页面状态没有不可达或无出口，高风险规则在正文和视觉中均有一致归宿；最终资产已经实际查看，不以脚本退出码代替视觉验收。
- 严格验证时，无上下文读者测试已覆盖预设问题、歧义、隐含假设和矛盾；发现的问题已回到对应阶段修正。
