# PRD 模板

本模板默认用于标准版 PRD。它消费已经确认的产品需求定义，只摘要和追溯背景、目标、方向与一级范围，不重新做产品决策。章节数量保持稳定；复杂需求通过补充矩阵和子项增加深度，不再增加大量平级章节。

本模板同时服务两个目标：一是让需求、范围、流程、功能、规则和验收足够完备；二是让读者先理解整体路径和页面变化，再进入细节。产品动线和页面信息结构只在会影响体验评审或实现完整性的需求中展开，不为所有需求强制增加文档负担。

## 目录

0. 文档信息与一页结论
1. 决策依据
2. 方案总览、体验结构与原型
3. 交付范围与功能需求
4. 规则、数据与质量边界
5. 影响、依赖与发布
6. 验收与追溯
7. 效果验证
8. 风险、待确认项与附录

## 章节适用性

| 章节 | 级别 | 何时需要 | 不适用时如何处理 |
|---|---|---|---|
| 0. 文档信息与一页结论 | 必填 | 所有需求 | 不可省略，可按轻量版压缩 |
| 1. 决策依据 | 必填 | 所有需求 | 不可省略，只摘要已确认决策 |
| 2. 方案总览、体验结构与原型 | 条件必填 | 改流程、页面、交互、多角色或多系统协作 | 整章省略，在 0.1 写明原因；简单实现说明可放入功能明细 |
| 3. 交付范围与功能需求 | 必填 | 所有需求 | 不可省略 |
| 4. 规则、数据与质量边界 | 条件必填 | 新增或改变状态、权限、规则、数据、异常处理或非功能风险 | 整章省略，在 0.1 写明原因 |
| 5. 影响、依赖与发布 | 条件必填 | 跨模块 / 系统、旧版本、历史数据、依赖、灰度、迁移或特殊发布 | 整章省略；常规发布可在 0.1 简述 |
| 6. 验收与追溯 | 必填 | 所有需求 | 验收不可省略；单功能可不用完整追溯矩阵 |
| 7. 效果验证 | 条件必填 | 需要判断用户行为、业务结果、实验效果或护栏变化 | 省略并说明为什么只需研发验收，例如恢复既定行为的缺陷修复 |
| 8. 风险、待确认项与附录 | 可选 | 存在风险、假设、未决问题或补充材料 | 无内容时整章省略，资料可合并到 0.1 |

“不适用”和“信息缺失”不是一回事：应当适用但尚未拿到原型、规则、指标或上线结论时，必须保留对应章节并标记负责人、时间和是否阻塞。

## ID 与追溯规则

核心对象使用稳定 ID：目标 `OBJ-01`、场景 `SCN-01`、功能 `FR-01`、原型或设计 `UI-01`、规则 `RULE-01`、验收 `AC-01`、指标 `MET-01`。

涉及页面或流程时，可按需增加动线 `FLOW-01`、页面 `PAGE-01` 和信息结构 `IA-01`。推荐形成：`目标 → 场景 →（动线 / 页面 / 信息结构，按需）→ 功能需求 → 原型/设计（如涉及界面）→ 规则 → 验收 → 指标`。不要为了填满追溯链而虚构 ID。ID 一经评审使用，不因章节移动而重编号。

## 2. 方案总览、体验结构与原型

### 2.2 产品动线与页面影响（按需）

当用户需要跨页面完成任务，或入口、页面跳转、返回、失败、取消、重试发生变化时，补充本节。重点说明“谁为了什么，从哪里进入，经过哪些页面或状态，到达什么结果”。

| 动线 ID | 场景 ID | 入口 / 起点 | 用户目的与关键动作 | 页面 / 状态转移 | 关键分支 | 结果 / 出口 | 返回、失败、取消或重试 |
|---|---|---|---|---|---|---|---|
| FLOW-01 | SCN-01 | PAGE-01 或业务入口 |  |  |  |  |  |

页面动线、页面内交互和业务状态流可以分别表达；不要求每份 PRD 同时输出三张图，也不要求使用 Mermaid。表格或文本路径可作为主源，流程图仅用于帮助快速阅读。

### 2.3 页面信息结构（按需）

当新增页面、页面信息重组、核心信息前置 / 后置或页面状态变化会影响需求评审时，补充本节。先给出页面层级或结构摘要，再列关键区域和信息项，不重复原型已经清楚的视觉细节。

#### 页面结构摘要

```text
PAGE-01 页面名称
├── 核心信息区
├── 主任务 / 操作区
└── 辅助信息与状态区
```

| PAGE-01 | IA-01 |  |  | P0 / P1 |  |  |  |

| 资产 ID | 类型 | 精确链接 / 文件路径 / Frame | 版本或更新时间 | 状态 | 负责人 | 覆盖场景 / 页面 / 功能 |

| UI-01 | Figma / 原型 / 设计稿 / 流程图 / 截图 |  |  | 草稿 / 评审中 / 已确认 / 已废弃 |  | SCN-01 / FR-01 |

关联要求：

- 外部原型链接应定位到具体页面、Frame 或 Node，不只放项目首页。
- 仓库内文件使用可定位的相对路径；多页文件同时写页码、画板或节点名称。
- 原型尚未完成时写明负责人、预计时间和是否阻塞研发，不虚构链接。
- PRD 是页面逻辑结构、业务规则和验收的主源；已确认原型是视觉布局和交互表达的主源。两者冲突时记录待确认项，并更新其中一方后再确认。

## 4. 规则、数据与质量边界

只保留适用于本需求的表格；不适用时写明原因。三种以上角色、状态或条件组合优先使用矩阵。

### 4.1 业务规则

| 规则 ID | 条件 / 角色 / 当前状态 | 允许或禁止的动作 | 处理结果 / 后续状态 | 冲突优先级 | 异常处理 |
|---|---|---|---|---|---|

### 4.2 异常与边界

- 空状态、加载失败和重复提交：

### 4.3 数据与埋点

|---|---|---|---|---|---|

### 4.4 非功能与质量要求

### 6.1 端到端追溯矩阵

| 目标 ID | 场景 ID | 功能 ID | 原型 ID / 节点 | 规则 ID | 验收 ID | 状态 |
|---|---|---|---|---|---|---|

界面需求缺少已确认原型时，应在状态中标记是否阻塞；纯规则、接口或后台任务可将原型列写为“不适用”。涉及页面或动线时，可在矩阵中增加 `FLOW-xx`、`PAGE-xx`、`IA-xx` 列；轻量需求不必强行增加完整矩阵。

### 6.2 研发验收标准

#### AC-01 用例名称

- Given：前置角色、数据和状态。
- When：用户或系统执行的动作。
- Then：页面、交互、数据、状态和联动结果；必要时引用 UI-01 和 RULE-01。

至少覆盖主流程、关键状态、权限差异、异常失败、历史回归和跨模块联动。
