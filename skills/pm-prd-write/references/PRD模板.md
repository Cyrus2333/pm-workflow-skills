# PRD 模板

本模板默认用于标准版 PRD。它消费已经确认的产品需求定义，只摘要和追溯背景、目标、方向与一级范围，不重新做产品决策。章节数量保持稳定；复杂需求通过补充矩阵和子项增加深度，不再增加大量平级章节。内部 MVP、单页复杂状态、异步任务或跨系统能力必须进入组合输出结构判断；缺少按条件应填的评审简版、页面状态与操作矩阵、系统能力需求表、研发 spec 交接清单或验收矩阵时，必须说明省略原因。

本模板同时服务三个目标：一是让需求、范围、流程、功能、规则和验收足够完备；二是让读者先理解整体路径和页面变化，再进入细节；三是明确 PRD 与研发 spec 边界。产品动线和页面信息结构只在会影响体验评审或实现完整性的需求中展开，不为所有需求强制增加文档负担；接口、队列、存储、算法等只写到产品能力和验收结果，具体实现进入 spec 交接清单。不要因为不写 spec 细节就把 PRD 压缩成方向、范围和功能清单；用户可见状态、操作限制、业务规则、异常兜底和验收标准仍必须具体。

**推荐阅读顺序：**先读第 0 章的一页结论，再读第 2 章的方案闭环、产品动线和页面信息结构，最后进入第 3、4、6 章核对具体行为、规则和验收。每个章节先写“本节结论”，再写表格或清单；表格承载事实，不能代替对行为的解释。

## 目录

0. 文档信息与一页结论
1. 决策依据
2. 方案总览、体验结构与原型
3. 交付范围与功能需求
4. 规则、数据与质量边界
5. 影响、依赖与发布
6. 验收与追溯
7. 效果验证
8. 风险、待确认项、研发 spec 交接与附录

## 章节适用性

| 章节 | 级别 | 何时需要 | 不适用时如何处理 |
|---|---|---|---|
| 0. 文档信息与一页结论 | 必填 | 所有需求 | 不可省略，可按轻量版压缩 |
| 1. 决策依据 | 必填 | 所有需求 | 不可省略，只摘要已确认决策 |
| 2. 方案总览、体验结构与原型 | 条件必填 | 改流程、页面、交互、多角色或多系统协作 | 整章省略，在 0.1 写明原因；简单实现说明可放入功能明细 |
| 3. 交付范围与功能需求 | 必填 | 所有需求 | 不可省略 |
| 4. 规则、数据与质量边界 | 条件必填 | 新增或改变状态、权限、规则、数据、异常处理或非功能风险 | 整章省略，在 0.1 写明原因 |
| 5. 影响、依赖与发布 | 条件必填 | 跨模块 / 系统、旧版本、历史数据、依赖、灰度、迁移或特殊发布 | 整章省略；常规发布可在 0.1 简述 |
| 6. 验收与追溯 | 必填 | 所有需求 | 验收不可省略；单功能可不用完整追溯矩阵 |
| 7. 效果验证 | 条件必填 | 需要判断用户行为、业务结果、实验效果或护栏变化 | 省略并说明为什么只需研发验收，例如恢复既定行为的缺陷修复 |
| 8. 风险、待确认项、研发 spec 交接与附录 | 可选 | 存在风险、假设、未决问题、待研发 spec 补齐事项或补充材料 | 无内容时整章省略，资料可合并到 0.1；内部 MVP 或跨系统能力建议保留 spec 交接清单 |

“不适用”和“信息缺失”不是一回事：应当适用但尚未拿到原型、规则、指标或上线结论时，必须保留对应章节并标记负责人、时间和是否阻塞。

## 组合输出结构（内部 MVP / 单页复杂状态 / 异步 / 跨系统判断）

当需求属于内部 MVP、异步任务、跨系统能力，或属于“单页多信息区且涉及状态流转、主操作、权限差异、异步结果、跨系统能力或关键异常兜底”时，必须进入组合结构判断；按下表决定哪些模块必填：

| 模块 | 放置位置 | 省略规则 |
|---|---|---|
| 评审简版 | 标准 PRD 前 | 内部 MVP 或评审会议不得省略；若用户只要正式 PRD，在 0.1 说明 |
| 标准 PRD | 第 0-8 章 | 默认不得省略 |
| 页面状态与操作矩阵 | 第 4 章或功能明细内 | 有状态流转、按钮可用性、权限或失败态时不得省略 |
| 系统能力需求表 | 第 3 章功能清单后 | 涉及接口、异步任务、第三方、存储、算法或跨系统时不得省略 |
| 研发 spec 交接清单 | 第 8 章 | 涉及接口 / 任务 / 存储 / 算法 / 第三方能力时不得省略 |
| 验收矩阵 | 第 6 章 | 标准 PRD 必须；轻量单功能可压缩但要说明 |

边界说明：页面状态与操作矩阵是跨功能、跨信息区的总览主源；功能明细中的条件分支只解释该功能内部行为，不要在两个位置重复粘贴同一组状态分支。系统能力需求表回答“产品需要系统做到什么、失败时用户看到什么”；研发 spec 交接清单回答“研发还要定义哪些接口、任务、存储、算法和监控细节”，不要把同一内容复制两遍。

## ID 与追溯规则

核心对象使用稳定 ID：目标 `OBJ-01`、场景 `SCN-01`、功能 `FR-01`、原型或设计 `UI-01`、规则 `RULE-01`、验收 `AC-01`、指标 `MET-01`。

涉及页面或流程时，可按需增加动线 `FLOW-01`、页面 `PAGE-01` 和信息结构 `IA-01`。Page 表示路由或页面容器；Section / 模块 / 信息区用 IA 表达；Flow 表示用户路径。单页多模块项目只建立一个 PAGE，再列多个 IA / Section，避免把模块误拆成多个页面。推荐形成：`目标 → 场景 →（动线 / 页面 / 信息结构，按需）→ 功能需求 → 原型/设计（如涉及界面）→ 规则 → 验收 → 指标`。不要为了填满追溯链而虚构 ID。ID 一经评审使用，不因章节移动而重编号。

## 评审简版（内部 MVP / 评审会议按需输出）

控制在 1-2 页，面向快速对齐，不复制完整 PRD。建议包含：

- 一句话方案：说明对象、场景、核心能力和结果。
- 目标与非目标：保留关键边界，避免反复扩写。
- 体验结构：明确是几个页面、页面内有哪些信息区 / 模块、主链路和删除 / 失败等关键分支。
- 核心规则：只列会影响用户体验或验收的规则。
- 验收标准：列 MVP 成功必须满足的端到端结果。
- 待研发 spec 补齐：列接口、队列、存储、算法、第三方能力等实现事项，不在简版中展开字段和方案。
- 省略说明：若组合输出结构中的必填模块被裁剪，说明省略原因和影响。

## 2. 方案总览、体验结构与原型

### 2.1 方案闭环与目标流程

用一段话先说明方案如何从入口到结果形成闭环，再用表格核对每一步。每一行都写清楚谁在什么时间点接收什么输入、完成什么动作、得到什么反馈，以及下一步或终止条件；不要只写“处理数据”“进入下一步”。如果存在失败、返回、取消、重试或状态过期，至少在对应行写出用户回到哪里、看到什么、能否继续。

| 场景 ID | 阶段 / 时间点 | 角色 / 系统 | 前置输入 | 动作 | 系统反馈 | 下一步 / 临界点 |
|---|---|---|---|---|---|---|

### 2.2 产品动线与页面影响（按需）

当用户需要跨页面完成任务，或入口、页面跳转、返回、失败、取消、重试发生变化时，补充本节。重点说明“谁为了什么，从哪里进入，经过哪些页面或状态，到达什么结果”。如果是单页内完成任务，应明确写“单页内状态 / 信息区切换”，不要写成多页面跳转。

| 动线 ID | 场景 ID | 入口 / 起点 | 用户目的与关键动作 | 页面 / 状态转移 | 关键分支 | 结果 / 出口 | 返回、失败、取消或重试 |
|---|---|---|---|---|---|---|---|
| FLOW-01 | SCN-01 | PAGE-01 或业务入口 |  |  |  |  |  |

页面动线、页面内交互和业务状态流可以分别表达；不要求每份 PRD 同时输出三张图，也不要求使用 Mermaid。表格或文本路径可作为主源，流程图仅用于帮助快速阅读。页面转移不要只写页面名称，要说明触发动作、离开前状态、到达后用户要完成的任务，以及失败或返回后的落点。单页多信息区场景只建一个 PAGE，区块和状态变化放入 IA 或状态矩阵。

### 3.3 功能需求明细

本节是研发、测试和产品复核的共同规格源。先写行为，再挂 ID；不能只列字段、枚举和引用关系。功能项按“用户要完成的一个结果”组织，不按接口字段或单个状态机械拆分。读完单个功能后，读者应能回答：谁在什么条件下触发、页面和系统分别做什么、不同条件下结果是什么、失败后如何恢复、哪些行为保持不变、如何验收。

**核心功能详写要求**

- P0 功能不得只写一段摘要或一句“支持某能力”；必须展开为“需求结论、行为说明、条件与分支、异常与恢复、保持不变与边界、追溯”。
- 若 P0 功能没有复杂分支，也要写清触发前提、页面表现、操作可用性、系统结果、下一状态和验收关联。
- P1 / P2 功能可以按风险合并，但不能省略会影响验收的状态、权限、异常和恢复路径。
- 评审简版可以压缩功能明细；标准 PRD 和示例 PRD 必须体现可供研发、测试和产品逐条评审的产品行为规格。

PRD 中的接口 / 系统能力写法：写“页面需要获取活动详情”“提交后创建或替换有效投稿”“删除自己的投稿后软删除并触发重新合成”“页面查询合成状态并展示最新作品”。不要写 API 路径、HTTP 方法、请求 / 响应字段、错误码、微信 serverId 下载、转码混音、队列、存储路径、重试超时等；这些放入 8.2 研发 spec 交接清单。

正例：PRD 不写 API 字段，但要写“用户点击提交后，系统创建或替换有效投稿，投稿池展示我的记录，最新作品进入合成中；提交失败时保留本地录音并允许重试”。这类内容属于产品行为和验收结果，不能因 spec 边界而省略。

#### FR-01 功能名称

**需求结论**

用 2 至 4 句完整句子说明实现后的行为。至少包含角色、场景、触发、核心变化和最终结果。不要写成“前置条件：已登录”“系统处理：查询状态”这类字段名加短语。

**行为说明**

1. **触发与前提：**谁在什么页面或业务环节执行什么动作；必须满足哪些登录、权限、数据和业务状态条件；不满足时进入哪个明确分支。
2. **用户可见行为：**页面新增、删除或改变什么；内容出现在哪里、默认展示什么、哪些操作可用；操作后用户立即看到什么反馈。
3. **系统与数据行为：**系统根据哪些已确认信息判断；何时读取、计算、保存或刷新；结果如何提供给页面和后续流程；是否产生状态或数据副作用。只写能力和产品结果，不写接口字段、存储路径或算法实现。
4. **结果与后续路径：**成功后进入什么页面或状态；失败后停留在哪里、展示什么、能否重试；返回或取消时是否保留已输入内容。

**条件与分支**（存在多个角色、状态或条件组合时使用）

| 进入条件 | 用户看到什么 | 可执行操作 | 系统处理与数据结果 | 后续页面 / 状态 | 优先级或冲突规则 |
|---|---|---|---|---|---|
|  |  |  |  |  |  |

每行必须表达一个完整分支，不能写“同原逻辑”“正常展示”“按情况处理”。至少写出进入条件、用户看到的内容或状态、是否可操作、操作后结果和下一步。需要复用既有行为时，写明可定位来源，以及本次要求保持不变的具体表现。

**异常与恢复**（只写本功能可能发生且会影响用户或数据的异常）

| 异常条件 | 用户反馈 | 系统 / 数据处理 | 是否可重试及方式 | 记录与告警 |
|---|---|---|---|---|
|  |  |  |  |  |

**保持不变与边界**

- 明确本次不改变的页面、规则、数据和流程；
- 说明功能不适用的角色、端、业务类型或历史数据；
- 若存在待确认项，写明负责人、最晚时间和阻塞影响，不在正文中假装已经确认。

**追溯**

- 对应目标 / 场景：OBJ-01 / SCN-01；
- 所属页面 / 信息结构（如适用）：PAGE-01 / IA-01；

- 关联规则：RULE-01；
- 对应验收：AC-01、AC-02。

| 信息结构 ID | 元素 | 内容与数据来源 | 默认状态 | 展示条件 | 可操作条件 | 操作结果 | 校验 / 报错 |
|---|---|---|---|---|---|---|---|

#### 表达粒度示例

- **不合格：**“系统根据用户状态返回展示状态，异常时兜底。”读者不知道何时判断、有哪些输入、页面怎么表现、兜底是什么。
- **合格：**“登录用户每次打开详情页时，服务端根据活动阶段、成员身份和报名状态返回唯一展示状态；客户端只负责按状态渲染，不自行推断资格。身份无法确认时页面不展示‘可报名’，而是显示‘暂时无法确认你的报名资格，请刷新后重试’，并保留刷新入口；用户点击报名时仍由报名接口重新校验，失败时留在详情页展示具体原因并刷新状态。”
- **拆分原则：**“生成状态”“展示文案”“点击报名”如果共同决定用户是否能完成报名，应在同一功能链路中说明；只有埋点有独立触发、参数和验收目标时，才单列为数据需求。
- **一句话需求反例：**“用户可以提交录音，提交后进入投稿池并触发合成。”这只说明了能力名，缺少前提、按钮状态、防重复、成功反馈、失败恢复、替换规则和验收关联。
- **示范级表达方向：**“用户在完成录音并进入待试听状态后，可以点击提交。点击后按钮进入提交中并禁止重复点击；提交成功时，本次录音成为该用户在当前活动下唯一有效投稿，投稿池立即展示‘我的投稿’，最新作品区进入合成中；提交失败时保留本地试听结果，按钮恢复可点击，并提示失败原因或重试建议。若用户此前已有有效投稿，本次提交替换旧投稿，旧投稿不再参与下一版合成。”
