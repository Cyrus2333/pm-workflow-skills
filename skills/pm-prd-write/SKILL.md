# pm-prd-write

把已确认的产品决策展开成可实现、可测试、可上线和可验证的交付规格。

## 优先读取

- 既有规则、指标、角色关系或结算改造时，先读[需求迭代闭环与收尾协议](../../shared-references/需求迭代闭环与收尾协议.md)；普通页面或文案需求不必展开。

1. [PRD 模板](./references/PRD模板.md)

## 定稿前的方案重评估门禁

当输入需求经历多轮讨论，或用户质疑方案复杂度、源头规则、历史迁移、冻结时点、结算口径时，PRD 不应直接继续堆叠章节。定稿前必须先完成一次“源头规则 → 业务不变量 → 方案复杂度”的复核：

- 对照最新需求定义的迭代版本与决策台账，确认 PRD 引用的是 active 版本；
- 逐项检查锁定时点、归属来源、重算 / 不重算、历史边界、角色权限和失败语义；
- 说明哪些复杂度来自不可改变的业务不变量，哪些可以通过收敛源头规则消除；
- 对新事实源、读模型、迁移、双写、异步、事务和补偿，分别说明为什么需要、替代方案为何不采用、失败时如何降级；
- 如果上层规则发生变化，停写受影响章节，标记旧 PRD / Spec / 验收为过期，回退 `pm-requirement-define` 与 `pm-requirement-grade`。

PRD 开始实现前应输出一张“定稿检查卡”：决策版本、分级版本、受影响产物、技术预验证结论、尚未验证的假设和重新审查触发条件。这样可以避免把“文档写完”误认为“方案已经稳定”。

## 工作边界

负责：

- 在已确认需求定义和分级结论内，把一级产品范围拆成版本、页面、模块、流程和功能清单
- 在适用时补充产品动线、页面影响和页面信息结构，不把它们强行套用到纯后端或低风险修改
- 区分 Page（路由或单页容器）、Section / 模块 / 信息区、Flow（用户路径）和 IA（信息结构），避免把单页内多个区块误写成多个页面
- 只在 PRD 中定义接口或系统“能力要求、用户可见结果和验收口径”，把接口字段、队列、存储、算法等实现细节交给研发 spec
- 展开角色、状态、权限、规则、异常、数据和跨模块联动
- 定义历史兼容、灰度、迁移、回滚、监控和运营准备
- 关联已有原型、设计文件和具体 Frame / 节点，建立功能与验收追溯
- 对涉及页面体验的需求，形成原型范围与页面状态规划，作为 `pm-prd-html` 的输入；只定义产品逻辑和视觉约束，不在本 skill 中生成 SVG
- 编写研发验收用例和可执行的效果验证方案

不负责：

- 重新证明需求是否值得做
- 重新定义目标或发散新的产品方向
- 在没有决策记录或分级结论时擅自改变一级范围、重大取舍和交付门槛
- 在上游规则或范围已变化时继续沿用旧版本 PRD，不做失效标记和回退对账
- 规定 API 路径、HTTP 方法、请求 / 响应字段、错误码、幂等实现、任务队列、存储路径、转码参数、混音算法、重试超时等研发 spec 细节

## PRD 与研发 spec 边界

硬原则：PRD 只写“系统需要具备什么能力、用户会看到什么结果、什么算验收通过”；如果内容主要影响接口字段、技术选型、任务队列、存储或算法实现，标记为“交给研发 spec”，不要强行写进 PRD。

| 内容类型 | PRD 写到什么程度 | 交给研发 spec 的内容 |
|---|---|---|
| 页面结构与信息区 | 页面 / 单页容器、模块目的、关键元素、展示条件、用户可见状态 | 前端组件拆分、代码结构、样式实现细节 |
| 业务规则与状态 | 谁在什么条件下能做什么、结果和下一状态、冲突优先级 | 状态枚举命名、数据库状态值、事务和锁实现 |
| 接口 / 系统能力 | 页面需要获取 / 提交 / 删除 / 查询 / 触发什么能力，以及成功失败时的产品结果 | API 路径、HTTP 方法、请求响应字段、错误码、鉴权中间件、幂等技术方案 |
| 异步任务 / 算法 / 存储 | 用户可感知的任务状态、等待提示、失败兜底、验收结果 | 队列选型、重试超时、存储路径、文件命名、转码参数、算法实现 |
| 验收标准 | Given / When / Then 的用户可见表现、系统状态和业务结果 | 单元测试设计、接口契约测试细节、压测脚本 |

只要影响用户体验、业务规则或验收结果，就写进 PRD；只影响实现方式且不改变产品结果，就列入研发 spec 交接清单。若不确定是否属于产品规则，优先提出少量澄清问题，或标为待确认，不自行发散。

不要因为区分 PRD/spec 边界而过度压缩 PRD。PRD 不写接口字段和算法细节，但仍必须写清用户可见状态、操作限制、业务规则、异常兜底、系统能力结果和验收标准。正例：PRD 不写 API 字段，但要写“用户点击提交后，系统创建或替换有效投稿，投稿池展示我的记录，最新作品进入合成中；提交失败时保留本地录音并允许重试”。

## 输入契约

开始前至少取得：

- 文档用途与读者：标准 PRD、评审简版、研发 spec 交接清单，或内部 MVP 快速评审；未说明时默认标准 PRD，内部 MVP / 单页多信息区 / 异步任务 / 跨系统能力默认使用组合输出结构
- 已确认的问题、证据和影响对象
- 目标、非目标和方向级成功假设
- 推荐方向、选择依据和重大取舍
- 一级范围、主要角色和重大约束
- 已知主要入口、用户主任务和关键路径（如已有）
- `pm-requirement-grade` 的建议等级、红线命中、AI Coding 结论、PRD 必填重点、研发 spec / QA / 灰度 / 回滚 / 上线观察要求
- 需要 PRD 深入的状态、权限、规则、联动、数据或兼容维度
- 已有原型、设计文件或交互说明；没有时需确认是否适用、由谁补充以及是否阻塞
- 对需要原型的需求，确认页面 × 状态、每个状态的进入条件、展示信息、主要动作、系统结果、下一状态、视觉差异和参考资产；这些内容由本 skill 梳理，最终 SVG 由 `pm-prd-html` 生成
- 对单页多信息区需求，额外确认共享页面骨架：哪些信息区在所有状态保持、哪些信息区随状态变化、哪些信息区按条件出现、主操作区如何变化；原型不能只画状态差异而省略共享信息区
- 如果交付目标是“设计前即可评估页面效果”，额外建立页面内容契约：逐项列出所有用户可见静态文案、动态字段、状态标签、按钮、placeholder、空态、错误和操作反馈，并写清展示条件、缺省、长度 / 密度约束、原型关联和待确认责任；不要把“详见设计稿”作为内容主源
- 对移动端原型，额外确认端类型与逻辑视窗、页面是单屏还是可滚动长页、固定 / 吸底 / 吸顶区域、各状态的用户视口锚点、信息密度与可访问性约束；缺少既有页面或组件参考时标记待确认，不把“整页塞进一屏”当作默认约束
- 对需要 UX 级别输出的需求，额外确认原型档位（`ux-prototype` / `wireframe`）、内容 / 布局 / 交互 / 组件真实性要求、代表性数据、设计系统或中性视觉基线、页面 Schema 和静态 HTML / SVG 交付要求；缺失项必须进入 `prototypeReadiness`，不得等到 HTML 阶段猜测
- 对需要交给 UI 设计的需求，额外输出组件目录、状态变体、Token / 设计资产来源、页面节点与内容 ID 约定，以及哪些内容已确认、哪些仍不得作为设计基线
- 当 `pm-requirement-grade` 标记体验交付复杂度为“复杂”，读取其必备中间层清单：多页面补页面地图与导航契约；独立状态域补状态架构；复杂组件补组件行为表；多端补端与布局矩阵；状态组合较多补原型覆盖计划；命中内容完整型 UX 原型时补页面内容契约与内容覆盖检查。统一术语、字段和质量门槛参见[页面内容契约与 UX 原型](../../shared-references/页面内容契约与UX原型.md)

如果需求定义和分级结论未以独立文档提供，但用户已经明确表达，可先整理为输入摘要和分级待确认项再继续。若仍需比较方向、改变目标、调整业务原则或决定一级范围，转 `pm-requirement-define`；若缺口会改变交付等级、AI Coding 边界或评审门槛，先转 `pm-requirement-grade`。

PRD 编写过程中发现已确认方向与项目事实冲突时，不擅自重做产品决策。明确冲突、影响和待决策项，再返回 `pm-requirement-define`；发现红线或风险等级变化时返回 `pm-requirement-grade` 重新定级。

## 选择输出形态与文档级别

默认输出“标准版 PRD”。根据复杂度调整篇幅，但不得牺牲逻辑闭环。内部 MVP、单页多信息区、异步任务、跨系统能力、评审会议或快速对齐场景，必须进入“组合输出结构”判断；按下表决定哪些模块必填。用户明确只要其中一种时可以裁剪，但必须说明被省略内容和原因。

### 内部 MVP / 单页 / 异步 / 跨系统的组合输出结构

当需求属于内部 MVP、异步任务、跨系统能力，或属于“单页多信息区且涉及状态流转、主操作、权限差异、异步结果、跨系统能力或关键异常兜底”时，必须进入组合结构判断；按下表决定哪些模块必填。缺少应填模块时，必须在第 0 章说明省略原因：

| 模块 | 何时必须 | 目的 |
|---|---|---|
| 评审简版 | 内部 MVP 或评审会议必须 | 让产品、业务、研发、测试快速确认目标、范围、页面结构、关键规则和验收底线 |
| 标准 PRD | 默认必须 | 承载完整产品行为规格、规则、边界、验收和追溯 |
| 页面状态与操作矩阵 | 有状态流转、按钮可用性、失败态或权限差异时必须 | 说明不同状态下用户看到什么、能做什么、系统结果和下一状态 |
| 系统能力需求表 | 涉及接口、异步任务、第三方能力、存储、算法或跨系统协作时必须 | 从产品角度列明页面需要哪些系统能力、触发时机、用户可见结果和失败兜底 |
| 研发 spec 交接清单 | 涉及接口 / 任务 / 存储 / 算法 / 第三方能力时必须 | 明确哪些实现细节交给 spec，避免 PRD 误写字段或算法 |
| 验收矩阵 | 标准版 PRD 必须；多功能 / 多规则时必须完整 | 建立目标、场景、功能、页面 / 信息区、规则和验收的追溯关系 |
| 原型范围与页面状态规划 | 涉及新页面、页面迁移、复杂交互或多个用户可见状态时必须 | 说明哪些页面 × 状态需要可视化，以及原型需要表达的用户可见信息、主要动作和视觉约束；不重复功能明细和规则矩阵 |

边界说明：页面状态与操作矩阵是跨功能、跨信息区的总览主源；功能明细中的条件分支只解释该功能内部行为，不要在两个位置重复粘贴同一组状态分支。系统能力需求表回答“产品需要系统做到什么、失败时用户看到什么”；研发 spec 交接清单回答“研发还要定义哪些接口、任务、存储、算法和监控细节”，不要把同一内容复制两遍。

### 评审简版

用于产品、业务、研发、测试快速过目，控制在 1-2 页内。只保留：一句话方案、目标与非目标、一个页面还是多个页面、页面内信息区、主链路、关键状态、核心规则、验收标准、待决策 / 待 spec 补齐事项。不要复制完整 PRD 的全部表格。

### 研发 spec 交接清单

列出 PRD 已确认的产品能力，以及必须由研发方案继续补齐的实现事项。至少区分：当前不阻塞产品评审但阻塞实现的事项、需要技术预验证的前置项、接口 / 队列 / 存储 / 算法 / 第三方能力待定项。不要在 PRD 正文里用推测字段替代 spec。


### 轻量版

适用于局部文案、展示或单页面低风险调整，且不涉及新角色、规则、状态流转和历史数据。

可以合并章节，但必须保留：问题、目标、范围、具体变化、边界、研发验收，以及指标不适用的说明。

### 标准版

适用于普通功能、单条完整流程或少量跨模块联动。完整覆盖模板核心章节，是默认级别。

### 完整版

出现以下任一情况时使用：

- 多角色、多场景或多端
- 业务规则、状态机、权限或数据口径变化
- 跨系统联动、历史数据迁移或灰度发布
- 需要版本拆分、复杂上线或效果复盘

三种级别沿用同一套主章节：轻量版可合并不适用的子项，完整版通过状态、权限、规则、追溯和发布矩阵增加深度，不额外堆叠平级章节。

## 章节适用性与裁剪

模板是覆盖面清单，不是要求每份 PRD 填满所有章节。

- 核心必填：`0 文档信息与一页结论`、`1 决策依据`、`3 交付范围与功能需求`、`6 验收与追溯`
- 条件必填：`2 方案总览、体验结构与原型`、`4 规则、数据与质量边界`、`5 影响、依赖与发布`、`7 效果验证`
- 可选：`8 风险、待确认项、研发 spec 交接与附录`

条件章节的触发规则以模板中的适用性表为准。裁剪时遵守：

- 真正不适用的章节可以整体省略，并在第 0 章写明“省略章节及原因”
- 只要涉及新页面、页面跳转、入口变化、页面信息重组或关键状态变化，`2.1` 和 `2.2` 应保留；纯后端或不影响用户路径的修改可说明“产品动线和信息结构不变”
- 当用户说明“单页”“一个页面里几个区块”“模块化布局”时，`PAGE` 只记录单页容器，区块用 `IA` / Section 表达，不把章节或模块标题误写为多个页面
- 应当适用但信息缺失时，不得省略；标记待确认、负责人、时间和是否阻塞
- 不输出空标题、空表格或大段“不适用”，也不为了保持完整而虚构内容
- 核心章节可以按需求复杂度压缩，但问题—范围—功能—验收链不能断
- 单一轻量需求可在功能明细内直接关联验收；多功能、多原型或复杂规则需求使用完整追溯矩阵

## 两层文档结构

### 决策记录层

为了让 PRD 自包含，摘要记录已经确认的：

- 背景事实和问题
- 目标、非目标和成功假设
- 推荐方向、选择依据和重大取舍
- 一级范围和重大约束

这里负责“引用、固化和追溯”产品决策，不重新发散方案。若必须改变结论，应生成新的决策记录后再继续 PRD。

### 体验与研发交付层

回答：

- 用户从哪里进入、经过哪些页面或状态、如何到达结果
- 关键页面需要呈现哪些信息，以及信息之间如何组织
- 具体改哪些页面、模块、流程、规则和数据
- 不同角色、状态、权限和异常条件下如何表现
- 影响哪些现有能力和历史逻辑
- 如何发布、兼容、回滚和验收
- 每个界面需求对应哪个原型或设计节点，以及原型当前是否已确认
- 哪些系统能力从产品结果上必须具备，以及哪些研发 spec 事项需要后续补齐、哪些会阻塞实现但不阻塞产品评审

## 编写规则

### 1. 产品决策必须可追溯但不重复执行

- 背景、问题、目标和方案结论注明来源或关联需求定义
- 引用上游已经记录的推荐方向、选择依据和未选方案；上游未记录时不在 PRD 中补做方案比较
- 不为了填充 PRD 重新生成不同方案或改变一级范围
- 无法确认的内容标记为“待确认”或“假设”

### 2. 使用现状与目标对照

重要变化优先写成：

| 维度 | 当前状态 | 目标状态 | 影响对象 |
|---|---|---|---|

避免只写“优化体验”“支持某能力”“调整一下”等不可验收描述。

### 3. 体验结构要能独立评审

- 页面或流程变化时，先用简洁的产品动线说明入口、主任务、页面 / 状态转移、关键分支和结果；
- 对受影响页面说明页面目的、主要信息区、主操作和必要状态；
- 严格区分 Page（路由或页面容器）、Section / 模块 / 信息区（页面内分区）、Flow（用户路径）和 IA（信息结构）；单页多模块项目只建一个 PAGE，再列多个 IA / Section；
- 方案流程、产品动线和业务状态流可以分别表达，不强行合成一张复杂图；
- 表格是事实主源，流程图只用于帮助快速理解；没有合适的图形能力时，使用表格或文本路径即可；
- 信息结构不需要写 SVG 坐标或前端 CSS，但页面需求必须完整列出影响页面理解、操作和效果评估的用户可见内容；静态标题、按钮、placeholder、状态标签、空态、错误和操作反馈不能因为“原型会画”而失去主源；
- 需要 UX 原型时，必须同时给出页面 Schema、组件目录、状态变体、代表性数据、移动端视口契约和设计资产 / 中性视觉基线；
- 目标是让读者判断路径是否闭环、页面是否覆盖、信息是否缺失，并让 UX 原型在设计前验证内容层级、首屏、密度、组件形态和状态收口，而不是用 PRD 替代最终视觉设计。

### 3.1 先讲清楚，再展开细节

PRD 按“结论 → 用户路径 → 页面与信息结构 → 功能行为 → 规则与异常 → 验收”的顺序组织信息。每个章节先用一段话说明本节结论，再用表格或列表承载可核对的细节；表格后补一句结论，避免读者只看到碎片而需要自己拼装。

控制冗余：关键边界可以在一页结论、范围和非目标中适度重复，但同一结论不应在多个章节用不同措辞反复扩写；技术细节未定时统一写“交给研发 spec”，不要在风险、依赖、功能和验收中绕着重复。

功能需求按用户可感知的结果拆分，而不是按接口字段、状态枚举或单个埋点机械拆分。一个功能如果包含多个连续步骤，应放在同一个需求项中说明完整链路；只有当它有独立的实现边界、验收方式或负责人时，才单独拆成需求项。

P0 核心功能不得只写摘要段落或一句话需求。标准版 PRD 中，所有 P0 功能都要写清“触发与前提—用户可见行为—系统与数据结果—条件分支—异常恢复—保持不变与边界—验收追溯”；P1 / P2 可以按风险合并，但不能省略影响验收的状态和失败路径。评审简版可以压缩，正式示例和标准 PRD 必须体现可逐条评审的产品行为规格。

已确认、假设、待确认和不适用必须使用明确标签区分。不能用“通常”“相关”“正常”“处理一下”等概括性词语隐藏决策；如果业务确实未决定，应写出缺口、负责人、最晚确认时间和阻塞影响。

### 3.2 规则变更、结算时序与历史兼容（命中时必写）

当 PRD 修改已有规则、角色归属、派生指标、等级 / 权益、批量结算或状态流时，不能只写目标规则；必须将“旧系统如何变成新系统”写成可实现、可测试、可回溯的规格。至少包含：

1. **规则变更台账**：旧规则、新规则、明确不变项、生效范围、历史数据处理和决策来源；
2. **影响地图**：用户入口与页面、关系 / 状态写入、实时同步、定时任务、批量结算、后台 / 运营、测试 / 观测、稳定文档和发布动作；
3. **时序与归属表**：事实发生点、正式生效点、冻结点、冻结前后关系变更、结果变化触发的重算，以及迟到数据如何处理；
4. **幂等与失败恢复**：重复触发、并发、任务重试、部分成功、积压记录、续跑 / 补偿和排障信息；
5. **历史边界**：仅作用于新事件、回溯旧数据，还是新旧规则分界处理；如需回溯，写明迁移 / 补算范围、校验、回滚和验收证据；
6. **多角色去重**：同一主体在同一事件承担多个角色时，明确业务指标是否只计一次、角色审计是否保留。

推荐先确定“归属 / 快照”，再计算“结果指标”：关系变更通常更新待冻结归属；活动结果、评价或审核结果变化才重算已经确认归属主体的派生指标。若页面展示临时预览，必须明确它不写入正式累计、不参与等级 / 权益 / 结算，除非需求明确另有规则。

这一节不是让 PRD 代替研发 spec。接口、集合、索引、队列和具体算法仍交给 spec；PRD 只规定产品必须可观察、可恢复、可验收的结果。

### 3.3 页面内容契约与内容完整性

当需求命中页面改版、新页面、单页多信息区、多个状态域，或用户要求原型可直接评估页面效果时，页面信息结构之后必须增加“页面内容契约”。它不是视觉稿，也不是接口字段表，而是页面用户可见信息的产品主源。

内容契约至少逐项记录：

- 页面 / 信息区和稳定 `CONTENT-ID`；
- 用户可见内容：静态标题、字段、状态文案、按钮、placeholder、提示、空态、错误和操作反馈；
- 内容类型：静态信息、动态数据、条件信息或操作反馈；
- 展示条件、状态所有者、缺失 / 空 / 加载 / 失败 / 过期表现和恢复动作；
- 内容优先级、长度 / 截断 / 数量 / 密度约束和代表性数据；
- 允许动作、不可用原因、系统结果和下一状态；
- 原型故事、功能、规则和验收关联；
- 已确认、假设、待确认、不适用及负责人、时间和阻塞影响。

页面内容契约与信息结构的关系是“结构 + 内容”，与页面状态表的关系是“页面内容 + 状态变化”。不要把所有状态域做成笛卡尔积；先区分全局、页面、信息区、业务和组件状态，再列出必须成图的代表组合。内容契约未完成时，不能以“设计稿补充文案 / 字段”作为 PRD 完成条件。

原型规划应同时说明：共享页面骨架、页面 × 状态 × 内容覆盖、首屏与滚动 / 固定区域、长文本和代表性数据、探索稿 / 评审稿 / 基线稿状态。详细字段定义和质量门槛参见[页面内容契约与 UX 原型](../../shared-references/页面内容契约与UX原型.md)。

### 3.4 UX 原型交接契约与就绪门禁

当需求分级标记“内容完整型 UX 原型”，或用户明确要求设计前评估页面效果时，第 2 章必须形成以下交接配置：

```markdown
#### UX 原型交付配置
- prototypeTarget：ux-prototype / wireframe / interactive-hifi / 不需要（interactive-hifi 表示可交互高保真原型，路由到 `pm-prototype-deliver`；与静态档位互斥，同一产物不得两边各做一遍）
- prototypeFidelity：内容 / 布局 / 交互 / 组件 / 视觉，各项为必须 / 建议 / 不适用
- prototypeReadiness：prototype-not-ready / prototype-ready-with-conditions / prototype-ready
- pageSchema：页面壳层、信息区、组件目录、状态变体和稳定节点 ID
- contentContract：页面全部用户可见内容及内容覆盖
- viewportContract：端类型、逻辑视口、滚动、固定区、安全区和视口锚点
- designSystemRefs：已有组件、Token、截图、Figma / Penpot 节点或中性视觉基线
- representativeData：长标题、多行说明、多项列表、缺图、空值、错误和权限样本
- staticDelivery：单文件 HTML、静态 SVG、无 JS 降级、无外部资源
```

就绪判定：页面入口和任务、P0 信息区、主要用户可见内容、关键状态 / 异常、移动端视口、代表性数据和静态交付约束都已确认，且没有阻塞页面理解或主操作的待确认项，才可标记 `prototype-ready`。

**真实数据门槛**：涉及内容型页面时，`representativeData` 优先使用真实台账 / 真实供给数据而非编造样本；原型定稿与视觉打磨开始前，占位内容必须全部替换为真实数据。真实数据同时充当 AI 推断的事实约束——台账之外的业务规则不得脑补。真实数据确实不可得时允许降级为代表性样本，但必须标注降级原因与数据到位负责人。

`prototype-ready-with-conditions` 可以进入 `pm-prd-html` 生成评审稿，但必须在 HTML 中显式展示待确认条件，不能作为 UI 设计基线；`prototype-not-ready` 不得让 HTML 通过通用占位或自由发挥补齐。

该配置只定义产品事实和交接约束，不写 SVG 代码、CSS 坐标、前端组件实现或具体导出脚本。

### 4. 功能要求写成完整行为规格

每个核心需求项必须先用 2 至 4 句完整句子说明：谁在什么场景触发什么，系统和页面发生什么变化，用户最终得到什么结果。字段标题是检查提示，不是合格正文；不得只在标题后补一个名词或短语。

正文覆盖适用的行为链：

- **角色与场景：**具体到谁、在哪个页面或业务环节、为了完成什么任务；
- **触发与前置条件：**说明动作或事件何时发生，以及登录、权限、数据和状态前提；
- **用户可见行为：**说明页面新增、删除或变化的内容、位置关系、默认状态、可操作性和反馈；
- **系统与数据行为：**说明系统使用哪些已确认信息作判断、何时写入或刷新、结果如何供页面和后续流程消费；
- **条件和优先级：**存在多个状态时明确每个状态的进入条件、表现、允许动作、操作结果和冲突优先级；
- **异常与恢复：**说明数据缺失、请求失败、重复操作、状态过期和并发变化时用户看到什么、能否重试以及数据是否受影响；
- **保持不变：**明确本次不改变的既有能力，引用既有逻辑时必须给出可定位来源和保持不变的具体行为；
- **验收关联：**让每个关键行为和分支至少对应一个可执行验收条件。

复杂条件使用决策表，线性行为使用编号步骤或短段落。表格负责比较，正文负责解释，不把完整行为拆散成需要读者自行拼装的字段碎片。每个分支至少写清“进入条件—页面表现—允许动作—系统结果—下一状态”；若用户能看到文案、按钮、加载、错误或空状态，直接写出具体表现。

不默认规定接口字段、数据库表或代码结构；只有用户要求或产品约束必须落到该层时才写。接口相关内容在 PRD 中优先写能力，例如“页面需要获取活动详情”“提交录音后创建或替换有效投稿”“删除后软删除并触发重新合成”“页面查询合成状态并展示最新作品”；API 路径、请求响应字段、错误码、微信素材下载、音频转码、混音、队列、存储、重试超时等列入研发 spec 交接清单。输入不足以确定行为时，列出待确认事项、负责人、最晚时间和阻塞影响，不自行补造业务决策。

### 5. 用矩阵覆盖复杂边界

当存在三种以上状态、角色或条件组合时，优先使用状态矩阵、权限矩阵或规则决策表，不要只写散文描述。

#### 5.1 复杂体验中间层（条件必填）

体验交付复杂度不会改变风险等级，也不要求简单需求填满额外表格。仅在对应信号命中时补充：

- **页面地图与导航契约**：多页面的入口、出口、返回落点、共享页面壳层、跨页传递对象和保留状态；
- **状态架构**：区分全局、页面、信息区和组件状态域，标明互斥 / 独立关系、优先级、组合限制和状态所有者；不把可独立变化的状态笛卡尔积式平铺；
- **复杂组件行为表**：列表、表单、筛选、分页、批量、编辑或长数据的默认内容、加载 / 空 / 错误、选择 / 校验、权限和恢复行为；
- **端与布局矩阵**：各端共享规则、布局或交互差异、需要独立评审的端形态和设计资产；
- **原型覆盖计划**：哪些页面 / 状态域 / 端形态需要 UX 原型，哪些只由流程或规则覆盖，及其理由；同时记录代表性数据和待确认项。
- **UX 原型交付配置**：原型档位、真实性要求、页面 Schema、设计资产 / 中性视觉基线、静态交付方式和 `prototypeReadiness`。

这些表只描述产品结果、用户可见行为和评审覆盖，不写组件实现、路由代码、状态管理库或响应式 CSS。

### 6. 原型规划、生成与 PRD 必须双向可追溯

- 为目标、场景、功能、原型、规则、验收和指标使用稳定 ID
- 外部原型链接定位到具体页面、Frame 或 Node；本地文件写明路径和页码 / 画板
- 功能明细引用原型 ID，原型资产表反向标注覆盖的场景和功能
- PRD 负责业务逻辑、页面内容契约、规则和验收，已确认原型负责页面结构、信息层级、视觉和交互表达
- 两者冲突时记录待确认项并更新主源，不用“以原型为准”或“以 PRD 为准”掩盖冲突
- 没有原型时明确“不适用”或标记是否阻塞，不虚构文件和链接
- 不使用“详见原型”代替页面行为、状态、异常和验收正文；原型只能补充视觉布局和交互表达
- 需要原型时，先在第 2.5 节完成页面 × 状态规划和 UX 原型交付配置，再交给 `pm-prd-html` 生成静态优先内嵌 SVG；`pm-prd-write` 不生成 PNG、SVG 代码或独立原型文件
- 第 2.4 节维护页面内容契约，第 2.5 节维护原型覆盖、视口、组件和视觉表达约束，第 2.5 节的交付配置维护静态交接与就绪状态；完整产品行为仍以第 3、4 章为准，避免同一规则在多个章节重复维护

### 7. 区分三类标准

- 研发验收标准：判断功能是否按要求实现
- 效果判断标准：判断方案是否产生预期结果
- 验证指标：定义数据来源、口径、基线、目标、观察周期和负责人

三者不得混为一段“验收标准”。

### 8. 验收标准必须可执行

关键流程优先使用 Given / When / Then，至少覆盖：

- 主流程
- 关键状态和权限分支
- 异常与失败分支
- 历史逻辑不受影响的回归场景
- 数据、消息、审核、搜索或导出等联动

### 9. 非功能要求按风险展开

按需求风险检查性能、容量、稳定性、可访问性、安全、隐私、合规、国际化、审计和可观测性。需要时写可验证阈值，不适用时说明原因。

### 10. 裁剪必须透明

对不适用章节按“章节适用性与裁剪”执行。省略原因集中写在第 0 章，不保留空标题；信息缺失和不适用必须严格区分。

### 11. 输出前执行一致性审查

完成正文后，单独做一次跨章节检查，而不是边写边假设自然一致：

- 同一角色、对象、页面、状态和动作是否始终使用同一名称
- 时间、金额、比例、容量、次数和时区等单位与口径是否一致
- 主流程、功能正文、规则矩阵、异常处理和验收标准是否描述同一结果
- 已确认事实、合理假设、待确认项和不适用项是否发生身份漂移
- 目标、场景、功能、原型、规则、验收和指标的 ID 是否断链或重复
- 原型、PRD 和研发 spec 输入发生冲突时，是否记录待决策项而非静默选边

发现冲突时优先回到已确认决策和来源修正；不能判断时标为待确认并说明阻塞影响，不擅自统一成看似完整的答案。

### 12. 按受众生成派生输出

标准 PRD 是单一事实来源。只有用户或评审场景需要时，才从同一份 PRD 派生不同视图：

- 管理者视图：目标、范围、关键取舍、投入前提、主要风险和待决策项
- 产品 / 设计 / 测试视图：用户路径、页面变化、状态权限、异常恢复和验收
- 研发视图：已确认的产品能力、系统可见结果、质量边界和待 spec 补齐事项
- 运营视图：生效范围、配置、迁移、用户沟通、人工处置和已知限制

派生输出只裁剪和重组已确认内容，不新增规则，不把 API 字段、错误码、队列、存储或算法参数补进“研发版 PRD”，也不替代正式 PRD 和研发 spec。

## 协作方阅读与交接

正式 PRD 是单一事实来源。不同协作方可以从不同章节开始，但不能只依赖口头补充或各自维护一套规则：

| 协作方 | 首先阅读 | 重点确认 |
|---|---|---|
| 产品负责人 / 管理者 | 第 0、1、5、8 章 | 一页结论、方向取舍、范围、风险和待决策项 |
| 设计 | 第 2、3、4 章及原型规划 / 索引 | 用户路径、页面结构、信息层级、状态、反馈和原型覆盖 |
| 研发 | 第 3、4、5、6、8.2 章 | 产品能力、规则、异常、依赖、验收和 spec 待补事项 |
| 测试 | 第 4、6、7 章；需要视觉评审时再看 `pm-prd-html` | 条件、动作、结果、回归、护栏、页面状态覆盖和指标验证 |
| 运营 | 第 5、7、8.1 章 | 生效范围、兼容、配置、人工处置、已知限制和反馈入口 |

发现目标、方向、一级范围或重大取舍需要变化时，暂停 PRD 细化并回到 `pm-requirement-define`；发现接口、队列、存储或算法细节未定义时，记录到 spec 交接清单，不在 PRD 中自行补造。

## 产物修订记录与版本追溯

只要本次输出会写入项目目录、被引用、交接或供他人评审，必须在产物中保留当前版本和修订记录。第一次留档写 `v0.1`；后续每轮改变规则、范围、证据、状态、验收、审计或发布事实时立即追加一条。纯错别字和不改变语义的排版可不记录。

修订记录至少说明：版本、日期、触发原因 / 阶段、主要变化、受影响章节或下游、确认人 / 责任人、状态（`active` / `superseded` / `stale` / `pending-confirmation` / `archived`）。上游版本变化时，不得静默覆盖旧结论；若影响当前产物，标记旧版本或旧证据失效并重新审查。

## 质量门禁

本 skill 的“完成标准”只表示产物已按方法生成，不等于已通过交接质量审计。

- 讨论、探索或用户明确要求“只先给初稿”时，不自动审计，并明确标记“未审计”；
- 当输出达到 `ready`、给出最终分级、准备交给设计 / 研发 / 测试 / 运营，或用户要求复核 / 验收时，必须在本次交付前自动调用 `pm-quality-audit`；
- 只有 `PASS`，或用户明确接受带责任人和完成条件的 `PASS_WITH_CONDITIONS`，才可标记为可交接；
- `BLOCKED` 必须回到本 skill、证据 skill 或上游决策，不得用补造事实的方式消除；
- 是否需要把审计报告写入项目根目录 `quality-audits/`，按用户是否要求留档 / 交接附件决定。

## 完成标准

输出前逐项检查：

- 产品决策能够追溯到需求定义或明确输入，交付门槛能够追溯到 `pm-requirement-grade` 或明确分级依据
- PRD 没有擅自改变目标、方向、一级范围、重大取舍或分级门槛
- 功能、验收和指标能够对应已确认目标与方案
- 主流程、角色动作和系统反馈完整
- 单页、多页面、页面内信息区和用户路径没有混用或误拆
- 需要评估体验时，页面入口、主任务、页面转移、关键分支和结果闭环清楚
- 受影响页面的信息层级、关键元素和必要状态可被读者理解
- 命中内容完整型 UX 原型时，页面上每个用户可见静态文案、动态字段、状态标签、动作和反馈都有内容契约主源，原型不依赖设计稿补齐
- 不打开原型时，读者仍能复述主路径、页面变化、关键状态、异常收口和验收条件
- 页面内容契约、页面状态组合、原型覆盖计划和 UX 原型交付配置能够互相核对，未成图组合有规则 / 验收依据且未被误标为已验证
- `prototypeReadiness` 与实际输入一致；`prototype-ready` 没有阻塞页面理解、主操作或状态收口的待确认项；静态交付要求已传递给 `pm-prd-html`
- 每个核心需求以完整句子说明触发、行为和结果，没有用字段标签、ID 引用或“按原逻辑”代替正文
- 每个 P0 功能都已展开条件分支、异常恢复、边界和验收追溯，没有停留在一句话需求
- 状态、权限、异常和联动边界可被研发与测试识别
- PRD 只写能力、产品结果和验收；接口字段、错误码、队列、存储、算法等 spec 细节已从正文剥离或标入交接清单
- PRD 没有因 spec 边界而过度压缩，系统能力、页面状态、操作限制和异常兜底仍足够具体
- 每个核心需求项都能映射到验收标准
- 界面需求能够定位到具体原型 / 设计节点，原型状态和主源边界清楚
- 需要原型的需求已形成可交给 `pm-prd-html` 的页面 × 状态规划；单页多信息区同时形成共享页面骨架与状态差异表；移动端页面同时明确视口、滚动 / 固定区域和状态锚点；不需要原型时写明原因，不为模板填充空表
- 目标、场景、功能、原型、规则、验收和指标能够通过稳定 ID 追溯
- 指标包含口径、基线或补数计划、目标、周期和观察方式
- 高风险需求已定义适用的性能、安全、隐私、合规或可观测性要求
- 风险、依赖、假设和待确认项单独列出
- 角色、术语、状态、单位、规则、异常、验收和追溯 ID 已完成跨章节一致性审查
- 面向管理者、研发、设计、测试或运营的派生输出没有改变正式 PRD 的事实、规则和边界
- 若生成 HTML 协作交付，`pm-prd-html` 只消费正式 PRD 和原型规划，SVG / 流程图没有新增规则或独立口径
- 内部 MVP、单页复杂状态、异步任务或跨系统场景已进入组合结构判断；应填模块已包含，缺失项已说明省略原因
- 文档不依赖作者口头补充才能理解核心逻辑

文档确认后，需要输出更新说明或更新日志时使用 `pm-update-write`。
- 持久化产物已标注当前版本、状态和修订记录；重要变更能说明影响范围与是否需要下游重做。
