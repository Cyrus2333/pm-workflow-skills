# pm-prd-write

把已确认的产品决策展开成可实现、可测试、可上线和可验证的交付规格。

## 优先读取

1. [PRD 模板](./references/PRD模板.md)
2. 需要参考完整粒度时，再读[PRD 示例](./references/PRD示例.md)

在项目仓库内，再按需读取：

1. `AGENTS.md`
2. 根 `README.md`
3. 产品或项目文档索引
4. 与需求相关的页面、规则、流程、数据、运营和研发文档
5. 已确认的产品需求定义结果
6. 已有原型、设计稿、流程图或交互说明；尚未产出时确认负责人、时间和是否阻塞

## 工作边界

负责：

- 把一级产品范围拆成版本、页面、模块、流程和功能清单
- 展开角色、状态、权限、规则、异常、数据和跨模块联动
- 定义历史兼容、灰度、迁移、回滚、监控和运营准备
- 关联原型、设计文件和具体 Frame / 节点，建立功能与验收追溯
- 编写研发验收用例和可执行的效果验证方案

不负责：

- 重新证明需求是否值得做
- 重新定义目标或发散新的产品方向
- 在没有决策记录时擅自改变一级范围和重大取舍

## 输入契约

开始前至少取得：

- 已确认的问题、证据和影响对象
- 目标、非目标和方向级成功假设
- 推荐方向、选择依据和重大取舍
- 一级范围、主要角色和重大约束
- 需要 PRD 深入的状态、权限、规则、联动、数据或兼容维度
- 已有原型、设计文件或交互说明；没有时需确认是否适用、由谁补充以及是否阻塞

如果这些信息未以独立需求定义文档提供，但用户已经明确表达，可先整理为输入摘要再继续。若仍需比较方向、改变目标、调整业务原则或决定一级范围，转 `pm-requirement-define`。

PRD 编写过程中发现已确认方向与项目事实冲突时，不擅自重做产品决策。明确冲突、影响和待决策项，再返回 `pm-requirement-define`。

## 选择文档级别

默认输出“标准版”。根据复杂度调整篇幅，但不得牺牲逻辑闭环。

### 轻量版

适用于局部文案、展示或单页面低风险调整，且不涉及新角色、规则、状态流转和历史数据。

可以合并章节，但必须保留：问题、目标、范围、具体变化、边界、研发验收，以及指标不适用的说明。

### 标准版

适用于普通功能、单条完整流程或少量跨模块联动。完整覆盖模板核心章节，是默认级别。

### 完整版

出现以下任一情况时使用：

- 多角色、多场景或多端
- 业务规则、状态机、权限或数据口径变化
- 跨系统联动、历史数据迁移或灰度发布
- 需要版本拆分、复杂上线或效果复盘

三种级别沿用同一套主章节：轻量版可合并不适用的子项，完整版通过状态、权限、规则、追溯和发布矩阵增加深度，不额外堆叠平级章节。

## 章节适用性与裁剪

模板是覆盖面清单，不是要求每份 PRD 填满所有章节。

- 核心必填：`0 文档信息与一页结论`、`1 决策依据`、`3 交付范围与功能需求`、`6 验收与追溯`
- 条件必填：`2 方案总览与原型`、`4 规则、数据与质量边界`、`5 影响、依赖与发布`、`7 效果验证`
- 可选：`8 风险、待确认项与附录`

条件章节的触发规则以模板中的适用性表为准。裁剪时遵守：

- 真正不适用的章节可以整体省略，并在第 0 章写明“省略章节及原因”
- 应当适用但信息缺失时，不得省略；标记待确认、负责人、时间和是否阻塞
- 不输出空标题、空表格或大段“不适用”，也不为了保持完整而虚构内容
- 核心章节可以按需求复杂度压缩，但问题—范围—功能—验收链不能断
- 单一轻量需求可在功能明细内直接关联验收；多功能、多原型或复杂规则需求使用完整追溯矩阵

## 两层文档结构

### 决策记录层

为了让 PRD 自包含，摘要记录已经确认的：

- 背景事实和问题
- 目标、非目标和成功假设
- 推荐方向、选择依据和重大取舍
- 一级范围和重大约束

这里负责“引用、固化和追溯”产品决策，不重新发散方案。若必须改变结论，应生成新的决策记录后再继续 PRD。

### 研发交付层

回答：

- 具体改哪些页面、模块、流程、规则和数据
- 不同角色、状态、权限和异常条件下如何表现
- 影响哪些现有能力和历史逻辑
- 如何发布、兼容、回滚和验收
- 每个界面需求对应哪个原型或设计节点，以及原型当前是否已确认

## 编写规则

### 1. 产品决策必须可追溯但不重复执行

- 背景、问题、目标和方案结论注明来源或关联需求定义
- 引用上游已经记录的推荐方向、选择依据和未选方案；上游未记录时不在 PRD 中补做方案比较
- 不为了填充 PRD 重新生成不同方案或改变一级范围
- 无法确认的内容标记为“待确认”或“假设”

### 2. 使用现状与目标对照

重要变化优先写成：

| 维度 | 当前状态 | 目标状态 | 影响对象 |
|---|---|---|---|

避免只写“优化体验”“支持某能力”“调整一下”等不可验收描述。

### 3. 功能要求写到可实现粒度

每个核心需求项至少说明：

- 编号和名称
- 使用角色与场景
- 前置条件和触发方式
- 主流程与结果
- 页面、字段、内容或交互变化
- 状态变化和数据处理
- 权限限制
- 异常与兜底
- 埋点、日志或审计要求
- 对应验收标准

不默认规定接口字段、数据库表或代码结构；只有用户要求或产品约束必须落到该层时才写。

### 4. 用矩阵覆盖复杂边界

当存在三种以上状态、角色或条件组合时，优先使用状态矩阵、权限矩阵或规则决策表，不要只写散文描述。

### 5. 原型和 PRD 必须双向可追溯

- 为目标、场景、功能、原型、规则、验收和指标使用稳定 ID
- 外部原型链接定位到具体页面、Frame 或 Node；本地文件写明路径和页码 / 画板
- 功能明细引用原型 ID，原型资产表反向标注覆盖的场景和功能
- PRD 负责业务逻辑、规则和验收，已确认原型负责页面结构、视觉和交互表达
- 两者冲突时记录待确认项并更新主源，不用“以原型为准”或“以 PRD 为准”掩盖冲突
- 没有原型时明确“不适用”或标记是否阻塞，不虚构文件和链接

### 6. 区分三类标准

- 研发验收标准：判断功能是否按要求实现
- 效果判断标准：判断方案是否产生预期结果
- 验证指标：定义数据来源、口径、基线、目标、观察周期和负责人

三者不得混为一段“验收标准”。

### 7. 验收标准必须可执行

关键流程优先使用 Given / When / Then，至少覆盖：

- 主流程
- 关键状态和权限分支
- 异常与失败分支
- 历史逻辑不受影响的回归场景
- 数据、消息、审核、搜索或导出等联动

### 8. 非功能要求按风险展开

按需求风险检查性能、容量、稳定性、可访问性、安全、隐私、合规、国际化、审计和可观测性。需要时写可验证阈值，不适用时说明原因。

### 9. 裁剪必须透明

对不适用章节按“章节适用性与裁剪”执行。省略原因集中写在第 0 章，不保留空标题；信息缺失和不适用必须严格区分。

## 默认输出结构

0. 文档信息与一页结论
1. 决策依据
2. 方案总览与原型
3. 交付范围与功能需求
4. 规则、数据与质量边界
5. 影响、依赖与发布
6. 验收与追溯
7. 效果验证
8. 风险、待确认项与附录

## 完成标准

输出前逐项检查：

- 产品决策能够追溯到需求定义或明确输入
- PRD 没有擅自改变目标、方向、一级范围或重大取舍
- 功能、验收和指标能够对应已确认目标与方案
- 主流程、角色动作和系统反馈完整
- 状态、权限、异常和联动边界可被研发与测试识别
- 每个核心需求项都能映射到验收标准
- 界面需求能够定位到具体原型 / 设计节点，原型状态和主源边界清楚
- 目标、场景、功能、原型、规则、验收和指标能够通过稳定 ID 追溯
- 指标包含口径、基线或补数计划、目标、周期和观察方式
- 高风险需求已定义适用的性能、安全、隐私、合规或可观测性要求
- 风险、依赖、假设和待确认项单独列出
- 文档不依赖作者口头补充才能理解核心逻辑

文档确认后，需要输出更新说明或更新日志时使用 `pm-update-write`。
