# pm-requirement-define

负责做出产品决策，把输入推进到“问题、目标、方向和一级范围已经确认，可以进入需求分级与后续交付路由”的状态。

## 优先读取
- 所有需要留档或交接的产物都遵守[产物修订记录与版本追溯规范](../../shared-references/产物修订记录与版本追溯规范.md)；纯临时草稿可不建立修订表。
- 需求在多轮讨论中发生规则、架构、范围或验收大改时，先读[需求迭代反复与大改治理指南](../../shared-references/需求迭代反复与大改治理指南.md)；普通局部修改不必展开。

1. [需求定义模板](./references/需求定义模板.md)
2. [需求完整性检查清单](./references/需求完整性检查清单.md)
3. 需要参考完整粒度时，再读[需求定义示例](./references/需求定义示例.md)
4. 需要判断或执行深度质询时，读[深度质询协议](./references/深度质询协议.md)
5. 修改触发规则或需要校准判断时，读[深度质询触发回归案例](./references/深度质询触发案例.md)
6. 需求在已有系统上修改规则、指标、角色关系或结算时，读[需求迭代闭环与收尾协议](../../shared-references/需求迭代闭环与收尾协议.md)
7. 方向探索与方案讨论阶段涉及需求方诉求传达（概念、参照物、文案、样式反馈）时，读[诉求传达与协作反馈指南](../../shared-references/诉求传达与协作反馈指南.md)

在项目仓库内，再按需读取 `AGENTS.md`、根 `README.md`、产品或项目文档索引，以及与需求直接相关的规则、数据、研究和历史方案。

## 核心边界

本 skill 回答：

- 为什么要做：现状、问题和影响是否成立
- 希望改变什么：用户和业务目标是什么
- 选择什么方向：有哪些解法，为什么选当前方向
- 做到哪里为止：一级范围、非目标和重大约束是什么
- 交给分级和后续 PRD 时已知哪些体验线索：主要角色、入口、主任务和关键路径（如已有）
- 如果需求目标包含“评估完整页面效果”或设计不应补齐业务信息，记录页面内容完整性要求、需要覆盖的端形态 / 状态范围、原型档位意图和当前信息缺口；只描述评审目标，不展开字段和页面规格
- 如果预览环境存在脚本受限、离线或安全沙箱约束，记录静态单文件 HTML / SVG 的交付意图；不在本 skill 内规定 SVG 实现
- 如何判断值得继续：成功假设和主要风险是什么

本 skill 不回答：

- 每个页面、字段和交互具体如何变化
- 每个状态、角色、权限和异常条件如何处理
- 消息、审核、搜索、导出、数据和历史兼容的详细规则
- 如何发布、回滚、验收和精确定义指标口径

这些内容先由 `pm-requirement-grade` 判定交付等级和门槛；需要完整规格时再由 `pm-prd-write` 展开。

## 输出表达要求

需求定义不是把输入重新排成标签清单。每个结论至少用完整句子说明“针对谁、在什么场景、要改变什么、为什么这样判断”；表格用于并列比较事实或方向，不能用“优化体验”“支持能力”“待处理”等短语代替结论。对于已知的入口、主任务和关键路径，要写出用户从哪里进入、完成什么动作、得到什么结果；如果页面效果需要在设计前评审，补充“评审需要看清什么”和“哪些用户可见内容不能由设计稿补齐”；未知时明确标注未知，不提前虚构页面规格。体验交付意图只传递目标和风险，不把页面细节提前写入需求定义。

## 根据输入成熟度调整路径

- 模糊想法：先还原事实、定义问题和目标，再探索方向。
- 具体功能诉求：先把功能提议还原为问题；方向合理时直接确认选择依据和一级范围。
- 已有方案：不重复脑暴，只检查问题—目标—方向的逻辑、取舍和阻塞决策。

## 判断是否启动深度质询

判断目标不是“输入是否足够详细”，而是当前是否存在会改变问题、目标、方向、一级范围、投入量级或重大风险责任的未决问题。

先将缺口路由：项目事实自行查阅；用户、竞品和数据证据交给对应证据 skill；会影响交付等级的风险信息交给 `pm-requirement-grade`；页面行为、状态权限和验收交给 `pm-prd-write`；研发实现交给 spec。只有必须由负责人决定的产品决策缺口才进入质询判断，`needs-input` 不自动等于需要质询。

输出三类判断：

- `不需要`：直接继续，并说明剩余缺口应由哪个步骤处理。
- `单问题试探`：边界不确定时只问一个最可能改变判断的问题，回答后重新分类。
- `建议深度质询`：存在重大未决决策时，先列出触发原因、首轮主题和预计范围，获得用户确认后再开始。

用户明确要求“持续追问”“挑战方案”或等价表达时可直接进入；其他情况不得静默启动多轮质询。详细硬触发、软信号、问题格式、决策记录和停止条件按[深度质询协议](./references/深度质询协议.md)执行。

## 按证据缺口选择增强 skill

证据不足时按需使用，不作为固定前置流程：

- 有访谈、工单、问卷开放题或观察材料，需要提炼用户问题与差异：`pm-research-synthesize`
- 需要比较外部解法、行业惯例或差异化空间：`pm-competitor-analyze`
- 需要判断问题规模、指标变化、上线效果或异常原因：`pm-metrics-review`

只选择能补当前决策缺口的 skill，不默认全部执行。它们提供证据与分析，不代替本 skill 确认问题、目标、方向和一级范围；证据已足够时直接继续需求定义。

## 规则变更与既有系统迭代专项

当需求是在已有功能上调整规则、角色关系、指标或结算口径时，先启用[需求迭代闭环与收尾协议](../../shared-references/需求迭代闭环与收尾协议.md)，至少完成：

- 规则变更台账：旧规则、新规则、明确不变项、生效范围、历史处理和来源状态；
- 影响地图：页面、写入、派生计算、触发链路、后台 / 运营、测试 / 观测和文档发布；
- 若涉及时间或关系变化：明确事实发生点、冻结点、冻结前后变更、重算触发、幂等、中断恢复和历史边界。

不要把“当前字段是什么”直接当作“历史结算应依据什么”。先完成业务时序和归属原则，再把技术实现留给 PRD / spec。若旧规则已上线，需求定义必须明确是只影响新事件、补算历史，还是两者分开处理。

## 需求迭代反复与方案大改治理

当用户提出“是不是设计复杂了”“源头规则能否收敛”“重新梳理整套方案”“方案基本收尾但请完整审查”等信号时，不要继续在当前版本上局部补丁。先按[需求迭代反复与大改治理指南](../../shared-references/需求迭代反复与大改治理指南.md)完成一次版本重评估：

1. 建立当前版本基线，列出已确认、待确认、假设、已否决和不再讨论的事项；
2. 将变更归类为局部表达、产品规则、架构 / 数据模型、范围 / 风险或验收 / 发布事实更正；
3. 若命中产品规则、架构 / 数据模型或范围 / 风险变更，明确宣布原分级、PRD、Spec、验收和审计中哪些内容失效，回退到本 skill；
4. 先复盘业务不变量和源头规则，再决定是否需要快照、读模型、迁移、双写、异步任务或复杂兼容；
5. 每轮只推进一个层级：业务原则 → 产品行为 → 技术方案 → 验证交付。上层未冻结时，不把下层细节写成已定方案；
6. 只有问题、目标、一级范围、历史边界、关键时序和复杂度取舍共同冻结后，才允许输出 `ready` 并交给分级 / PRD。

需求定义的默认输出增加两项：

- **迭代版本与决策台账**：记录版本、触发原因、业务决策变化、受影响产物、当前状态；
- **复杂度源头复盘**：记录可收敛的源头规则、采用 / 不采用及其对范围和风险的影响。

## 工作流程

### 0. 判断路径与质询模式

读取可查事实，判断任务类型和输入成熟度，完成缺口分类。需要时输出质询模式判断；未获用户确认前不进入多轮质询。

启用质询后按问题、目标、方向、一级范围和进入分级 / PRD 条件的依赖顺序推进。每轮更新已确认结论和未决分支；当剩余问题只属于证据、PRD 或研发 spec 时立即停止，并回到本流程形成需求定义。

### 1. 还原现状和证据

说明 WHO、WHEN / WHERE、WHY / WHAT、当前 HOW、HOW MUCH 和 EVIDENCE。

区分已验证事实、用户陈述、合理推断和待验证假设。没有数据时说明缺失原因及是否阻塞方向判断。

涉及方案探索或页面体验的需求，开工前向需求方收集**参照物清单**（竞品或参照产品截图、参照方案、真实素材、内容台账、目标口径数据），逐项登记"传递的诉求"，模板见[诉求传达与协作反馈指南](../../shared-references/诉求传达与协作反馈指南.md) §3。清单缺失不阻塞需求定义，但应标注"建议补齐"——参照物后置会显著增加后续方案与原型迭代轮次。

### 2. 定义问题与需求

从事实中推导：

- 当前状态与预期状态的差距
- 问题发生的主要环节
- 受影响角色和影响程度
- 不处理的主要损失
- 需求方真正希望达到的状态

用户提出的按钮、入口、状态或功能只作为候选解法。

### 3. 明确目标与非目标

定义用户状态变化、业务结果变化、目标人群、覆盖场景和方向级成功信号。目标必须对应问题。

同时说明本轮不解决什么，以及哪些既有业务原则保持不变。

### 4. 探索与选择方向

当方向未定或存在实质争议时，提出 2 至 3 个不同方向，比较：

- 问题覆盖范围
- 预期收益和成功依赖
- 产品、设计、研发和运营投入量级
- 长期价值、维护成本和主要副作用
- 外部参考的适用前提

输出推荐方向、未选原因、关键假设和会改变选择的临界条件。方向已有充分结论时，只记录选择依据。

方向发散期建议与需求方共同提炼 3 至 5 个**概念锚点**作为每轮讨论的校准基准（少说、说准、反复引用，确定后不频繁换词）；概念锚点随需求定义简报交接给下游。文字讨论触及抽象极限时，可按[诉求传达与协作反馈指南](../../shared-references/诉求传达与协作反馈指南.md) §7 切换低保真单文件 HTML 原型承载讨论——它是方向排除工具，方向收敛即停。

### 5. 划定一级范围与重大约束

只定义决策层边界：

- 涉及哪些产品端、业务域、主流程和主要角色
- 本次明确包含和不包含什么
- 是否涉及新角色、新状态、新权限、核心规则、跨系统、历史数据或合规风险
- 哪些重大约束会影响方案可行性或投入量级

涉及自动化、AI、第三方能力、高频调用、资产或不可逆动作时，额外扫描：

- 成本是否随用户量、调用量、数据量或地区扩张非线性增长
- 第三方或降级失败影响的是便利性、核心体验、收入、资产还是合规
- 自动判断错误由谁发现、复核、解释、纠正和承担处置责任
- 降级是否会产生假成功、重复执行、不可逆结果或责任不清
- 规模扩大 10 倍时，哪些产品规则、人工流程或服务承诺会失效

这里只识别“会影响分级或需要 PRD 展开的维度”，不枚举完整状态、权限、异常和联动规则。

如用户或已有材料已经提供，可在分级 / PRD 交接中记录主要角色、主要入口、用户主任务和已知关键路径；这些是线索和范围，不是详细页面规格，也不是 `ready` 的额外硬门槛。

### 6. 定义成功假设

说明：

- 用户行为或状态预计如何变化
- 业务结果预计如何变化
- 哪些结果会证明方向值得继续
- 哪些护栏不能明显受损
- 当前缺少什么基线或验证证据

这里只定义指标方向和判断假设；具体口径、基线、目标、数据源和观察周期由分级后的 PRD 或指标方案展开。

### 7. 判断是否可进入分级与后续交付

- `ready`：问题、目标、推荐方向、一级范围和重大约束已明确
- `needs-decision`：仍存在会改变方向、业务原则或投入量级的阻塞决策
- `needs-input`：关键事实、对象或影响程度不足，尚不能做方向判断

达到 `ready` 不代表规格已经完整，只代表产品决策可以先交给 `pm-requirement-grade` 定级；若分级结论要求 PRD，再交给 `pm-prd-write` 展开。

## 产物修订记录与版本追溯

只要本次输出会写入项目目录、被引用、交接或供他人评审，必须在产物中保留当前版本和修订记录。第一次留档写 `v0.1`；后续每轮改变规则、范围、证据、状态、验收、审计或发布事实时立即追加一条。纯错别字和不改变语义的排版可不记录。

修订记录至少说明：版本、日期、触发原因 / 阶段、主要变化、受影响章节或下游、确认人 / 责任人、状态（`active` / `superseded` / `stale` / `pending-confirmation` / `archived`）。上游版本变化时，不得静默覆盖旧结论；若影响当前产物，标记旧版本或旧证据失效并重新审查。

## 质量门禁

本 skill 的“完成标准”只表示产物已按方法生成，不等于已通过交接质量审计。

- 讨论、探索或用户明确要求“只先给初稿”时，不自动审计，并明确标记“未审计”；
- 当输出达到 `ready`、给出最终分级、准备交给设计 / 研发 / 测试 / 运营，或用户要求复核 / 验收时，必须在本次交付前自动调用 `pm-quality-audit`；
- 只有 `PASS`，或用户明确接受带责任人和完成条件的 `PASS_WITH_CONDITIONS`，才可标记为可交接；
- `BLOCKED` 必须回到本 skill、证据 skill 或上游决策，不得用补造事实的方式消除；
- 是否需要把审计报告写入项目根目录 `quality-audits/`，按用户是否要求留档 / 交接附件决定。

## 默认输出

输出“产品需求定义简报”：

1. 一句话结论与成熟度
2. 质询模式判断与关键决策记录（触发时）
3. 现状事实、证据和问题定义
4. 目标、成功假设与非目标
5. 可选方向、推荐方向和关键取舍
6. 一级范围与重大约束
7. 迭代版本与决策台账、复杂度源头复盘（命中时）
8. 主要假设、风险和阻塞决策
9. 分级风险线索与 PRD 需要重点展开的维度
10. `ready` / `needs-decision` / `needs-input`

## 交给需求分级 / PRD 的输入契约

进入 `pm-requirement-grade` 时至少交付；若分级结论要求 `pm-prd-write`，这些内容继续作为 PRD 输入：

- 已确认的问题及证据
- 目标、非目标和成功假设
- 推荐方向、选择依据和未选方案
- 一级范围与主要角色
- 已知重大约束和阻塞项处理结论
- 主要入口、主任务和关键路径（如已知；未知时明确标记）
- `pm-requirement-grade` 需要判断的风险线索：资金 / 交易、登录 / 授权 / 隐私、权益 / 资产、核心链路、后端写入 / 状态机、AI 自动化结果、全局配置、外部依赖、可回滚性和项目画像红线
- PRD 需要展开的产品动线、页面信息结构（如适用）、状态、权限、规则、联动或数据维度
- 已知体验复杂度线索：多页面导航或跨页状态、独立状态域、复杂列表 / 表单 / 批量操作、多端差异；只交接线索，不在需求定义阶段展开页面规格
- 若为已有系统规则 / 指标 / 结算迭代：附规则变更台账、影响地图，以及冻结点、重算、幂等、失败恢复和历史边界的已确认结论或待决项；
- 若涉及接口、异步任务、第三方能力、存储或算法，只交接“产品能力要求”和“技术预验证 / spec 待补齐事项”，不要提前写 API 路径、请求响应字段、错误码、队列、存储路径或算法参数

## 完成标准

- 问题能够从事实或明确假设中推导
- 可查事实、证据缺口、产品决策、产品规格和研发实现缺口已正确区分，没有把所有信息不足都转成用户追问
- 质询模式判断说明了理由；多轮质询已获得用户确认，边界案例优先使用单问题试探
- 目标与问题对应，不是功能清单
- 方向有选择依据，重大取舍未隐藏
- 一级范围、非目标和重大约束清楚
- 成本放大、第三方失败、降级后果和自动决策责任等适用风险没有被遗漏
- 未提前编写研发规格级细节，接口和技术链路只写到能力、约束和待 spec 补齐事项
- `pm-requirement-grade` 无需重新做产品方向决策即可定级；PRD 作者无需重新做产品方向决策即可继续
- 已知的入口、主任务和关键路径已交接；未知部分已标记为分级待确认或 PRD 待展开，不把详细页面规格提前写入需求定义
- 关键结论和分级 / PRD 交接内容使用完整句子表达，读者不需要根据标签或 ID 自行推断“要改变什么”
- 深度质询在产品决策足够明确时停止，没有继续追问分级不需要的页面字段、接口参数或与当前方向无关的边缘问题
- 会改变方向或投入量级的阻塞决策已记录负责人、最晚确认时间和不成立时的影响
- 持久化产物已标注当前版本、状态和修订记录；重要变更能说明影响范围与是否需要下游重做。
