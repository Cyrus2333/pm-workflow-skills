# pm-requirement-define

负责做出产品决策，把输入推进到“问题、目标、方向和一级范围已经确认，可以开始写 PRD”的状态。

## 优先读取

1. [需求定义模板](./references/需求定义模板.md)
2. [需求完整性检查清单](./references/需求完整性检查清单.md)
3. 需要参考完整粒度时，再读[需求定义示例](./references/需求定义示例.md)
4. 需要判断或执行深度质询时，读[深度质询协议](./references/深度质询协议.md)
5. 修改触发规则或需要校准判断时，读[深度质询触发回归案例](./references/深度质询触发案例.md)

在项目仓库内，再按需读取 `AGENTS.md`、根 `README.md`、产品或项目文档索引，以及与需求直接相关的规则、数据、研究和历史方案。

## 核心边界

本 skill 回答：

- 为什么要做：现状、问题和影响是否成立
- 希望改变什么：用户和业务目标是什么
- 选择什么方向：有哪些解法，为什么选当前方向
- 做到哪里为止：一级范围、非目标和重大约束是什么
- 交给 PRD 时已知哪些体验线索：主要角色、入口、主任务和关键路径（如已有）
- 如何判断值得继续：成功假设和主要风险是什么

本 skill 不回答：

- 每个页面、字段和交互具体如何变化
- 每个状态、角色、权限和异常条件如何处理
- 消息、审核、搜索、导出、数据和历史兼容的详细规则
- 如何发布、回滚、验收和精确定义指标口径

这些内容由 `pm-prd-write` 展开。

## 输出表达要求

需求定义不是把输入重新排成标签清单。每个结论至少用完整句子说明“针对谁、在什么场景、要改变什么、为什么这样判断”；表格用于并列比较事实或方向，不能用“优化体验”“支持能力”“待处理”等短语代替结论。对于已知的入口、主任务和关键路径，要写出用户从哪里进入、完成什么动作、得到什么结果；未知时明确标注未知，不提前虚构页面规格。

## 根据输入成熟度调整路径

- 模糊想法：先还原事实、定义问题和目标，再探索方向。
- 具体功能诉求：先把功能提议还原为问题；方向合理时直接确认选择依据和一级范围。
- 已有方案：不重复脑暴，只检查问题—目标—方向的逻辑、取舍和阻塞决策。

## 判断是否启动深度质询

判断目标不是“输入是否足够详细”，而是当前是否存在会改变问题、目标、方向、一级范围、投入量级或重大风险责任的未决问题。

先将缺口路由：项目事实自行查阅；用户、竞品和数据证据交给对应证据 skill；页面行为、状态权限和验收交给 `pm-prd-write`；研发实现交给 spec。只有必须由负责人决定的产品决策缺口才进入质询判断，`needs-input` 不自动等于需要质询。

输出三类判断：

- `不需要`：直接继续，并说明剩余缺口应由哪个步骤处理。
- `单问题试探`：边界不确定时只问一个最可能改变判断的问题，回答后重新分类。
- `建议深度质询`：存在重大未决决策时，先列出触发原因、首轮主题和预计范围，获得用户确认后再开始。

用户明确要求“持续追问”“挑战方案”或等价表达时可直接进入；其他情况不得静默启动多轮质询。详细硬触发、软信号、问题格式、决策记录和停止条件按[深度质询协议](./references/深度质询协议.md)执行。

## 按证据缺口选择增强 skill

证据不足时按需使用，不作为固定前置流程：

- 有访谈、工单、问卷开放题或观察材料，需要提炼用户问题与差异：`pm-research-synthesize`
- 需要比较外部解法、行业惯例或差异化空间：`pm-competitor-analyze`
- 需要判断问题规模、指标变化、上线效果或异常原因：`pm-metrics-review`

只选择能补当前决策缺口的 skill，不默认全部执行。它们提供证据与分析，不代替本 skill 确认问题、目标、方向和一级范围；证据已足够时直接继续需求定义。

## 工作流程

### 0. 判断路径与质询模式

读取可查事实，判断任务类型和输入成熟度，完成缺口分类。需要时输出质询模式判断；未获用户确认前不进入多轮质询。

启用质询后按问题、目标、方向、一级范围和进入 PRD 条件的依赖顺序推进。每轮更新已确认结论和未决分支；当剩余问题只属于证据、PRD 或研发 spec 时立即停止，并回到本流程形成需求定义。

### 1. 还原现状和证据

说明 WHO、WHEN / WHERE、WHY / WHAT、当前 HOW、HOW MUCH 和 EVIDENCE。

区分已验证事实、用户陈述、合理推断和待验证假设。没有数据时说明缺失原因及是否阻塞方向判断。

### 2. 定义问题与需求

从事实中推导：

- 当前状态与预期状态的差距
- 问题发生的主要环节
- 受影响角色和影响程度
- 不处理的主要损失
- 需求方真正希望达到的状态

用户提出的按钮、入口、状态或功能只作为候选解法。

### 3. 明确目标与非目标

定义用户状态变化、业务结果变化、目标人群、覆盖场景和方向级成功信号。目标必须对应问题。

同时说明本轮不解决什么，以及哪些既有业务原则保持不变。

### 4. 探索与选择方向

当方向未定或存在实质争议时，提出 2 至 3 个不同方向，比较：

- 问题覆盖范围
- 预期收益和成功依赖
- 产品、设计、研发和运营投入量级
- 长期价值、维护成本和主要副作用
- 外部参考的适用前提

输出推荐方向、未选原因、关键假设和会改变选择的临界条件。方向已有充分结论时，只记录选择依据。

### 5. 划定一级范围与重大约束

只定义决策层边界：

- 涉及哪些产品端、业务域、主流程和主要角色
- 本次明确包含和不包含什么
- 是否涉及新角色、新状态、新权限、核心规则、跨系统、历史数据或合规风险
- 哪些重大约束会影响方案可行性或投入量级

涉及自动化、AI、第三方能力、高频调用、资产或不可逆动作时，额外扫描：

- 成本是否随用户量、调用量、数据量或地区扩张非线性增长
- 第三方或降级失败影响的是便利性、核心体验、收入、资产还是合规
- 自动判断错误由谁发现、复核、解释、纠正和承担处置责任
- 降级是否会产生假成功、重复执行、不可逆结果或责任不清
- 规模扩大 10 倍时，哪些产品规则、人工流程或服务承诺会失效

这里只识别“需要 PRD 展开的维度”，不枚举完整状态、权限、异常和联动规则。

如用户或已有材料已经提供，可在 PRD 交接中记录主要角色、主要入口、用户主任务和已知关键路径；这些是线索和范围，不是详细页面规格，也不是 `ready` 的额外硬门槛。

### 6. 定义成功假设

说明：

- 用户行为或状态预计如何变化
- 业务结果预计如何变化
- 哪些结果会证明方向值得继续
- 哪些护栏不能明显受损
- 当前缺少什么基线或验证证据

这里只定义指标方向和判断假设；具体口径、基线、目标、数据源和观察周期由 PRD 或指标方案展开。

### 7. 判断是否可进入 PRD

- `ready`：问题、目标、推荐方向、一级范围和重大约束已明确
- `needs-decision`：仍存在会改变方向、业务原则或投入量级的阻塞决策
- `needs-input`：关键事实、对象或影响程度不足，尚不能做方向判断

达到 `ready` 不代表规格已经完整，只代表产品决策可以交给 `pm-prd-write` 展开。

## 默认输出

输出“产品需求定义简报”：

1. 一句话结论与成熟度
2. 质询模式判断与关键决策记录（触发时）
3. 现状事实、证据和问题定义
4. 目标、成功假设与非目标
5. 可选方向、推荐方向和关键取舍
6. 一级范围与重大约束
7. 主要假设、风险和阻塞决策
8. PRD 需要重点展开的维度
9. `ready` / `needs-decision` / `needs-input`

## 交给 PRD 的输入契约

进入 `pm-prd-write` 时至少交付：

- 已确认的问题及证据
- 目标、非目标和成功假设
- 推荐方向、选择依据和未选方案
- 一级范围与主要角色
- 已知重大约束和阻塞项处理结论
- 主要入口、主任务和关键路径（如已知；未知时明确标记）
- PRD 需要展开的产品动线、页面信息结构（如适用）、状态、权限、规则、联动或数据维度
- 若涉及接口、异步任务、第三方能力、存储或算法，只交接“产品能力要求”和“技术预验证 / spec 待补齐事项”，不要提前写 API 路径、请求响应字段、错误码、队列、存储路径或算法参数

## 完成标准

- 问题能够从事实或明确假设中推导
- 可查事实、证据缺口、产品决策、产品规格和研发实现缺口已正确区分，没有把所有信息不足都转成用户追问
- 质询模式判断说明了理由；多轮质询已获得用户确认，边界案例优先使用单问题试探
- 目标与问题对应，不是功能清单
- 方向有选择依据，重大取舍未隐藏
- 一级范围、非目标和重大约束清楚
- 成本放大、第三方失败、降级后果和自动决策责任等适用风险没有被遗漏
- 未提前编写研发规格级细节，接口和技术链路只写到能力、约束和待 spec 补齐事项
- PRD 作者无需重新做产品方向决策即可继续
- 已知的入口、主任务和关键路径已交接；未知部分已标记为 PRD 待展开，不把详细页面规格提前写入需求定义
- 关键结论和 PRD 交接内容使用完整句子表达，读者不需要根据标签或 ID 自行推断“要改变什么”
- 深度质询在产品决策足够明确时停止，没有继续追问页面字段、接口参数或与当前方向无关的边缘问题
- 会改变方向或投入量级的阻塞决策已记录负责人、最晚确认时间和不成立时的影响
