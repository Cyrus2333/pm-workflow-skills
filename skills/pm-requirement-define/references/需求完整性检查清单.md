# 需求定义完整性检查清单

## 可读且可决策

- [ ] 一句话结论能让不了解背景的读者说清问题、推荐方向和结果
- [ ] 关键结论使用完整句子，不只留下字段名、标签或 ID

## 质询判断正确

- [ ] 已先判断任务类型，并读取可直接取得的项目事实
- [ ] 已区分可查事实、用户 / 竞品 / 数据证据缺口、产品决策缺口、PRD 规格缺口和研发实现缺口
- [ ] 没有把所有 `needs-input` 自动转成深度质询
- [ ] 需要质询时已说明硬触发或软信号，而不是只说“需求比较复杂”
- [ ] 边界案例优先使用一个高信息量试探问题，而不是直接开始多轮追问
- [ ] 多轮质询开始前已获得用户确认，用户可以选择停止或保留待确认项
- [ ] 质询问题和建议答案区分事实、用户确认、AI 建议和待验证假设

## 问题成立

- [ ] 已区分事实、问题、目标、用户提出的解法和假设
- [ ] 问题能够从现状事实或明确假设中推导
- [ ] 已说明影响对象、场景、程度和不处理的损失

## 方向可决策

- [ ] 目标与问题一一对应
- [ ] 方向未定时比较过真实可选方案
- [ ] 推荐方向、选择依据、成功依赖和主要风险清楚
- [ ] 已说明关键取舍和会改变选择的临界条件

## 一级范围清楚

- [ ] 已说明涉及的产品端、业务域、主流程和主要角色
- [ ] 已记录已知主要入口、主任务和关键路径；未知部分已明确标记，且不是用“进入下一步”等空泛短语代替
- [ ] 已明确本次包含和不包含什么
- [ ] 已扫描新角色、状态、权限、规则、跨系统、历史数据和合规约束
- [ ] 涉及自动化、AI、第三方、高频调用、资产或不可逆动作时，已扫描成本放大、失败影响、降级后果和责任归属
- [ ] 已判断用户量、调用量或地区扩大 10 倍时，当前规则、人工流程和服务承诺是否仍成立
- [ ] 只标记需要 PRD 深入的维度，没有提前展开规格矩阵

## 可以交给 PRD

- [ ] 已定义方向级成功假设和护栏
- [ ] 会改变方向或投入量级的阻塞决策已解决
- [ ] 已列出 PRD 需要重点展开的规格维度
- [ ] PRD 作者无需重新做产品方向决策
- [ ] 达到 `ready` 后已停止质询，没有继续追问页面字段、接口参数或技术选型

满足以上条件时标记为 `ready`。方向或业务原则未定标记为 `needs-decision`；关键事实不足标记为 `needs-input`。
