# 产品需求深度质询协议

用于判断产品需求是否需要进入交互式深度质询，并在需要时通过依赖有序的问题暴露隐含决策、取舍和重大约束。它是 `pm-requirement-define` 的可选工作模式，不是新的产品决策入口，也不替代研究、数据分析、PRD 或研发 spec。

## 1. 判断目标

不要根据“输入是否详细”判断是否质询。判断的是：

> 当前是否存在会改变问题定义、产品目标、方案方向、一级范围、投入量级或重大风险责任的未决问题？

页面字段、文案、状态枚举、埋点参数、接口字段和技术选型缺失，不足以单独触发深度质询。

## 2. 判断前置动作

在询问用户前先完成：

1. 判断任务是产品决策、证据分析、PRD 展开、更新沟通还是研发实现。
2. 读取用户已提供材料，以及项目内可直接取得的规则、页面、数据和历史决策。
3. 将缺失信息区分为“可查事实”和“必须由负责人决定的事项”。
4. 只有项目事实无法回答且答案会改变产品决策时，才进入质询判断。

不要询问能够从项目仓库、现有文档、数据或用户已经提供的材料中直接获得的信息。

## 3. 缺口分类与路由

| 缺口类型 | 典型问题 | 正确动作 |
|---|---|---|
| 可查项目事实 | 当前入口、既有状态、历史规则是什么 | 读取项目文档、代码或已有材料 |
| 用户证据 | 用户为何失败、不同人群有什么差异 | `pm-research-synthesize` |
| 外部解法证据 | 竞品机制、行业惯例、替代方式是什么 | `pm-competitor-analyze` |
| 数据证据 | 问题规模、漏斗变化、上线效果是什么 | `pm-metrics-review` |
| 产品决策 | 为谁解决、改变什么、选哪个方向、做到哪里 | 深度质询或单问题试探 |
| 产品规格 | 页面行为、状态权限、异常和验收是什么 | `pm-prd-write` |
| 研发实现 | API、字段、队列、存储、算法和技术选型是什么 | 研发 spec |

`needs-input` 不能自动等于“需要质询”。先完成上述分类；证据缺口优先补证据，规格和实现缺口交给下游。

## 4. 触发规则

### 硬触发信号

命中任一项，默认建议启动深度质询：

- 已判断为 `needs-decision`
- 用户直接指定具体功能，但问题、目标或需求主体未确认
- 存在两个以上会产生不同范围、投入或风险的真实方向，尚无选择依据
- 需求方、业务规则或已有材料之间存在会改变方案的冲突
- 未决问题会改变一级范围、业务原则或投入量级
- 涉及资金、资产、核心权限、安全、合规或不可逆动作，责任边界未确认
- 涉及自动化或 AI 判断，但错误发现、复核、解释、纠正和处置责任未确认

### 软触发信号

- 目标用户或场景过于宽泛
- 目标只是“提升体验”“增强能力”“提高效率”等抽象表达
- 没有非目标或保持不变的业务原则
- 只有一个方案，且没有说明为什么选择它
- 没有方向级成功信号
- 关键前提只有需求方主观判断
- 方案依赖人工运营、第三方或高频调用，但没有容量和降级判断
- 规模扩大后现有规则、服务承诺或人工流程可能失效

判断方式：

- 0 至 1 个软信号：通常不启动，继续需求定义。
- 2 至 3 个软信号：先提出 1 个高信息量问题，再重新判断。
- 4 个以上软信号：建议启动深度质询。

硬触发优先于软信号数量。高风险责任缺失不能被其他已明确项抵消。

### 明确不触发

- 已有完整且一致的需求定义，只需要编写 PRD
- 低风险小改动，问题、目标、方向和范围均已确认
- 只是整理、改写、评审或传播已确认内容
- 剩余缺口只涉及页面规格、验收、接口或研发实现
- 用户证据、竞品证据或数据证据不足，但产品决策本身没有等待用户回答的事项

## 5. 三类判断结果

### 不需要

说明为什么可直接继续，以及剩余缺口应由哪个步骤处理。

### 单问题试探

边界不确定时，只问一个最可能改变判断的高信息量问题。回答后重新分类，不自动扩展成完整访谈。

优先选择能够区分以下分支的问题：

- 是解释既有规则，还是改变规则
- 是解决用户问题，还是满足内部管理需要
- 是方向未定，还是只缺规格
- 是缺负责人决策，还是缺外部证据

### 建议深度质询

列出 1 至 3 个触发原因、预计先处理的决策主题和大致轮次。没有用户确认前，不开始连续追问。

## 6. 用户确认门

默认输出：

```markdown
## 质询模式判断

- 判断：不需要 / 单问题试探 / 建议深度质询
- 触发原因：
- 缺口类型：
- 建议动作：
- 预计范围：首轮问题数或主题
```

建议深度质询时，允许用户选择：

- 开始深度质询
- 只问最关键的一个问题
- 将问题记录为待确认并继续形成草案
- 当前不质询

除非用户已明确要求“挑战方案”“持续追问”“grill me”或等价表达，否则不要静默进入多轮质询。

## 7. 质询执行方式

围绕决策依赖从上游到下游推进：

1. 问题是否成立：对象、场景、现状、影响和不处理损失。
2. 目标是否清楚：用户状态、业务结果、非目标和护栏。
3. 方向是否被选择：替代方向、选择依据、成功依赖和临界条件。
4. 一级范围是否明确：包含、不包含、角色、业务域和重大约束。
5. 是否可以进入 PRD：剩余问题属于决策、证据、规格还是实现。

复杂、敏感或高度依赖上一个回答的事项，一次问一个问题。多个问题互不依赖且用户背景完整时，每轮最多 3 个问题；不要把完整检查清单一次性抛给用户。

每轮结束后更新决策树：哪些分支已确认、哪些答案产生了新分支、哪些问题已被项目事实或证据解决。

## 8. 问题格式

每个关键问题尽量包含：

```markdown
### Q-01：决策问题

**为什么现在问：**这个答案会改变什么。

**当前已知：**已确认事实、用户陈述和证据缺口。

**建议答案：**AI 的临时建议及适用前提；没有足够依据时明确不推荐。

**请确认：**需要负责人做出的具体选择。
```

不要用建议答案诱导用户把推断当事实。存在真实选项时可给 2 至 3 个互斥选项，并说明影响；不能合理穷举时使用开放问题。

## 9. 决策记录

启用质询时维护：

| 决策 ID | 决策问题 | 已确认结论 | 依据类型 | 影响范围 | 未决条件 | 负责人 |
|---|---|---|---|---|---|---|

依据类型至少区分：项目事实、用户确认、研究证据、竞品证据、指标证据、AI 建议和待验证假设。

最终需求定义只保留会影响产品结论的决策记录，不把完整聊天逐字复制进正式文档。

## 10. 停止与退出条件

每轮后检查，若不再存在会改变问题、目标、方向、一级范围、投入量级或重大责任的未决问题，立即停止。

满足以下条件可结束：

- 问题能从事实或明确假设中推导
- 目标和非目标与问题对应
- 推荐方向、未选原因和临界条件明确
- 一级范围和重大约束明确
- 剩余缺口已经路由到证据、PRD 或研发 spec
- 可以稳定判断为 `ready`、`needs-decision` 或 `needs-input`

用户选择停止时，保留已确认结论，并将剩余事项标为待确认及其阻塞影响，不强迫完成整个问题树。

## 11. 禁止事项

- 不因输入短、需求复杂或用户说“写 PRD”就自动质询
- 不用追问替代查阅项目事实
- 不把用户回答自动升级为已验证事实
- 不把证据不足的问题改写成产品负责人偏好问题
- 不提前追问页面字段、接口参数和技术选型
- 不为了显得全面而问与当前决策无关的问题
- 不在达到停止条件后继续追问边缘细节

## 12. 质量评估

不要只看总体准确率。持续记录：

- 触发准确率：建议质询的案例中，质询是否真的改变或确认了关键产品决策
- 关键问题召回：重大未决决策是否被识别
- 误触发率：本可直接进入 PRD 或其他 skill，却被拉入质询
- 严重漏判：资金、权限、AI 责任、合规等重大未决问题是否漏过
- 下游返工：PRD 阶段是否仍需重新讨论问题、方向或一级范围

在没有真实案例校准前，不承诺固定准确率。优先保证重大风险不漏判，同时通过单问题试探和用户确认降低普通需求的误触发成本。
