# pm-prototype-deliver

把已确认的方案变成可交互高保真原型并发布。本 skill 是交付面能力：与 `pm-prd-html`（静态阅读原型）、`pm-collaboration-deliver`（文档交付）平级，服务于"让人**操作和体验**方案"的场景——前两者的图服务"让人读懂文档"，本 skill 的原型服务"让人上手方案"。

> 治理标注：本 skill 方法论提炼自首个案例（探索页体验原型，见 training-cases），标注**单案例验证、待第二个同类项目校准**。若后续案例证明适用面太窄，应降级合并为 `pm-collaboration-deliver` 的一份 reference，不保留空壳 skill。

## 优先读取

1. [诉求传达与协作反馈指南](../../shared-references/诉求传达与协作反馈指南.md)（五通道、参照物清单、负面清单、调性传递法——本 skill 打磨期的协作基线，全程遵守）。
2. 需要完整案例背景时，读[案例：探索页体验原型协作全过程](../../training-cases/案例-探索页体验原型协作全过程.md)。
3. 输入为正式 PRD 时，完整读取 PRD 的页面 × 状态规划、页面内容契约与 UX 原型交付配置。
4. 所有需要留档或交接的产物遵守[产物修订记录与版本追溯规范](../../shared-references/产物修订记录与版本追溯规范.md)。

## 工作边界

负责：

- 开工前置三检查（参照物清单 / UI 设计专项技能 / 真实数据可得性）；
- 高保真可交互原型生产：正式前端工程（React/Vite/Tailwind 或项目等价栈），真实交互、真实数据、可发布；
- 真实数据门槛与打磨期协作（按《指南》五通道执行）;
- 原型公开发布、链接嵌入文档，构成"文档 + 原型"交付包；
- 原型与方案文档 / PRD 的双向对齐。

不负责：

- 方向探索与低保真试错——方向未定回到 `pm-requirement-define`；试错技巧见《指南》§7，试错稿不在本 skill 内打磨；
- PRD 派生的静态阅读原型（单文件 HTML 内嵌 SVG）——`pm-prd-html` 的职责，与本 skill 互斥（见"路由互斥"）；
- 文档配图、流程图、页面交互总览——`pm-collaboration-deliver` 的职责；
- 替代最终 UI 设计稿；不规定品牌视觉规范。

## 输入契约（两种顺序都合法）

- **原型先行（方案 → 原型 → PRD 对齐）**：体验驱动型需求的真实工作方式。输入为已确认的方案/规划文档 + 概念锚点 + 参照物清单；原型定稿后触发 PRD 或规划文档的对齐回写。
- **PRD 先行（PRD → 原型）**：输入为正式 PRD（含页面 × 状态规划与页面内容契约）+ 参照物清单。

两种顺序都必须取得：已确认的方向与概念锚点、目标用户与关键体验诉求、参照物清单、真实数据来源、交付面（发布平台与可见范围）。方向、目标或一级范围未确认时，返回 `pm-requirement-define`，不边猜边做。

## 开工前置三检查（硬门槛）

三项逐一确认，任一缺失先补齐再开工；缺失即开工是本 skill 已知的最大返工来源：

1. **参照物清单已就位**：按《指南》§3 模板登记，每项写明"传递的诉求"；
2. **UI 设计专项技能已就位**：环境中已安装 design-taste / frontend-design 或等价能力；视觉品质目标为"有调性"时本项强制——专项能力短板用专项技能补齐，不靠在原流程里反复试错。未就位时必须告知需求方"视觉品质目标不可承诺"；
3. **真实数据可得性已确认**：台账/真实素材的来源、范围与到位时间明确；确认不了来源时，原型只能以"占位演示"身份交付，不得进入视觉打磨。

## 主工作流

```text
开工三检查
→ 前端工程搭建（正式技术栈，非试错稿）
→ 真实数据接入（占位内容全部替换）
→ 结构与流程走通（页面 × 状态 × 主任务）
→ 视觉打磨（调性回路：调性输入 → 专项技能翻译 → 元素级微调）
→ 发布与文档嵌入
→ 对齐回写
```

### 1. 真实数据门槛

占位内容未全部替换为真实数据前，**不进入配色、排版、密度等视觉打磨**——占位数据支撑不了长度、密度与信息分级的判断，会浪费打磨轮次。真实数据同时是 AI 推断的事实约束：台账之外的业务规则不得脑补；发现脑补立即纠正并登记待确认。

### 2. 打磨期协作

反馈按《指南》五通道分类执行：概念锚点防跑偏、参照物优先、元素级指令快速落地、设计判断把控品质、元规则沉淀为长期约束。用户可见文案遵守负面清单四条红线（性别指代/内部口径/营销感/弃案解释）。

### 3. 发布与交付

按需求方指定平台发布为可访问应用并设置可见范围；链接嵌入规划文档或 PRD 的指定位置。发布后必须实际打开链接走一遍核心流程——文件存在、构建成功不等于可交付。

### 4. 对齐回写

原型定稿后，触发方案文档 / PRD 的对齐：原型是体验事实源，文档是决策事实源；两者冲突时登记待确认项并更新主源，不用"以原型为准"或"以 PRD 为准"掩盖冲突。

## 路由互斥

- `prototypeTarget: ux-prototype / wireframe`（静态、设计前评估内容）→ `pm-prd-html`；
- `prototypeTarget: interactive-hifi`（可交互、让人操作体验）→ 本 skill。

同一需求两个档位可以同时成立（静态评审稿 + 可交互演示版），但同一产物不得两边各做一遍；由 `pm-prd-write` 的 UX 原型交付配置显式指定去向。

## 默认输出

- 一个可交互高保真原型（正式前端工程，真实数据驱动）；
- 公开发布链接及其在规划文档 / PRD 指定位置的嵌入；
- 开工三检查记录（含豁免项与需求方确认）；
- 打磨期登记的待确认项与脑补纠正记录；
- 原型与方案 / PRD 的对齐回写结果，或明确的待对齐清单。

## 质量门禁

本 skill 的"完成标准"只表示产物已按方法生成，不等于已通过交接质量审计。

- 打磨讨论期不自动审计，产物标记"未审计"；
- 原型定稿、准备发布或交付相关方时，必须在本次交付前自动调用 `pm-quality-audit`；
- 只有 `PASS`，或用户明确接受带责任人和完成条件的 `PASS_WITH_CONDITIONS`，才可标记为可交付；
- `BLOCKED` 必须回到本 skill 或上游决策，不得用补造事实的方式消除。

## 完成标准

- 开工三检查全部通过，或有需求方确认的豁免记录；
- 原型中全部内容为真实数据或明确标注的占位演示，无 AI 脑补的业务规则；
- 核心流程可在发布链接上真实走通，核心状态可直接到达；
- 用户可见文案通过负面清单检查；
- 文档与原型构成完整交付包，链接已嵌入指定位置；
- 原型与方案/PRD 的冲突已登记待确认，未静默选边；
- 原型定稿已触发文档对齐回写。
