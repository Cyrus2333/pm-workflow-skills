评审入口

问题

单页同时承载试听、录音、投稿、异步合成和失败兜底，状态关系容易分散。

目标

让用户在一个微信 H5 页面内完成试听、录音、投稿、替换、删除和最新作品播放闭环。

范围

一个 PAGE-01 H5 页面及其 6 个信息区、页面状态、异步合成结果和投稿管理。

非目标

不在 PRD 内定义 API、队列、存储、转码、混音算法等研发实现。

摘自正式 PRD 的风险 / 待确认项

        评审简版

        评审简版

        一句话方案

        为业务同事提供一个微信 H5 优先的异步合唱内部 MVP：用户进入固定歌曲活动页后，可试听原唱、录制并提交自己的声音；系统在新增、替换或删除有效投稿后自动重新合成最新合唱作品，页面展示原唱、最新作品、投稿池和合成状态，用于验证“多人异步参与后生成合唱作品”的核心体验是否成立。

        目标与非目标

        类型内容
        目标验证业务同事能否在微信 H5 内顺利完成录音、提交、自动合成和播放最新作品的闭环。
        目标验证合唱成品是否达到“能听出多人一起唱，并具备趣味性”的最低内部体验标准。
        非目标不做实时连麦、不做视频、不做多歌曲后台、不做公开传播、不做评论点赞排行、不做专业修音。

        体验结构

        本期只有 PAGE-01 异步合唱活动页。页面内包含 6 个信息区：

        1. 活动与玩法说明区；
        2. 原唱播放器区；
        3. 最新合唱作品区；
        4. 录音与试听区；
        5. 投稿池区；
        6. 合成状态与提示区。

        主链路：进入页面 → 播放原唱 → 开始录音 → 停止录音 → 试听 → 提交 → 系统自动合成 → 播放最新合唱作品。

        删除链路：用户删除自己的有效投稿 → 投稿池更新 → 系统自动重新合成 → 最新作品更新；若合成失败，页面保留上一版可播放作品并提示失败。

        核心规则

        规则结论
        投稿有效性单个用户默认只保留 1 条有效投稿；再次提交视为替换最新有效投稿。
        删除权限用户只能删除自己的有效投稿；他人投稿不展示删除入口，系统也必须拦截。
        自动合成新增、替换或删除有效投稿后均自动触发重新合成，用户不需要点击“合成”按钮。
        失败兜底合成失败时不误展示为成功；如存在上一版成功作品，继续保留可播放入口。

        MVP 验收底线

        • 至少 2 名业务同事能在微信 H5 中完成录音、提交和播放最新作品。
        • 新增或替换投稿后，页面进入合成中状态，合成成功后最新作品更新。
        • 删除自己的投稿后，最新作品不再包含该投稿，并在合成完成后更新。
        • 微信录音不可用、提交失败、合成失败时均有明确提示，不进入假成功状态。

        待研发 spec 补齐

        • 微信录音授权、素材获取、上传和服务端处理链路。
        • 录音素材存储、转码、混音、任务队列、重试超时和失败告警方案。
        • 页面所需活动详情、投稿提交、投稿删除、合成状态查询等能力的接口规格。
        • 内部体验数据、日志和排查方式。

        • 一句话方案：建设一个微信 H5 优先的单页异步合唱内部 MVP，让业务同事围绕固定歌曲录制并提交自己的声音，由系统在投稿变化后自动生成最新合唱作品。

        • 关键取舍与非目标：本期只做音频和固定歌曲；不做实时合唱、视频、多歌曲后台、公开传播、评论点赞排行和专业修音。
        • 本次交付范围与版本：1 个微信 H5 页面、6 个信息区、投稿新增 / 替换 / 删除规则、合成状态展示和 MVP 验收标准。

        • 最大风险或待决策项：微信 H5 录音链路和服务端音频处理链路需先完成技术预验证；若不可行，需要降级为上传本地音频或仅保留概念 Demo。

        FR-01 页面加载活动信息

        需求结论

        用户进入 PAGE-01 后，页面应加载并展示活动基础信息、原唱可用状态、最新合唱作品状态、当前有效投稿集合、当前用户投稿状态和合成状态。加载成功后，6 个信息区应形成一致的初始状态，让用户知道当前能否听原唱、是否已有最新作品、能否录音提交、自己是否已有投稿。加载失败或关键数据缺失时，页面必须明确提示并提供重试，不得让用户在信息不完整时误以为可以完成提交或播放。

        行为说明

        1. 触发与前提：用户通过内部 H5 链接进入 PAGE-01，页面开始获取当前活动所需的产品数据。活动必须处于可访问状态；若活动已关闭、不可访问或数据不存在，页面进入对应终止态，不展示录音提交主操作。

        FR-03 最新合唱作品播放

        需求结论

        1. 触发与前提：页面加载成功后，IA-03 根据当前合成作品状态展示；每次投稿新增、替换或删除后，该区域随合成状态更新。

        4. 结果与后续路径：用户能播放最新成功作品，或理解为什么暂时没有可播放作品。后续投稿变化会再次进入合成中并最终更新该区域。

        需求结论

        微信录音是 MVP 的主链路。用户点击开始录音后，页面应清楚进入录音中状态；停止后，用户必须能试听本次录音，并可选择重录或提交。授权失败、录音失败或上传失败时，页面应给出明确提示并回到可理解状态，不得展示待试听、已提交或合成中等假成功状态。

        FR-05 提交或替换投稿

        需求结论

        用户在待试听状态下点击提交后，系统应把本次录音保存为该用户在当前活动下的唯一有效投稿；如果此前已有有效投稿，本次提交替换旧投稿。提交成功后，投稿池应立即体现“我的投稿”，最新作品区进入合成中；提交失败时保留本次待试听录音并允许重试，不得展示已提交或合成中成功路径。

        行为说明

        1. 触发与前提：用户已完成录音并处于待试听状态，活动允许投稿，页面没有正在提交的请求。用户点击提交触发提交流程。
        2. 用户可见行为：点击后提交按钮进入加载态并禁止重复点击；页面保留当前录音试听结果，但避免用户在提交中重复重录造成状态混乱。提交成功时展示成功反馈，投稿池出现或更新“我的投稿”，合成状态进入合成中。
        3. 系统与数据行为：系统将本次录音变成当前用户的有效投稿；若已有有效投稿，则旧投稿不再有效且不参与下一版作品。具体提交接口、幂等键、存储路径和事务实现交给研发 spec。
        4. 结果与后续路径：提交成功后进入 FR-07 自动合成链路；提交失败时回到待试听状态，用户可以重试提交或重录。

        FR-06 投稿池展示与删除自己的投稿

        需求结论

        投稿池用于展示当前参与最新合唱的有效投稿集合，并让用户确认自己的声音是否已经参与。列表需要区分“我的投稿”和“其他同事投稿”；只有我的有效投稿展示删除入口。删除成功后，该投稿从有效投稿集合中移除，并触发重新合成；删除失败时，投稿仍保留，页面明确提示失败并允许重试。

        行为说明

        1. 触发与前提：页面加载成功后展示投稿池；提交成功、删除成功或刷新页面时更新投稿池。用户已有有效投稿时，可对自己的投稿发起删除。
        2. 用户可见行为：无投稿时展示空态；有投稿时展示投稿列表和我的投稿标识。我的投稿展示删除入口，点击后建议出现确认提示，避免误删；他人投稿不展示删除入口。
        3. 系统与数据行为：删除成功意味着该投稿不再是有效投稿，且不参与下一版合唱。具体软删除字段、权限校验实现和重复删除处理交给研发 spec。
        4. 结果与后续路径：删除成功后投稿池更新，合成状态进入合成中；删除失败时列表保持不变，用户可重试。

        FR-07 自动重新合成与状态展示

        需求结论

        新增有效投稿、替换有效投稿和删除有效投稿都会自动触发重新合成，用户不需要也不应该操作“合成”按钮。页面需要让用户理解当前最新作品是否正在生成、是否已成功、是否失败，以及当前可播放作品是否为上一版。多次投稿变化连续发生时，页面最终应呈现基于最新有效投稿集合的合唱结果；具体任务去重、排队和并发处理由研发 spec 定义。

        行为说明

        1. 触发与前提：FR-05 提交 / 替换成功或 FR-06 删除成功后，系统进入自动合成链路。页面在 IA-06 展示合成状态，在 IA-03 展示最新作品区对应状态。
        2. 用户可见行为：合成中显示“正在生成最新版本”一类提示；成功后最新作品播放器更新；失败后显示失败提示。若合成中或失败时存在上一版成功作品，页面可保留播放入口，但必须标明它不是本轮最新结果。
        3. 系统与数据行为：系统基于当前有效投稿集合生成合唱作品。PRD 不规定队列、任务 ID、去重、重试、超时、文件存储或混音算法；spec 需保证产品上可识别当前作品状态和最新成功作品。
        4. 结果与后续路径：合成成功后用户可播放最新作品；失败时用户可继续查看投稿池、播放上一版作品（如有），并等待后续投稿变化再次触发合成。

        连续多次投稿变化页面提示正在生成最新版本等待、查看投稿池最终结果应对应最新有效投稿集合最新成功 / 失败产品结果以最新有效集合为准，技术实现交给 spec

        FR-08 空态和失败兜底

        需求结论

        MVP 可以接受部分能力失败，但不能让用户误解当前状态。页面需要覆盖无投稿、原唱失败、录音失败、提交失败、删除失败、合成失败和页面整体加载失败等关键分支，并明确哪些情况下用户可以继续、哪些情况下必须重试或退出。所有失败态都应优先保护用户理解和数据正确性，不为了流程顺畅展示假成功。

        行为说明

        1. 触发与前提：任一关键能力无数据、失败或状态未知时触发对应兜底。兜底应发生在对应信息区，页面级失败才覆盖整页。
        2. 用户可见行为：用户能看到明确状态说明、可行下一步和不可操作原因。例如无投稿时鼓励录音，提交失败时保留试听，合成失败时说明最新作品未生成。
        3. 系统与数据行为：失败态不应产生错误的有效投稿、已删除、最新成功作品或公开传播结果。具体错误码、重试次数和告警通道交给研发 spec。

        6.2 研发验收标准

        AC-01 用户能完成提交并看到自己的投稿

        • Given：用户通过微信打开 PAGE-01，原唱可播放，录音能力可用，活动当前允许投稿。
        • When：用户完成录音、试听并提交。
        • Then：页面提示提交成功，投稿池展示“我的投稿”，系统进入合成中状态；提交失败时页面保留本次试听结果并允许重试，不展示已提交。

        AC-02 再次提交会替换自己的有效投稿

        • Given：用户已经有一条有效投稿。
        • When：用户重新录音并再次提交成功。
        • Then：投稿池中该用户仍只有一条有效投稿，内容以最新提交为准，并触发新一轮合成。

        AC-03 微信录音不可用时不会假成功

        • Given：微信授权失败、录音 API 不可用或上传失败。
        • When：用户尝试录音或提交。
        • Then：页面展示明确失败原因或重试提示，不展示待试听、已提交或合成中成功路径；原唱播放器仍按可用状态展示。

        AC-04 删除自己的投稿后会重新合成

        • Given：用户已有有效投稿，且投稿池中可能还有其他同事投稿。
        • When：用户删除自己的投稿成功。
        • Then：投稿池不再展示该投稿，该投稿不参与下一版合唱，页面进入合成中；合成成功后最新作品更新为不包含该投稿的版本。

        AC-05 合成失败能够明确兜底

        • Given：投稿变化后系统开始合成，且存在“有上一版作品”和“无上一版作品”两组数据。
        • When：本轮合成失败。
        • Then：页面提示最新版本生成失败；有上一版作品时继续允许播放上一版，无上一版作品时展示暂无可播放作品；页面不得把失败版本展示为成功。
