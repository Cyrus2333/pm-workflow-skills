# HTML PRD 交付规范

## 1. 定位

HTML PRD 是“规格 → 阅读版 → 原型评审”的编译结果。

它不是：

- 完整 PRD 的删节版；
- 把 Markdown 原文原样搬进网页；
- 独立的高保真设计稿；
- 第二套产品规则。

它要让读者沿着以下路径理解同一份事实：

```text
问题与目标 → 用户主线 → 页面 × 状态 × 内容 → 原型与用户任务 → 规则与异常 → 评审点 → 需求与验收
```

## 2. 产物框架

单个 HTML 建议包含以下区域：

### 2.1 评审入口

只保留最少的定位信息：

- 要解决的问题；
- 目标和一句话方案；
- 本次范围、非目标和关键取舍；
- 可选的“评审关注”：仅摘取正式 PRD 已写的风险、待确认项、关键决策、验收风险或明确的评审状态，并链接回原章节。

入口不是“完整 PRD 的前置摘要”，不要在此重复功能明细、规则矩阵和验收表。没有可追溯来源时，不生成“评审关注”区块。

### 2.2 用户主线

以用户可理解的步骤表达主流程，并只画关键分支：

- 入口；
- 用户动作；
- 系统结果；
- 主要成功 / 失败 / 人工兜底出口。

分支较多时，按场景分组，不把互斥状态串成一条假流程。

### 2.3 状态板与原型评审

固定三栏：

- 左栏：场景、页面、页面状态；
- 中栏：当前状态的黑白灰 SVG 线框；
- 右栏：用户任务、可见信息、主要动作、系统结果、下一状态、规则 / 功能 / 验收依据。

左栏是状态控制器，中栏是视觉证据，右栏是当前状态的产品语义。三栏只承担当前状态评审，不承载整份 PRD。

### 2.4 需求索引

用一张可读的映射表把状态与正式规格连起来：

| 页面状态 | 用户任务 | 主要动作 | 结果 / 下一状态 | 功能 / 规则 / 验收 |
|---|---|---|---|---|
| 推荐期 | 判断并完成办理 | 点击办理 | 提交中 → 成功 / 失败 | FR-xx / RULE-xx / AC-xx |

ID 是定位辅助，状态名称、用户任务和结果必须可以脱离 ID 阅读。

### 2.5 规格详情

正式 PRD 不删除，但默认按章节折叠或按需展开：

- 第 0—8 章保持原顺序；
- 标题、表格、规则、功能明细、验收、指标、发布、风险和 spec 交接都可回看；
- 阅读入口中的事实不再完整复制一遍；
- 当前状态的追溯项可以直接跳到对应章节或条目。

## 3. 页面 × 状态中间层

页面改版或 UX 评审需求若命中内容完整型原型，额外消费[页面内容契约与 UX 原型](../../../shared-references/页面内容契约与UX原型.md)：原型不是模块示意图，而是当前故事的完整用户可见页面；所有静态文案、动态字段、状态标签、动作和反馈必须可回溯，未确认内容必须标阻塞。

原型和阅读版都从以下结构生产，而不是从 PRD 全文直接猜：

```text
场景
→ 用户任务
→ 页面
→ 页面状态
→ 信息项 / 页面区域
→ 用户动作
→ 系统结果
→ 下一状态
→ 功能 / 规则 / 验收依据
```

独立状态的判断标准：

- 用户看到的信息发生实质变化；
- 主操作或按钮可用性发生变化；
- 页面结构或异常恢复路径发生变化；
- 进入加载、空态、成功、失败、确认、提交中或人工兜底。

只有轻微选中态、禁用态或短文案变化时才可合并，并在中间层记录合并理由。

### 3.1 共享页面骨架

单页多信息区必须同时维护两张表：

| 表 | 回答的问题 | 下游用途 |
|---|---|---|
| 页面信息结构 / 共享页面骨架 | 页面由哪些区域组成，哪些区域跨状态保持，哪些区域按条件显示 | 生成所有状态的共同布局和信息覆盖清单 |
| 页面内容契约 | 每个信息区具体显示哪些静态文案、动态字段、状态标签、动作和反馈 | 生成当前故事的完整用户可见内容，并执行内容覆盖检查 |
| 页面 × 状态表 | 当前状态下哪些区域的内容、可用性、动作和结果发生变化 | 生成状态差异和状态切换上下文 |

原型输出前执行覆盖核对：每个 P0 信息区都有对应区域；每个区域都标明静态、动态、条件或操作反馈；每个状态差异都能定位到区域；没有来源的区域不添加，有来源但未确认的区域标记“待确认”。

因此，中栏原型不是“当前状态的一张简图”，而是“共享页面骨架在当前状态下的完整呈现”。页面信息结构中的 P0 区域应保持相同顺序；每个区域只替换其状态化内容、可用性和动作。右栏补充当前状态下各区域的固定 / 动态 / 条件属性和本状态变化。页面较长时，可使用可滚动长页面或结构化缩略，但不得因视窗限制删除 P0 信息区。

共享骨架同时是布局计算的唯一入口：

1. 维护一个纵向 layout cursor，从页面头部开始顺序放置模块；
2. 每个模块先根据标题、正文实际行数、状态提示、内边距和操作区计算自身高度，再返回新的 cursor；
3. 下一模块的 `y = 上一模块结束位置 + 模块间距`，不得在各状态中分别维护互不相关的绝对 `y`；
4. 状态只提供内容和显隐参数，不复制骨架坐标；内容变化后必须重新计算当前卡片及全部下游模块；
5. 新生成的复杂原型采用 `annotated-v1`：以 `<g data-layout-block="稳定模块名" data-layout-box="稳定卡片名">` 包裹模块，并用唯一直属 `rect[data-layout-boundary]` 标记边界；控件同样完整标注。不得部分标注、部分依赖推断。

### 3.2 移动端视口与滚动

“原型覆盖完整”不等于“全部信息同屏”。移动端页面须按 PRD 中的端类型、逻辑视窗、页面长度、固定区域和状态视口锚点编译：

- 长页保留自然内容高度，在手机框的真实可视区域内纵向滚动；
- P0 信息区必须在同一页面原型中完整可达，不要求同屏可见；
- 状态切换定位到用户刚完成操作或需要理解结果的区域；弹层、确认和加载态保留所在页面上下文；
- 不通过缩小 SVG 内的正文、按钮、间距或触控区域来换取全页同屏；
- 未提供设计资产时采用基础移动端线框基线，并在评审上下文说明参考资产待确认，不伪造高保真产品样式。

### 3.3 复杂体验的编译边界

当分级结论的体验交付复杂度为“复杂”时，HTML 读取 PRD 的相应中间层，不自行推导产品行为：

| PRD 中间层 | HTML 的编译结果 | 不做什么 |
|---|---|---|
| 页面地图与导航契约 | 按“场景 → 页面 → 状态”分组的状态板；必要时给轻量页面地图；故事右栏说明入口、离开、返回和跨页结果 | 不模拟路由实现或凭空增加导航 |
| 状态架构 | 同一状态域内的合法切换；右栏显示当前故事涉及的状态域和代表组合 | 不把独立状态域做成所有组合的截图或无来源开关 |
| 复杂组件行为表 | 列表 / 表单 / 筛选 / 分页 / 批量操作的默认、加载、空、错误、校验、权限和恢复形态 | 不伪造数据、筛选条件、字段或操作结果 |
| 端与布局矩阵 | 同一故事的必要端形态切换或并列预览 | 不把一端缩放成另一端，或额外交付多个 HTML |
| 原型覆盖计划 | 紧凑覆盖台账：计划、实际故事、端形态、豁免及规则 / 验收依据 | 不将台账做成统计仪表盘或重复状态矩阵 |

独立状态域的组合数量较多时，原型只呈现覆盖计划中能证明关键用户任务、异常和端差异的代表组合。其他组合继续以状态架构、规则和验收为主源；HTML 要能定位这些依据，但不能用可交互控件假装它们都已被原型验证。

### 3.4 多页面、复杂组件与多端故事

- 多页面故事应表达用户可见的入口、页面间结果、离开和返回落点；跨页保留的信息只按 PRD 的导航契约展示。
- 表单、列表和批量任务先保持页面信息结构与正常阅读尺度，再在当前状态替换动态内容；不把复杂页面简化成“一个按钮 + 一句说明”。
- 表格和列表可在设备框或阅读壳层中滚动；不能以极小字号压缩所有列。PRD 未定义的列隐藏、筛选默认值、排序或分页策略均不补造。
- 多端差异只在端与布局矩阵要求时额外成图。差异应真实反映信息层级、布局、输入或操作方式，而不只是设备外框变化。
- 一个状态故事的右栏只解释当前页面 / 状态 / 端形态，不重复其他页面的完整规则；涉及多个状态域时，列出当前代表组合和可定位依据即可。

## 4. 原型与现实约束

输入不仅是 PRD，还包括：

- 现有产品截图或页面；
- 设计规范、组件参考和交互习惯；
- 目标设备、页面尺寸和端类型；
- 目标用户的年龄、阅读能力、使用环境和信息密度约束；
- 已确认的文案、主操作和异常兜底。

默认原型是黑白灰低保真线框：

- 只表达布局、信息层级、用户可见文案、按钮和状态；
- 不使用品牌色、语义色、渐变、阴影、插画、照片和装饰性高保真细节；
- 不把内部状态码、接口字段、队列、存储、算法或评审说明画给用户；
- 异常页不凭空增加复杂操作；
- 老年用户、弱网或低端设备等约束必须在字号、文案、密度和操作数量上体现。

移动端线框优先复用既有产品的组件和尺寸。没有参考时，正文、标题、主操作和触控区域仍要按正常移动端阅读与操作尺度表达；HTML 阅读壳层可因窄屏整体适配，但不得反向改变原型的逻辑字号、控件尺寸或信息层级。

## 5. 去冗余规则

- 同一事实只在一个位置完整表达；
- 入口区只做定位，状态右栏只展示当前状态，规格区承载完整细节；
- 不重复生成“导览说明、设计原则、评审提醒、注意事项”段落；
- 不把内部 ID 作为主要阅读语言；
- 不把原型中的旁白、规则解释或追溯说明误当作用户文案；
- 不为了填满页面而增加卡片、标签、徽章、统计数字或泛化建议。

## 6. 阅读界面规范

### 6.1 以文档为主，不以仪表盘为主

HTML 的基础形态是可阅读的长文档，而不是项目看板：

- 左侧固定章节树，分为“阅读版”和“正式规格”两组；支持收起，当前阅读位置高亮；
- 中间为连续阅读画布，评审入口、用户主线、状态评审、需求索引和规格详情按顺序展开；
- 右侧上下文只出现在原型评审区，随当前页面状态切换；
- “规格详情”是阅读结构中的第 6 节，正式 PRD 的各个折叠章节作为其子项编号为 `6.1`、`6.2`……，不能再出现一组看起来与阅读版并列的 0、1、2 目录；
- 章节之间用留白和细分隔线建立层级，不把每个章节都做成有阴影的大卡片；
- 默认使用中性底色和少量强调色。强调色只用于当前导航、当前状态和关键定位，不承担装饰作用。

### 6.2 状态评审采用“故事”模型

每个“页面 × 状态”是一个独立故事；命中内容完整型 UX 原型时，故事必须同时消费页面内容契约，而不是一组只画模块骨架的散落原型截图：

| 区域 | 只承担的职责 | 不应该承载的内容 |
|---|---|---|
| 左侧状态栏 | 按场景、页面、状态选择当前故事 | 全量规则、验收正文、解释段落 |
| 中间预览 | 当前状态的 SVG 线框和设备框 | 内部 ID、产品旁白、评审意见 |
| 右侧上下文 | 当前任务、可见信息、动作、结果、下一状态、追溯 | 其他状态的细节、完整 PRD 章节 |

只有状态本身可被合法切换的变量，才可以做成控制器；例如加载、成功、失败、权限、是否已有内容。不要为了“交互感”添加没有来源的开关或模拟行为。

复杂需求先按场景和页面组织故事，再在页面下列出当前可评审的状态。跨页跳转、返回落点、独立状态域和端形态来自 PRD 中间层；原型控制器只选择已规划的故事或端形态，不能成为模拟业务后台的自由操作面板。

### 6.3 流程图采用结构化输入

- 先维护“场景 → 任务 → 状态 → 动作 → 结果”的中间层，再产出流程图和状态图；
- 主流程优先展示 5 到 7 个关键步骤；复杂分支按场景拆开，不做无法阅读的全量节点网；
- 最终图形内嵌为 SVG 或以轻量 HTML 结构呈现，不能依赖外部图形运行时；
- 任何流程节点都必须能回到对应状态或正式规格。

### 6.4 参考模式与不采用项

| 参考模式 | 可借鉴内容 | 本 skill 的落地方式 | 不采用原因 |
|---|---|---|---|
| Docusaurus / Starlight 类文档站 | 分组侧栏、当前章节定位、可收起导航、连续正文 | 内嵌 CSS / JS 的固定左侧导航和章节折叠 | 最终交付是单文件，不引入站点构建和运行时 |
| Storybook | 一个可复现 UI 状态对应一个 story，预览与上下文并列 | 页面 × 状态作为状态控制器的最小单位 | 不把产品原型做成组件开发环境或添加无来源的 controls |
| Mermaid | 从文本结构生成可维护的流程图与状态图 | 先生成中间层，再内嵌 SVG / 轻量图形 | 不在最终 HTML 依赖 Mermaid CDN 或完整运行时 |
| Penpot / 设计系统 | SVG、CSS、组件、token 和设计资产可作为协作事实源 | 读取截图、设计稿、组件和 token 约束原型 | 不把高保真设计稿复制进评审 HTML |
| React Flow / 白板工具 | 节点、连线和缩放画布适合探索复杂关系 | 仅借鉴节点图的建模思路 | 单个评审文档不需要一个可编辑无限画布 |

## 7. 真实渲染验收

必须浏览器渲染后检查：

### 内容

- 首屏能理解需求和可追溯的评审关注；源 PRD 没有相关内容时不强行补充；
- 主流程、关键分支和状态板能顺着阅读；
- 重要规则、验收和待确认项就近可找；
- 页面状态与原型、功能、规则、验收无断链。
- 复杂体验的页面地图、状态架构、复杂组件行为、端与布局矩阵和覆盖计划均已消费；未命中的中间层应说明不适用或回退原因。
- 覆盖计划中每个应成图组合都有实际故事和端形态；豁免组合可定位到状态架构、规则或验收依据。
- 页面信息结构中的所有 P0 区域在原型中均可辨识；
- 多个状态沿用同一共享页面骨架，没有把完整页面缩减成单一动作卡片；
- 固定、动态、条件和操作反馈在原型与右栏上下文中区分正确。
- 长页在设备框内可滚动，P0 区域完整可达；没有为同屏展示而缩小移动端内容。
- 状态切换后的视口位置、固定区域和弹层上下文符合原型规划。

### 视觉

- 原型是黑白灰线框；
- 原型没有解释性文本或内部术语；
- 页面、表格、状态切换、侧栏和长文档没有溢出 / 裁切；
- 桌面端和窄屏均可读；
- 长表格、复杂表单和批量操作没有通过极小字号、裁切或横向溢出伪装完整；多端形态没有因缩放而失真。
- 视觉层级服务阅读，不靠装饰制造信息量。
- 对状态栏中的每个 story / state 分别完成几何检查，而不是只看首态：文字不得超出所属卡片，不得与其他文字或控件重叠；卡片不得互相覆盖；模块标题不得压住上一模块；任何用户可见内容不得超出 SVG `viewBox` 或声明的可滚动页面边界。
- 禁用脚本时的初始静态 SVG、`data-initial-state`、脚本启动后的 active 状态和重新选择首态后的 SVG 必须一致。初始 host 为空、首态声明不一致或加载后结构跳变均为阻断问题。
- 装饰、蒙层、角标等合法叠加必须在最小元素或分组上显式写 `data-layout-allow="overlap"`；确需越界时追加 `overflow`。豁免只作用于该元素及其子元素，不允许全局忽略普通内容冲突。

### 交互

- 章节导航固定且可收起；
- 状态切换更新原型与上下文；
- 追溯项能够定位到规格详情；
- 规格章节按需展开，不要求读者回到 Markdown。
- 复杂多页面故事的入口、离开、返回落点和状态切换上下文一致；切换端形态或状态后不丢失当前故事语义。

## 8. 交付约束

- 每个用户项目只交付一个 HTML；
- CSS、JavaScript、流程图和 SVG 全部内嵌；
- 不生成 PNG、独立 SVG、外部数据文件或第二份评审稿；
- 模板与案例放在 `skills/pm-prd-html/` 内，不在项目根目录建立独立示例目录。

## 9. 自动布局门禁

生成完成后使用 [SVG 布局校验器](./svg-layout-validator.md) 对单文件 HTML 做浏览器实测。校验器必须枚举所有 `[data-state]`，输出状态、元素和冲突类型，并在存在未豁免阻断项时返回非零退出码。

浏览器验证发现问题后，修复生成逻辑或共享骨架并重新渲染全部状态，直到没有阻断级错位。未执行浏览器渲染或等价的真实字体几何验证时，交付结论最高只能是 `PASS_WITH_CONDITIONS`；静态标签检查或字符串规则不能替代视觉几何验证。

HTML 必须按校验器规范维护 `data-rendered-state` 与 `data-render-status`，每次切换后只保留一个目标 SVG，并等待状态 ready 与 `document.fonts.ready`。根 SVG 明确选择 `flat-v1` 或 `annotated-v1`；嵌套 SVG、`foreignObject`、部分标注、非法 allow 或不支持的文字结构直接阻断。运行环境或依赖缺失导致退出码 2 时，视为“验证未完成”，不能作为布局通过证据。
