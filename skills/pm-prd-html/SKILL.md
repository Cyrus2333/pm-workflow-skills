# pm-prd-html

`pm-prd-html` 是从“产品规格”到“团队可消费交付物”的编译层。

它解决的不是 PRD 写得不完整，而是让读者不必先读完一份长 Markdown、再靠内部 ID 拼接页面、状态、规则和原型之间的关系。

## 一、核心目标

把同一份正式 PRD 编译成一份可顺着阅读、可切换状态、可回到具体规格的 HTML：

```text
问题与目标
  → 用户主线
  → 关键页面与页面状态
  → 页面状态对应的原型与用户任务
  → 影响体验的规则与异常
  → 评审需要确认的事项
  → 具体需求、验收与研发交接
```

HTML 不是 PRD 摘要，也不是把 Markdown 原文整体塞进网页。它应当重新组织阅读顺序，同时保留从阅读版回到正式规格的路径。

## 二、职责边界

负责：

- 从正式 PRD、原型规划和设计约束中建立可消费的阅读结构；
- 建立“场景 → 用户任务 → 页面 → 页面状态 → 信息项 → 用户动作 → 系统结果 → 下一状态”的中间层；
- 依据页面状态生产必要的 SVG 线框原型和主流程 / 异常流程图；
- 将当前状态对应的用户任务、信息、动作、结果、规则、验收和追溯放在同一阅读上下文；
- 在一个 HTML 内提供章节定位、状态切换、规格定位和一致性检查；
- 进行真实渲染后的阅读验收，而不是只检查 Markdown 或 HTML 标签。

不负责：

- 重新判断需求是否值得做、重选方案、改变范围或补造业务规则；
- 替代 `pm-prd-write` 编写功能、规则、验收或研发 spec；
- 把高保真设计、品牌视觉或可上线前端产品当成原型交付；
- 生成多个 HTML、独立原型文件或 PNG；
- 用 HTML / SVG 自己创造 PRD 中没有确认的状态、按钮、异常出口或文案。

## 优先读取

优先读取：

1. 正式 PRD：问题、目标、范围、非目标、方案、功能、规则、异常、验收、指标、发布、风险和 spec 交接；
2. `2.5 原型范围与页面状态规划`（旧版 PRD 可能仍标为 `2.4`）；
3. 页面信息结构、页面状态与操作矩阵、场景—原型关联；体验交付复杂度为“复杂”时，还读取页面地图与导航契约、状态架构、复杂组件行为表、端与布局矩阵及原型覆盖计划；
4. 现有产品截图、已确认设计稿、组件规范、页面尺寸和端类型；
5. 命中内容完整型 UX 原型时，读取[页面内容契约与 UX 原型](../../shared-references/页面内容契约与UX原型.md)，并把它视为页面用户可见内容的主源；
6. 目标用户特征、阅读能力、信息密度和产品已有交互习惯；
7. 项目 `AGENTS.md`、根 `README.md` 和 [HTML PRD 交付规范](./references/HTML PRD交付规范.md)。

## 输入契约

原型生产至少需要这些信息：

- 用户任务；
- 页面与页面状态；
- 每个状态的可见信息、主要动作、系统结果、下一状态；
- 单页多信息区的共享页面骨架：所有状态保持的信息区、状态变化的信息区、条件显示区、主操作区和各自的数据 / 规则来源；
- 命中内容完整型 UX 原型时，页面内容契约：所有用户可见静态文案、动态字段、状态标签、按钮、placeholder、空态、错误和操作反馈，以及展示条件、缺省、长度 / 密度、代表性数据和追溯 ID；
- 页面尺寸、端类型、目标用户，以及页面是单屏、可滚动长页、分页还是弹层；
- 移动端的固定 / 吸顶 / 吸底区域、每个状态的视口锚点、信息密度和可访问性约束；
- 已确认的产品形态、组件习惯或参考资产；
- 状态与功能、规则、流程、验收的关联；
- 已确认、假设、待确认和不适用内容。

缺失时标记阻塞并回到 `pm-prd-write`，不要用通用页面经验猜测。

当 `pm-requirement-grade` 标记体验交付复杂度为“复杂”时，上述基础输入之外，按命中的信号消费以下 PRD 中间层：

- 多页面或跨页状态：页面地图与导航契约，包含入口、出口、返回落点、共享壳层、跨页传递对象和保留状态；
- 多个独立状态域或并行异步：状态架构，包含状态域、互斥 / 独立关系、优先级、组合限制和状态所有者；
- 列表、表单、筛选、分页、批量或编辑：复杂组件行为表，包含默认、加载、空、失败、校验、权限和恢复；
- 多端差异：端与布局矩阵，包含各端需要独立评审的形态与差异；
- 状态组合较多：原型覆盖计划，包含需要成图的代表组合、规则 / 流程覆盖的豁免组合及理由；
- 内容完整型 UX 原型：页面内容契约、页面 × 状态 × 内容覆盖、代表性数据和内容覆盖检查。

这些是 `pm-prd-write` 的产品事实，不在 HTML 阶段补写。缺失、互相冲突或不足以确定原型覆盖时，返回 `pm-prd-write`，而不是用通用控件、路由或数据补齐。

## 四、执行流程

### 1. 建立事实与约束包

先区分：

- 正式 PRD 事实；
- 已确认的页面 / 原型事实；
- 视觉和现实约束；
- 假设；
- 待确认项；
- 不属于本次交付的内容。

外部原型或截图只能补充页面形态和交互习惯，不能默默覆盖 PRD 的产品规则。发生冲突时，把冲突显示为待确认项，并回到 PRD 主源处理。

### 2. 建立页面 × 状态中间层

不要从 PRD 全文直接画图。先整理为：

```text
场景
  → 用户任务
  → 页面
  → 页面状态
  → 信息项 / 页面区域
  → 用户动作
  → 系统结果
  → 下一状态
  → 功能 / 规则 / 验收依据
```

原型的基本单位是“页面 × 状态”，不是 PRD 章节，也不是页面名称。加载、失败、空态、成功、确认、提交中、人工兜底等，只要改变用户可见信息或主要动作，就应作为独立状态或在状态清单中明确合并理由。

单页多信息区必须再建立“共享页面骨架 → 状态差异”的关系：先读取第 2.3 节页面信息结构、第 2.4 节页面内容契约和第 2.5 节共享页面骨架 / 原型规划，再把每个状态的变化映射到具体信息区。共享信息区不能因为状态原型只强调某个动作而消失；页面较长时，生成正常字号、可在设备框内滚动的长页面，不用缩小字号的一屏缩略图代替整页。

体验交付复杂度为“复杂”时，再建立**编译台账**，而不是把所有可能状态平铺为截图：

- 页面地图决定故事按“场景 → 页面 → 状态”如何分组，以及每个故事的进入、离开、返回和跨页可见结果；
- 状态架构决定哪些状态能在同一故事中切换，哪些独立状态域只按原型覆盖计划呈现代表组合；不做独立状态域的笛卡尔积；
- 复杂组件行为表决定列表、表单、筛选、分页、批量和编辑的当前可见行为；不伪造行数据、筛选条件或批量结果；
- 端与布局矩阵决定同一故事是否需要单独的桌面 / 移动端形态；端差异不能靠拉伸或缩小另一端原型伪装；
- 原型覆盖计划决定实际 SVG、流程 / 规则覆盖和豁免理由。每个计划项都关联到实际故事或规格依据，作为后续验收台账。

### 3. 编译阅读版

默认使用以下阅读顺序，但根据需求复杂度删减空章节：

1. **评审入口**：问题、目标、方案一句话、范围、非目标；如正式 PRD 已有风险、待确认项或关键决策，再生成带原文定位的“评审关注”；
2. **用户主线**：主流程、关键分支和影响体验的规则；
3. **页面地图与状态板**：场景 / 页面 / 状态选择器；复杂多页面时先给轻量页面地图和跨页结果，再进入状态故事；
4. **原型评审**：左侧状态控制器，中间 SVG 线框，右侧当前状态事实上下文；
5. **需求索引**：页面状态与功能、规则、验收的可读映射；复杂需求按需附上原型覆盖台账，只列计划、实际故事、豁免和依据；
6. **规格详情**：正式 PRD 的章节内容按需展开，而不是首屏堆叠；
7. **待确认与一致性**：只列阻塞、冲突、缺失映射和真实阅读验收结果。

阅读版可以重新组织内容，但不能丢失正式规格。完整规格应在同一个 HTML 内可展开、可定位、可回看。

### 4. 生产 SVG 原型和流程图

#### 原型视觉

默认使用黑白灰低保真线框：

- 表达页面结构、信息层级、用户可见文案、按钮、禁用、加载、失败和恢复入口；
- 颜色只允许灰阶，不使用品牌色、语义色、渐变、阴影、照片或装饰性视觉；
- 视觉参考只用于复用已有产品的结构、设备形态、组件习惯和信息密度；
- 面向老年用户、低网速、弱设备等现实约束，要在字号、密度、文案长度和操作数量上体现。

#### 移动端视口与交互基线

- 先按 PRD 已确认的逻辑视窗生成；未确认时使用常见移动端宽度作为线框基准，并在评审上下文标记为待确认；
- 页面是长页时，SVG 保留自然内容高度，设备框模拟真实可视高度并支持纵向滚动；不得为了让所有区域同时可见而压缩字号、按钮或间距；
- 状态切换按 PRD 的视口锚点定位到用户刚完成动作或最需要理解结果的区域；弹层、确认和加载态保留其所在页面上下文；
- 优先复用已有产品的字号、间距、组件和触控习惯。缺少设计资产时，低保真线框至少保证正文、标题、主操作和触控区域可正常阅读和点击，不能用极小文字或不可操作的伪按钮填满页面；
- 视觉缩放只可以用于 HTML 阅读壳层在窄屏中的整体适配，不能改变 SVG 内的移动端逻辑字号、控件尺寸或信息层级。

#### 原型文字

SVG 内只放用户真正看得到的内容：

- 页面标题、字段、状态文案、按钮、提示、必要占位符；
- 不放“评审说明”“需求 ID”“规则解释”“追溯关系”“内部状态码”“接口字段”或生成者旁白。

#### 原型可靠性

每个主要按钮、关键状态和异常出口都必须能回到中间层和正式 PRD；发现逻辑缺口时停止画图，回到 `pm-prd-write`，不能靠原型把缺口遮过去。

SVG 页面必须使用可推导的纵向布局，而不是把每个模块当成互不相关的绝对坐标集合：

- 优先使用“共享页面骨架 + 顺序布局 / layout cursor”。先计算当前模块的内容高度、上下内边距和操作区高度，再推进 cursor；后一个模块的 `y` 必须由前一个模块的结束位置与间距计算，不能独立写死一个会在文案变化后失效的坐标；
- 同一页面的所有状态复用同一个骨架生成函数或同一组布局 token，只替换状态相关的文案、数据、可用性、动作和条件区；不得为每个状态复制并手调整套坐标；
- 卡片高度由标题、正文（含换行后的实际行数）、状态提示、内边距和操作区共同决定。修改内容时必须重新计算卡片高度及所有下游模块位置，不能只替换 `<text>`；
- 新生成的复杂 SVG 使用受控 `annotated-v1` 契约完整标识 block、box、boundary 和 control；简单既有扁平示例可使用受限 `flat-v1`。嵌套 SVG、`foreignObject`、部分标注和未声明的复杂文字不在支持范围，必须由校验器阻断，不能降级为猜测性检查。具体属性见布局校验器规范。

复杂交互的原型仍以“用户可见结果”为边界：列表要表达加载、空、失败、选择和恢复，表单要表达必填、校验、提交和返回，筛选 / 分页 / 批量操作要表达已确认的入口、当前结果和失败恢复。不要把组件实现、无来源的筛选项、示例业务数据或为演示而加的控制器画进原型。

#### 原型信息结构最低要求

- 页面信息结构中的所有 P0 信息区都要在原型中有可辨识且可滚动到达的区域；状态不展示时，必须有明确的产品条件依据；不要求所有区域同时出现在一个手机视窗；
- 每个区域标记其实际职责：静态信息、动态数据、条件信息或操作反馈；这些标记放在右侧评审上下文，不写进用户可见 SVG；
- 多个状态使用同一页面骨架，状态差异只改变对应区域的文案、数据、可用性和动作；不得每个状态重新发明一套互不相同的页面布局；
- 原型中的信息区标题、关键文案和按钮应优先使用 PRD 已确认内容；缺少内容时显示待确认，不用通用占位文案填充；
- 原型质量验收增加“结构覆盖”项：逐个核对 P0 信息区、共享信息、状态差异、条件展示、主操作和异常出口。

### 5. 装配单一 HTML

- CSS、JavaScript、流程图和 SVG 全部内嵌；
- 不依赖 PNG、外部图片、外部 CSS、外部 JS 或数据文件；
- 固定左侧章节导航，支持收起；移动端可变为抽屉；
- 状态切换只更新当前原型和对应上下文，不重新创造另一套内容；
- 复杂多页面时，状态栏按场景和页面分组；右栏同时说明当前故事涉及的状态域、进入 / 离开结果和代表组合，未单独成图的组合只链接到状态架构或规则依据；
- 多端需求在同一个 HTML 的当前故事中切换已确认端形态，或并列展示必要端形态；不能把移动端等比缩小 / 放大为桌面端，也不能生成第二份 HTML；
- 移动端设备框保持真实可视高度；长页内容在框内纵向滚动，状态切换可按视口锚点重置滚动位置；
- 追溯 ID 作为辅助定位，主要阅读路径使用人类可读名称和完整句子；
- 规格详情按章节折叠或分页式展开，避免完整正文与阅读版同时展开造成重复噪音；
- 不增加无事实来源的“导览、原则、提示、注意、评审口号”等段落。
- “评审关注”不是模型自由发挥的总结：只摘取正式 PRD 已写的风险、待确认项、关键决策、验收风险或明确的评审状态；每条保留可跳转的源章节定位。源文档没有这些内容时省略整个区块。
- 原型覆盖台账只在复杂体验交付命中时显示，保持紧凑：计划覆盖、实际故事、端形态、豁免组合及规则 / 验收依据即可；它不是页面统计面板，也不重复完整状态表。

#### 阅读壳层与交互模式

最终 HTML 借鉴成熟文档产品和组件文档的职责划分，但不引入它们的运行时或构建依赖：

- **文档壳层**：左侧是固定、可收起的章节树；中间是连续的阅读画布。导航按“阅读版”和“正式规格”分组，当前章节高亮，不能把整份目录和每个二级标题同时默认展开；
- **目录编号**：阅读版为 1—5，`6. 规格详情` 是正式 PRD 的容器；其下所有可展开章节统一编号为 `6.1`、`6.2`……，不要再用另一套从 0 或 1 开始的平行编号；
- **状态故事**：每一个“页面 × 状态”是一个可切换的故事。左栏只负责选择故事，中栏只显示该故事的 SVG，右栏只显示该故事的任务、可见信息、动作、结果和追溯；不要把所有状态的说明并列堆在同一屏；
- **流程图**：流程和状态图从中间层生成。主线用少量步骤表达路径；有分支时按场景拆图或明确分支，不把所有互斥状态硬接成一条长链；
- **设计资产**：已有截图、组件库、设计 token、Figma / Penpot 设计稿是原型的上游约束。它们决定组件结构、密度、尺寸和交互习惯，不等同于在 HTML 中嵌入高保真设计资产。

不要为了模仿产品后台而把阅读版做成仪表盘。阅读区默认是平面文档：少量分隔线、清晰层级、有限的强调色；边框、圆角、徽章、阴影和统计数字只在确有定位作用时使用。状态评审区是唯一允许呈现“工具面板”结构的区域。

文案语言跟随源 PRD 和团队工作语言。不要在中文 PRD 的首屏添加泛化英文标签、功能徽章或生成者口号来填补视觉空间。

### 6. 真实阅读验收

必须在实际浏览器渲染后检查：

- 首屏能否回答“这是什么需求、为什么做、需要关注什么”；若源 PRD 没有可追溯的评审关注，则不强行生成；
- 用户主线能否从入口读到结果和关键异常；
- 页面状态是否能看全，状态切换是否与右侧上下文同步；
- 移动端长页是否使用正常逻辑字号、间距和触控区域，而非缩放到单屏；固定区域、弹层和状态锚点是否符合 PRD；
- 原型中的按钮、文案和状态是否来自 PRD；
- 当前状态的规则、验收和待确认项是否能就近找到；
- 图、流程、正文和验收是否互相矛盾；
- 复杂需求的页面地图、跨页返回、状态域、组件行为、端形态和原型覆盖是否与 PRD 中间层逐项对应；
- 原型覆盖计划中的每个应成图组合是否实际存在，未成图组合是否有规则 / 流程依据且未被误画为用户可操作开关；
- 章节导航滚动后是否仍可用；
- 桌面端、窄屏、长表格、复杂表单与批量操作是否可读，是否出现横向溢出；
- 读者是否仍需要频繁回到 Markdown 才能理解关键内容；
- 是否出现过多解释性文本、重复卡片、无依据的设计细节或泛化建议。

几何校验必须覆盖状态栏中的**全部 story / state**，不能只检查默认首屏。逐个状态渲染稳定后，至少检查：

- 文字是否超出所属卡片，或与其他文字、控件重叠；
- 卡片之间是否重叠，模块标题是否压住上一模块；
- 内容是否超出手机视口的可滚动内容范围或 SVG `viewBox` 边界；
- HTML 中禁用脚本时可见的初始静态 SVG、声明的 `data-initial-state`、脚本运行后的 active 状态和再次切换到首态后的 SVG 是否一致，避免加载前后跳变；
- 合法蒙层、装饰、角标只按元素上的显式 `data-layout-allow` 放行，普通卡片和正文不得借用豁免。

生成后运行 [SVG 布局校验器](./references/svg-layout-validator.md)。校验环境要求 Node.js ≥20、Skill 内锁定的 Playwright 和 Chromium；CLI 退出码 2 表示验证未完成。检测到阻断级几何问题时必须修复、重新渲染并重新执行，直到全部状态无阻断级错位。缺少依赖、浏览器、字体完成信号或其他原因导致浏览器验证未完成时，质量结论最高只能是 `PASS_WITH_CONDITIONS`，不得声称完全可交付。

## 质量门禁

本 skill 的“完成标准”只表示产物已按方法生成，不等于已通过交接质量审计。

- 讨论、探索或用户明确要求“只先给初稿”时，不自动审计，并明确标记“未审计”；
- 当输出达到 `ready`、给出最终分级、准备交给设计 / 研发 / 测试 / 运营，或用户要求复核 / 验收时，必须在本次交付前自动调用 `pm-quality-audit`；
- 只有 `PASS`，或用户明确接受带责任人和完成条件的 `PASS_WITH_CONDITIONS`，才可标记为可交接；
- `BLOCKED` 必须回到本 skill、证据 skill 或上游决策，不得用补造事实的方式消除；
- 是否需要把审计报告写入项目根目录 `quality-audits/`，按用户是否要求留档 / 交接附件决定。

## 默认输出

用户项目只交付一个文件：

```text
prd.html
```

本 skill 的模板和验证案例归档在 `skills/pm-prd-html/examples/`，不在仓库根目录创建平行的示例交付目录。

## 完成标准

- 只有一个 HTML 交付物，SVG 内嵌且无 PNG；
- 阅读版能顺着“问题 → 主线 → 状态 → 规则 → 评审点 → 规格”理解；
- 页面 × 状态中间层清楚，重要状态和异常没有无故遗漏；
- 复杂体验只按 PRD 的页面地图、状态架构、组件行为、端与布局矩阵和原型覆盖计划编译；代表组合、豁免组合和实际 SVG 均可核对；
- 页面、状态、动作、结果、功能、规则和验收可以双向定位；
- 原型遵循现有产品形态、设备、用户、滚动 / 固定区域和信息密度约束；
- 原型为黑白灰线框，只有用户可见文字；
- 正式 PRD 信息仍完整可回看，但不在首屏堆成原文长页；
- HTML 没有第二套业务规则、无依据的解释性内容或视觉噪音；
- 内容完整型 UX 原型的每个用户可见内容都有 PRD 主源，HTML 能报告内容覆盖、待确认和阻塞，不依赖设计稿补齐页面信息；
- 真实浏览器验收通过；发现产品逻辑问题时明确回退上游。
- SVG 布局校验覆盖全部 story / state，初始静态画面与运行时首态一致，且无未豁免的阻断级几何冲突；未完成浏览器或等价视觉验证时只可标记 `PASS_WITH_CONDITIONS`。
