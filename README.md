# PM Workflow Skills

面向 Codex 的产品工作流 skills 集合。它不是一组彼此独立的写作模板，而是一条从“模糊提需 / 证据材料”到“分级治理 / 交付规格 / 上线复盘”的可衔接工作流。

核心顺序：**需求定义 / 决策充分性判断 → 证据补齐（按需并回流） → 需求分级与交付路由 → 产物质量审计 → PRD / 单文件 HTML 协作交付 / AI Coding 任务边界 → 更新同步 → 指标复盘与迭代**。

这套 workflow 采用“两层完成定义”：skill 负责生成产物，`pm-quality-audit` 负责判断产物是否达到交接门槛。讨论 / 草稿阶段默认不打断创作；一旦输出 `ready`、准备交接或用户要求验收，原 skill 会在本次交付前自动调用审计。没有审计证据时，只能说“已生成”，不能说“已验证可交付”。审计报告默认回在对话中，需要留档时写入项目根目录 `quality-audits/`。

## Skills 一览

| Skill | 何时使用 | 输出交给谁 |
|---|---|---|
| `pm-requirement-define` | 想法、口头提需、问题、方向或一级范围尚未确认 | 交给 `pm-requirement-grade` 做等级和交付路由 |
| `pm-requirement-grade` | 需求定义基本完成，需要判断 L0/L1/L2/L3/H、AI Coding 是否允许、交付门槛和体验交付复杂度 | 交给 AI Coding、协作评审、`pm-prd-write` 或 hotfix 流程；若要在设计前评估完整页面效果，还传递“内容完整型 UX 原型”门槛 |
| `pm-prd-write` | 已确认问题、目标、方向、一级范围和分级结论，需要展开可评审、可实现、可验收的 PRD；涉及页面体验时形成页面 × 状态、共享骨架及移动端视口 / 滚动约束；要求设计前评估页面效果时增加页面内容契约和页面 × 状态 × 内容覆盖；复杂时按信号补齐体验中间层 | 交给 `pm-prd-html`、设计、研发 spec、测试、发布与 `pm-update-write` |
| `pm-prd-html` | 已有确认后的 PRD，需要生成一份便于团队阅读和评审的单文件 HTML | 输出按“问题 → 主线 → 页面状态 → 内容 → 原型 → 规则 → 评审点”组织的阅读版 `prd.html`，默认编译达到 UX 交接粒度的静态优先 SVG 原型；命中内容完整型 UX 原型时执行内容覆盖检查；复杂时编译代表组合、端形态和覆盖台账，并保留可按需回看的完整规格；发现产品逻辑问题时回到 `pm-prd-write` |
| `pm-prototype-deliver` | 方案或 PRD 已确认，需要让人操作和体验方案（`prototypeTarget: interactive-hifi`） | 开工三检查（参照物 / 设计专项技能 / 真实数据）后生产高保真可交互原型，发布为可访问链接并嵌入文档，原型定稿后触发文档对齐回写；不做静态阅读原型（`pm-prd-html` 职责，互斥） |
| `pm-research-synthesize` | 有访谈、问卷、客服、可用性测试或开放文本，需要提炼用户证据 | 交回 `pm-requirement-define`，不直接替代产品决策 |
| `pm-competitor-analyze` | 需要比较外部解法、竞品机制或替代方案来支持决策 | 交回 `pm-requirement-define`，不直接把竞品做法当需求 |
| `pm-metrics-review` | 需要复盘目标、上线效果、异常波动或补充规模 / 效果证据 | 行动可交给 `pm-requirement-define`、`pm-update-write` 或后续交付流程 |
| `pm-update-write` | 结论、范围、上线内容或计划变化已经确认，需要同步、通知或留档 | 交给目标受众执行；后续效果进入 `pm-metrics-review` |
| `pm-quality-audit` | 需要判断需求分析、分级、PRD、HTML、复盘等产物是否真的完整、严谨、可交接 | 返回 `PASS`、`PASS_WITH_CONDITIONS` 或 `BLOCKED`，带证据定位的缺陷与修复条件；不替代原 skill 写正文 |

### 产物修订记录与版本追溯

所有会被留档、引用或交接的工作流产物，都必须标注当前版本、状态、修订日期和修订记录。修订记录记录“这份产物改了什么”，复杂需求的迭代台账记录“业务决策如何变化”；二者不能互相替代。上游版本变化时，受影响的 PRD、HTML、审计、验收、更新说明和观察记录必须同步标记旧版本或旧证据失效。详见[产物修订记录与版本追溯规范](./shared-references/产物修订记录与版本追溯规范.md)。

## 推荐工作流

1. **先判断输入成熟度**：模糊想法、口头提需或未定方向先用 `pm-requirement-define` 判断是否足以决策；证据缺口会影响判断时，再按需使用研究、竞品或指标 skill 并回流到需求定义。
2. **需求定义只做产品决策**：确认为什么做、做什么方向、做到哪里、不做什么、有哪些重大约束和成功假设。
3. **统一进入分级门禁**：用 `pm-requirement-grade` 判断 L0/L1/L2/L3/H 和体验交付复杂度；后者只约束 PRD / HTML 的中间层，不因“改动小”“AI 能写”跳过资金、权益、登录、隐私、生产数据、状态机、核心链路、外部依赖等红线。若要求设计前评估完整页面效果，额外标记“内容完整型 UX 原型”。
4. **按等级选择交付**：
   - L0 → 变更记录即可。
   - L1 → AI Coding 任务边界、自测、上线前检查和回滚说明。
   - L2 → 协作简报、研发影响面评估、QA 和上线观察。
   - L3 → 完整 PRD、研发 spec、测试方案、灰度 / 回滚 / 监控和评审治理。
   - H → hotfix 治理包，先止血，再补测试、复盘和长期修复。
5. **PRD 只在需要时展开**：`pm-prd-write` 接收需求定义和分级结论，负责页面、流程、规则、状态、权限、验收、原型范围与页面状态规划，以及移动端视口、滚动、固定区域和状态锚点等产品事实；要求设计前评估完整页面效果时，额外建立页面内容契约，逐项维护静态文案、动态字段、状态标签、动作和反馈；体验复杂时按需补齐页面地图、状态架构、组件行为、端与布局、覆盖计划；不重新做方向选择。
6. **需要协作视觉交付时再编译 HTML**：`pm-prd-html` 读取已确认 PRD、页面内容契约和原型规划，把正式 PRD 编译成阅读版结构，完整规格在同一 HTML 内按需展开回看，并提供固定可收起侧栏、默认静态优先的 UX 级 SVG 原型和状态上下文；命中内容完整型 UX 原型时，原型要呈现当前故事的完整用户可见内容，并报告覆盖 / 待确认 / 阻塞；复杂体验只按覆盖计划展示代表组合和必要端形态，长页在真实手机视窗内滚动，不靠缩小字号同屏展示；JavaScript 只做渐进增强，禁用脚本时仍应能阅读全部页面状态；它不重新做产品决策、不维护第二套规则、不生成 PNG 或多个文档。
7. **需要可交互体验交付时走原型支线**：体验驱动型需求（需要相关方上手操作和体验方案）由 `pm-prototype-deliver` 承接，支持“方案 → 原型 → PRD 对齐”（原型先行）与“PRD → 原型”两种顺序；开工前必须完成参照物清单、UI 设计专项技能、真实数据三项前置检查。它与 `pm-prd-html` 的静态阅读原型互斥分工，由 `pm-prd-write` 的 `prototypeTarget` 显式指定去向。诉求传达与反馈方法（概念锚点、参照物清单、文案负面清单等）统一见[诉求传达与协作反馈指南](./shared-references/诉求传达与协作反馈指南.md)。
8. **统一做质量审计**：在进入下一环节前用 `pm-quality-audit` 检查上下文充分性、逻辑有效性、覆盖完整性、追溯性、可执行性和不确定性校准。任何 Blocker 都阻塞交接；Major 必须有责任人和完成条件。
9. **更新与复盘闭环**：已确认变化用 `pm-update-write` 同步；上线效果、目标复盘或异常诊断用 `pm-metrics-review`，必要时回到需求定义重新决策。
10. **既有规则迭代单独收口**：修改已有角色、指标、结算、状态或历史数据时，读取[需求迭代闭环与收尾协议](./shared-references/需求迭代闭环与收尾协议.md)，至少维护规则变更台账和影响地图；命中时序 / 历史边界时补冻结、重算、幂等和失败恢复；发版前区分验收、文档同步、生产发布和发布后观察。

## AI 协作方式

质量审计按交付意图触发：

- **讨论 / 探索 / 初稿**：默认只调用目标 skill，产物标记为“未审计”，便于快速迭代；
- **准备交接**：当你要求 `ready`、最终定级，或准备交给设计 / 研发 / 测试 / 运营时，目标 skill 会在本次交付前自动调用 `pm-quality-audit`；
- **明确审计**：可以直接说“请用 `pm-quality-audit` 审计刚才的产物”，选择只审计或审计并修复；
- **报告留档**：默认报告返回在对话中；说“留档”或“作为交接附件”时，报告写入项目根目录 `quality-audits/`。

推荐表达：

```text
先用 pm-requirement-define 给我一个可讨论初稿，不要急着审计。

现在请把需求定义收敛到可以进入分级的 ready 状态，并在交付前自动审计；如果 BLOCKED，不要继续往下写。

请把本次质量审计报告留档，作为后续分级的交接附件。
```

完整用法、交接契约和理想实践见 [WORKFLOW_GUIDE.md](./WORKFLOW_GUIDE.md)。贡献、命名和校验规范见 [CONTRIBUTING.md](./CONTRIBUTING.md)。真实反馈如何沉淀见 [ITERATION_GUIDE.md](./ITERATION_GUIDE.md)。

## 上下游交接原则

- 每个阶段输出都必须说明：已确认事实、分析推断、待确认项、负责人 / 最晚时间、下一步 skill 或交付角色。
- “完成标准”只证明按方法生成；正式交接前必须有 `pm-quality-audit` 的审计结论和证据定位。
- 质量不能靠一句“看起来完整”自证：审计必须先只找问题，再修复，再复审；未知项不得为了通过而补造。
- HTML 是正式 PRD 的派生协作交付物；SVG 只作为 HTML 内嵌的视觉证据，不形成第二套事实源或独立规则。默认档位是 `ux-prototype`：内容、布局、状态和组件层级足够真实；只有明确选择 `wireframe` 时才输出黑白灰线框。
- 原型交付有两个独立门槛：`prototypeReadiness` 判断 PRD 是否已提供足够事实，`pm-prd-html` 的静态检查 / 质量审计判断 HTML 是否真正覆盖这些事实；不能用“HTML 已生成”替代“UX 原型已就绪”。
- 静态优先不是“没有交互”：每个页面状态必须直接存在于初始 DOM，脚本只负责状态导航、定位和高亮等渐进增强；不允许通过 `innerHTML` 或运行时渲染函数作为唯一展示路径。
- 风险等级和体验交付复杂度是两个独立维度：前者决定门禁，后者决定 PRD / HTML 是否补充复杂体验中间层。
- 上游可以为下游提供摘要，但不能替下游展开职责；下游可以复述上游结论，但不能悄悄改变上游决策。
- 分级是需求定义之后、交付之前的统一门禁；L1 自助、L2 协作、L3 PRD/spec、H hotfix 都以分级结论为入口。
- 项目画像、项目仓库规则和业务红线优先于通用降级判断。

## 原项目兼容

识别到兴趣岛/XQD、`xqd-learning-weapp`、小程序、课程、直播、回放、支付或权益时，必须叠加 `pm-requirement-grade` 的项目画像和红线，不得因为通用化而放松原项目门槛。
